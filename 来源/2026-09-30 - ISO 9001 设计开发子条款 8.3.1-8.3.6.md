## 各子条款要点（A 级 — 逐段核对后转述）

### 8.3.1 General

- 要求组织**建立、实施并保持**设计和开发过程，以确保产品和服务满足要求
- **适用范围由 QMS 范围（§4.3）决定** → 这解释了 §8.3 为什么可以被删减
- ① 给出多档例子（自创品牌自行车的厂 vs 按客户图代工的厂 vs 连锁店 vs 独立咖啡馆），说明不同组织需要承担的 8.3 要求**深度不同**

### 8.3.2 策划（10 条）

| 条目 | 主题（转述） |
|------|-------------|
| a) | 产品和服务的**性质、时长与复杂度**，以及交付要求 |
| b) | 所需**阶段**，含适用的设计评审；以及验证、确认活动 |
| c) | 验证活动（确保输出满足输入）与确认活动（确保产品满足预期用途） |
| d) | **人员**：职责与权限 |
| e) | 所需**内部与外部资源**（知识、设备、技术、能力、外部供方、临时工、技术标准） |
| f) | 参与方之间的**沟通/接口**（人数、最有效的共享方式：会议、电信、纪要） |
| g) | **客户与用户的参与**（现场跟踪、客户试验、客户研究、消费者体验） |
| h) | 后续提供产品/服务所需的内容（图纸、控制、原材料、验收准则） |
| i) | **客户/相关方期望的控制水平**（如医疗器械或航空器的安全控制） |
| j) | 所需的**文件化信息**（项目计划、会议纪要、试验报告、图纸、作业指导书、流程图） |

> ② 补充一条实务判断：**标准并不要求设计计划本身必须文件化**，但不文件化显然不是好主意；组织可自行选择「全部产品共用一个计划 / 每个产品单独计划 / 混合」。

### 8.3.3 输入（5 条）

| 条目 | 主题 |
|------|------|
| a) | **功能与性能要求**（客户、市场或组织确定） |
| b) | **以往类似设计**的信息（项目档案、图纸、规格书、经验教训） |
| c) | **法律法规要求**（直接相关于产品或服务的提供） |
| d) | 组织**承诺遵守的标准或行为准则**（行业规范、安全与健康标准） |
| e) | **失效的潜在后果**（从可能致命到客户满意度损失） |

补充要求（①）：输入须**充分、完整、无歧义**；**冲突的输入须被解决**；适用的输入须作为文件化信息保留。

### 8.3.4 控制（6 条）

| 条目 | 主题 |
|------|------|
| a) | **明确要达到的结果**；须考虑与要求的偏差（如为提升性能 vs 成本/易用性的取舍） |
| b) | **实施评审**，以确认结果能满足要求、发现问题并制定解决方案 |
| c) | **实施验证**，确保输出满足输入要求 |
| d) | **实施确认**，确保最终产品/服务满足特定或预期用途 |
| e) | 对评审、验证、确认中发现的问题**采取必要措施**；措施有效性在下次评审中评估 |
| f) | **保留文件化信息**作为已按计划执行的证据 |

① 给出的可操作例子（**这部分对实际落地最有价值**）：

| 活动 | 做法示例 |
|------|---------|
| **评审** | 复杂度高 → 正式会议 + 会议纪要作为记录；复杂度低 → 计划上签注"已评审"+签名 + 日期即可 |
| **验证** | 做替代计算；与已验证的类似设计对比；做试验与演示；放行前检查该阶段的文件化信息 |
| **确认** | 营销试验；运营试验；**在预期使用条件下**的仿真与试验；局部仿真（如建筑抗震）；客户/用户试验并取得反馈 |
| **记录** | 会议纪要、检验与试验报告、客户批准 |

> 评审、验证、确认**可以作为一个统一过程完成，也可以分开做**。

### 8.3.5 输出（4 条）

| 条目 | 主题 |
|------|------|
| a) | 与 §8.3.3 的**输入要求一致** |
| b) | **足以支持后续所有过程**（含采购、生产、交付后活动）；须考虑"谁在什么情况下使用这些输出" |
| c) | 给出**监视与测量的要求**，含验收准则与放行准则 |
| d) | 明确产品的**必要特性**，确保安全、正确地提供或使用（含使用说明） |

① 补充：设计输出**是 §8.5 生产过程的关键输入**。输出的例子：图纸、产品规格（含保存要求）、材料规格、试验要求、质量计划、控制计划、过程规格、生产设备明细、施工计划与技术计算。

> ② 的一句提醒：在工业 4.0 语境下，**"蓝图即最终设计输出"已不再成立**，很多输出是纯数字形态（3D 模型等）。

### 8.3.6 更改

- 目的：确定、评审并**控制**在设计开发过程中或之后发生的更改，**防止对符合性产生不利影响**
- ① 指出变更可来自 QMS 内任何活动、任何阶段（其 a/b/c 分类即上文提醒的内容）
- 须保留的文件化信息：**更改的影响评估结果**（对已交付产品的影响）、**更改的授权**、**所采取的措施**；以及受影响的下游过程（采购、生产、交付）所采取的措施及其沟通方式
- ⚠️ 更改**可能需要重新执行验证与确认**

> ② 的实务观察：标准本身没有明说，但**对设计输出做版本控制**（给图纸/模型编版本号或字母，或用带版本控制的设计数据库）是这条要求的实际落点。
