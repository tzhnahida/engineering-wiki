# 2026-07-24 - C宏的副作用与类型安全

- **来源**: 微信公众号文章
- **格式**: Web 图文教程
- **链接**: `https://mp.weixin.qq.com/s/JUcWqGdS0Fsipfzm2r1dxQ`
- **主题**: `max` 宏的副作用陷阱——从求值次数、类型边界到函数式宏的安全判断框架

## 内容概述

以 `#define max(a, b) ((a) > (b) ? (a) : (b))` 为切入点，剖析函数式宏的三个核心问题：参数被多次求值导致副作用放大（`max(i++, j++)`）、括号只解决优先级不解决语义、缺乏类型边界和契约感。给出三种工程方案：`static inline`（标准 C）、GNU statement expression（GNU C 生态）、以及判断宏安全性的三问框架。

## 关键知识点

1. **宏是文本替换而非函数调用** — 预处理阶段展开，编译器看到的是展开后的代码
2. **副作用放大** — `max(i++, j++)` 展开后参数出现在多个位置，`++` 被执行了不该执行的次数
3. **括号只修语法** — `((a) > (b) ? (a) : (b))` 解决了优先级问题，但不保证参数只求值一次
4. **缺乏类型边界** — 宏没有函数签名，混合类型时适用运算符的默认类型规则，而非接口定义的契约
5. **三种方案**: `static inline`（标准 C，参数一次求值 + 类型明确）> GNU `({...})`（GNU C，泛型但非标准）> 裸宏（仅简单表达式可用）
6. **安全判断三问**: 参数会不会出现在展开后多次？括号是否保护了每个参数和结果？你要的是文本替换还是有契约的接口？
