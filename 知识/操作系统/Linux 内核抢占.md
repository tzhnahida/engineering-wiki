# Linux 内核抢占

内核抢占（Kernel Preemption）是 Linux 调度器的核心机制：允许高优先级任务在内核态打断当前正在执行的低优先级内核操作，从而提高系统响应速度。

## 用户态与内核态

进程在两个区域活动：

| 区域 | 说明 | 抢占行为 |
|------|------|----------|
| **用户态** | 执行应用程序代码（刷网页、写文件） | 始终可抢占 — 时间片到期即切换 |
| **内核态** | 执行系统调用（读写文件、分配内存） | 取决于内核抢占配置 — 这是本文关注的焦点 |

进入内核态的典型路径：系统调用、中断处理、异常（缺页等）。

## 非抢占内核 vs 抢占式内核

### 非抢占内核（早期 Linux）

```
进程 A 进入内核态（执行系统调用）
    ↓
进程 A 在内核态持续执行  ← 即使有更高优先级任务就绪，也无法打断
    ↓
进程 A 主动退出内核态（返回用户态或调用 schedule()）
    ↓
调度器检查就绪队列，切换到高优先级任务
```

**特点**:
- 响应延迟高：高优先级任务必须等当前内核操作完成
- 实现简单：内核代码天然互斥，不需要细粒度锁
- 适合场景：服务器 — 吞吐量优先，响应延迟可容忍

### 抢占式内核（现代 Linux）

```
进程 A 进入内核态
    ↓
中断到达 → 中断处理完成 → 返回内核态前检查 need_resched
    ↓
如果有更高优先级任务就绪 → 立即切换（抢占）
    ↓
A 的上下文被保存，高优先级任务开始执行
```

**规则**: 只要当前内核路径没有持有锁，就可以被抢占。

## 何时禁止抢占

### 持有自旋锁（Spinlock）

自旋锁保护的临界区**禁止抢占**。如果抢占发生，新任务可能再次尝试获取同一把锁 → 死锁。

```c
spin_lock(&lock);
/* 临界区 — 抢占被禁止 */
spin_unlock(&lock);
/* 抢占恢复 */
```

### 显式禁用抢占

```c
preempt_disable();
/* 禁止抢占 — 安全操作关键数据 */
/* ... */
preempt_enable();  /* 允许抢占 */
```

内核提供的关键 API：

| 函数 | 作用 |
|------|------|
| `preempt_disable()` | 增加抢占计数，禁止抢占 |
| `preempt_enable()` | 减少抢占计数，计数归零时允许抢占 |
| `preempt_count()` | 读取当前抢占计数 |
| `might_sleep()` | 调试断言：如果在原子上下文（抢占禁止、中断上下文）中调用则触发警告 |

> `might_sleep()` 用于标注"此处可能睡眠"的函数（如 `kmalloc(GFP_KERNEL)`），帮助在编译和运行时捕获在不该睡眠的地方调用了可睡眠函数的 bug。

## 抢占计数嵌套

`preempt_disable()` 和 spinlock 共享 `preempt_count` 字段。层层嵌套时：

```c
preempt_disable();         /* count = 1 */
    spin_lock(&lock);      /* count = 2 (隐含 preempt_disable) */
        /* 关键操作 */
    spin_unlock(&lock);    /* count = 1 */
preempt_enable();          /* count = 0 → 触发抢占检查 */
```

只有当 count 归零时，`preempt_enable()` 才会检查是否需要调度。

## 内核配置选项

编译内核时的抢占模式选择：

| 配置项 | 适用场景 | 行为 |
|--------|----------|------|
| `CONFIG_PREEMPT_NONE` | 服务器 | 完全不在内核态抢占，只在返回用户态或显式调用 `schedule()` 时切换 |
| `CONFIG_PREEMPT_VOLUNTARY` | 桌面（温和） | 在可能耗时较长的内核代码点（`might_sleep()` 标注处）插入主动调度点 |
| `CONFIG_PREEMPT` | 桌面/移动（激进） | 除持有锁的临界区外，几乎任何位置都可抢占 |
| `CONFIG_PREEMPT_RT` | 工业/硬实时 | 将内核改成完全可抢占的实时机制，自旋锁变为可睡眠的 rt_mutex，中断线程化 |

### PREEMPT_RT 补丁

打上 PREEMPT_RT 后，Linux 几乎变成硬实时系统：
- 延迟可低至 **微秒级**
- 常用场景：机器人控制、航空航天、工业自动化、金融交易系统
- 代价：吞吐量进一步降低，但仍远优于专用 RTOS 的生态成本

## 代价与权衡

| 方面 | 非抢占 / NONE | 抢占 / RT |
|------|---------------|-----------|
| **响应延迟** | ms 级，不可预测 | μs 级（RT），可预测 |
| **吞吐量** | 高（上下文切换少） | 低（频繁切换） |
| **代码复杂度** | 低 | 高（更细粒度锁、死锁风险） |
| **典型场景** | 数据库服务器、批处理 | 手机 UI、机器人、工控 |

## 与嵌入式系统的关系

对于嵌入式开发者：

- **嵌入式 Linux（树莓派、i.MX、Zynq 等）**：默认使用 `PREEMPT`，平衡响应与吞吐
- **MCU 裸机 / RTOS**：不涉及 Linux 抢占，但有类似概念 — RTOS 的抢占式调度本质上是在任务级别实现同样的"高优先级打断低优先级"
- **硬实时需求**：要么用 PREEMPT_RT 补丁的 Linux，要么直接用 RTOS（FreeRTOS、Zephyr 等），关键指标是**最大延迟可预测性**，而非平均延迟
