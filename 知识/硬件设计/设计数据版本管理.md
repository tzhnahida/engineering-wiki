# 设计数据版本管理

EDA 工程数据（原理图、PCB、BOM、库）的版本管理与代码的版本管理**不是同一个问题**。代码是文本，`diff` 天然可读；EDA 源文件是二进制容器，版本控制系统只能给快照，给不了差异。这一断层是硬件团队反复回到「到底哪个是真最终版」的根本原因。

本页讨论的是**领域层**问题：版本管理需要哪些要素、差异应当落在什么粒度、以及这些要素在二进制 EDA 工具链上如何落实。

## 1. 问题的起点：文件名的表达能力上限

工程实践中常见的做法是把项目名、版本号、日期、负责人写进文件名，再按评审/打样/量产等节点分文件夹归档。

这套做法**有价值但角色有限**：

- 文件名解决的是「它叫什么」，**不是**「它为什么要这样命名」
- 一个副本只能证明某个时刻**保存过**，不能说明改动发生在**网络、器件、封装，还是布局**
- 要找出差异，只能同时打开两个工程，凭记忆逐项核对

更隐蔽的代价是**过程信息散落**：评审意见另起一份文档、讨论留在群聊记录里、发给采购或生产的又是另一份附件。文件本身没有丢，但**设计过程已经断链**——没有人能复原「为什么变成现在这样」。

> 关键区分：命名规范仍然值得坚持，但它承担的是**识别**作用；设计差异、版本分支、节点和回溯，需要由系统化的版本管理承担。**不要指望用命名约定解决变更语义问题。**

### 多方并行修改时问题会被放大

临近打样阶段，改动通常来自多条线：

- 硬件工程师按评审意见改原理图
- PCB 工程师在另一份工程里调整布局
- 采购反馈某个器件需要替换

几条线各自推进后，要确认的不再是「哪一个文件最新」，而是两个完全不同的问题：

1. 这些改动**有没有真正汇合**？
2. 生产输出是不是来自**同一个设计状态**？

前者是合并问题，后者是节点问题——都超出了文件夹和聊天记录能回答的范围。

## 2. 版本管理的六个基本要素

一个可追溯的版本过程，必须能回答下列问题。缺任何一项，设计变化就无法完整还原：

| 要素 | 回答的问题 | 缺失的后果 |
|------|-----------|-----------|
| **作者** | 修改由谁完成 | 变更无人可追溯 |
| **差异** | 哪些**设计对象**发生变化 | 只能打开两个工程凭记忆核对 |
| **节点** | 什么时候形成正式节点 | 下游不知道以哪一版为准 |
| **分支** | 不同方案如何并行推进 | 两条路线互相覆盖，只能二选一 |
| **回溯** | 需要时怎样回到历史状态 | 改错了回不去 |
| **日志** | 操作过程如何记录 | 无法区分「谁在什么时候动了什么」 |

## 3. 差异的粒度：设计对象，而非文件字节

这是整套体系里**最容易做错**的一点。

工程师真正需要的不是「两个压缩包大小相差多少」或「文件校验和是否相同」，而是：

> **网表、器件、布局发生了什么变化。**

差异必须能**落到设计对象上**——哪一个网络的连接变了、哪一个器件被替换、哪一段走线被重画。只有落在这个粒度，评审者才能判断「这个修改是否符合预期」；停留在文件层，评审只能退化为「凭记忆核对」。

这条要求直接决定了工具选型（见第 7 节）：**能存快照的系统和能算差异的系统，往往不是同一个。**

## 4. 节点 ≠ 每次保存

版本节点**不等于**每次保存。一次内部评审、一次样板输出、一次量产资料发布，重要程度各不相同。

团队需要明文约定三件事：

1. **何时**创建正式节点
2. **谁**可以确认节点
3. 下游以**哪个**节点为准

> 原则：**工具负责记录和呈现，工程规则决定这些记录如何被使用。** 引入了版本管理工具但没约定节点规则，等于把混乱从文件夹搬进了工具。

## 5. 分支：处理尚未确定的设计路线

分支适用于**结果未知**的并行探索。典型场景：

- 方案 A：保留原器件继续优化
- 方案 B：验证替代料的可行性

两边**都需要修改和评审，却不应互相覆盖**。等验证结果明确后，团队再决定后续基于哪条路线推进。

与「复制两个文件夹」相比，分支关系的价值在于能保留：

- 方案**从哪里分开**
- 各自**经历了哪些修改**
- 以及最终**是否合并**——文件夹复制永远做不到合并，只能二选一后丢弃另一个

## 6. 备份 / 版本 / 日志：三个不同的问题

三者常被混为一谈为「多存几份文件」，但它们解决的是不同问题：

| 概念 | 保留什么 | 回答的问题 |
|------|---------|-----------|
| **备份** | 可恢复的**数据状态** | 数据丢了能不能救回来 |
| **版本** | 组织**研发节点** | 以哪一版为准 |
| **日志** | 记录**操作过程** | 谁在什么时候做了什么 |

三者结合，才能完整回答「这段设计变化是怎么发生的」。把它们都做成「多存几份」，仍然无法还原一段完整的设计变化。

## 7. EDA 工具链的实现约束

### 7.1 二进制格式是根本限制

主流商业 EDA 的源文件是**私有二进制容器**，不是文本：

| 文件 | 性质 | 置信度 |
|------|------|--------|
| Allegro `.brd` | 私有二进制设计数据库 | **A** |
| OrCAD `.dsn` | 二进制 | ⚠️ **B**：来源为社区问答，非 Cadence 官方文档 |

`.brd` 的结构已被开源项目反向工程记录：文件头前 4 字节为版本魔数，其后为块状链表结构（pad / track / net / DRC marker 等）。文件内**嵌有可读 ASCII 字符串**（网络名、焊盘定义、refdes、层标识、约束类名），但整体仍不可读。

| 魔数 | 对应版本 |
|------|---------|
| `0x0013_0000` | Allegro 16.0 |
| `0x0014_0400` | Allegro 17.2 |
| `0x0015_0000` | Allegro 18.0 |

**后果**：通用版本控制系统（git/svn）会将其判定为 binary，只能提供**历史快照与回退**，`diff` 不产生任何设计对象级信息。

> [!note] 对照：文本格式工具的差异
> 若原理图/PCB 以文本格式（如 S-expression）存储，`diff` 直接可读，版本管理成本骤降。**这是文件格式带来的能力差异，不是工具优劣**——但它决定了版本管理方案的形态：文本格式工具可以「一套 git 走天下」，二进制格式工具必须**版本控制 + 专用对比工具**双轨。

### 7.2 专用设计对比能力（补偿二进制 diff 的缺失）

商业 EDA 通常在工具内提供**设计对象级**的比较功能，作为文本 diff 的替代。以 Cadence 工具链为例：

| 工具 | 比对内容 |
|------|---------|
| OrCAD Capture | 原理图之间：整个 schematic folder 或单页，报**器件与网络连接性**差异 |
| Allegro PCB Editor | PCB 之间：两遍法（原版导出 XML → 新版载入 XML → 差异高亮），可双击网络定位到板上 |
| Allegro 17.4 | 两版次路径对比；**标准对比**（仅括号内容）vs **图形对比**（小改动）；含 tolerance check 抑制微小差异；可将差异标记为 DRC |
| 原理图 ↔ PCB | 应用更新**之前**先列出差异：连接性、refdes、约束 |

`⚠️ 存疑：上述菜单路径来自社区帖与第三方教程（B 级），会随 Cadence 版本漂移，实施前需在本机版本中实测确认。`

**一个关键接口**：此类工具的中间产物往往是**结构化文本（如 XML）**。这意味着「差异报告」本身可以变成**可 diff、可入库、可评审的工件**——这是把二进制设计数据接进文本版本控制系统的关键接口。

### 7.3 企业级数据管理方案

面向有权限体系与 PLM 对接需求的团队，EDA 厂商提供服务器端数据管理系统。以 Cadence 为例（均需服务器 + 授权）：

| 方案 | 核心能力 |
|------|---------|
| **Allegro Design Workbench (ADW)** | 库版本控制（变更通知、回滚）、WIP 数据管理（安全数据保险库）、签入/签出与权限、BOM 管理与 where-used、多站点库分发 |
| **Allegro Pulse** | 「Version On Save」自动版本化、集中存储、**PCB 版本与原理图版本联动**、PLM 集成 |
| **Allegro EDM** | 器件修订自动生成、sandbox 隔离 WIP 区、**签入时对设计对象打版本** |
| **DECM** | 项目 / 用户 / 版本管理，文件操作 pre/post 触发器 |
| **Windchill Workgroup Manager** | PLM 网关，MCAD/ECAD 单点受控 |

`⚠️ 存疑：有社区帖称 ADW 历史上更偏库管理而非设计工程（B 级单源，未证实）。`

**定位**：这类方案面向数十人以上、需要权限管理与 PLM 对接的组织。**单人/小团队引入属杀鸡用牛刀**——成本与部署维护负担远超收益。

> [!note] 工具原生的版本控制动向
> 有社区帖称 Cadence 已在 Allegro X System Capture 23.1+ 内置版本控制（含「与上一提交比较」）。`⚠️ 存疑：仅见社区单帖，未见官方文档佐证，需在本机版本实测。` 若属实，反映的商业 EDA 趋势是：**把版本控制从外挂的数据管理系统下沉进工具本身**。

## 8. 落地：版本控制系统的职责边界

把第 2 节的六要素映射到通用版本控制系统（以 git 为例），可以看清职责边界：

| 要素 | 通用 VCS 能否覆盖 | 机制 |
|------|------------------|------|
| 作者 | ✅ | commit 元数据 |
| **差异** | ❌ **二进制格式下不能** | 需专用对比工具补偿 |
| 节点 | ✅ | annotated tag（不可变，优于文件名） |
| 分支 | ✅ | branch + **merge**（优于文件夹复制） |
| 回溯 | ✅ | checkout / revert |
| 日志 | ✅ | commit log |

**结论：通用 VCS 覆盖六要素中的五项，唯一缺口是二进制格式下的「差异」。**

### 差异缺口的补法

| 方法 | 做法 | 适用性 |
|------|------|--------|
| **差异报告入库** | 用工具的设计对比功能导出结构化报告（XML 等文本），提交进版本库 | ⭐ 最有效——报告可 diff、可评审、可追溯，且是纯文本 |
| **ASCII 网表代理** | 脚本导出 ASCII 网表入库，`diff` 网表即「电路变了什么」 | 覆盖连接性变更，不覆盖布局 |
| **textconv 过滤器** | 配置外部转换器，**存储仍为二进制、展示时转文本** | 需工具提供命令行接口；无 CLI 的 EDA 工具实践受限 |
| **PDF 快照** | 打印原理图/布局为 PDF 入库做人工视觉比对 | 退路方案，不可自动 diff |

### 大体积二进制的处理

设计文件常达数十 MB，直接入库会持续撑大仓库体积，应声明为二进制并交由 LFS 托管：

```gitattributes
*.brd  binary  filter=lfs  diff=lfs  merge=lfs
*.dsn  binary  filter=lfs  diff=lfs  merge=lfs
```

### 生成物与源文件的分离

**源文件入库，生成物归档**——这是与代码工程一致的原则：

| 类别 | 内容 | 处理 |
|------|------|------|
| 源文件 | 原理图、PCB、库、网表 | 进版本库 |
| 生成物 | Gerber、NC Drill、装配图、钢网文件 | 单独归档，不进版本库 |
| 评审资料 | 对比报告、评审记录 | 进版本库（文本） |

### 流程钩子

可在提交前挂载检查（如 DRC / ERC），未通过不予提交——把流程铁律从「靠自觉」变为「靠机制」。

## 9. 小结：从「多存几份」到「可回答四个问题」

命名规范的作用是**识别**，无法承担变更语义。系统化的版本管理要能让团队直接回答四个问题：

1. **谁**改了
2. **哪里**变了
3. 以**哪个节点**为准
4. 怎样**回到历史**

当这四个问题有确定答案时，工程目录里才不再需要一个又一个「真的最终版」。
