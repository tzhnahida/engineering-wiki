# 1. 嵌入式软件工程化总论

## 什么是工程化

**工程化 = 把"我会这么干"变成"谁来了都得这么干"。**

裸机时代你的流程：

```
改代码 → Keil 点 Build → 烧录 → 肉眼看一下 → "嗯没事" → push
```

这个流程的问题不是"不对"，而是**不可重复、不可追溯、不可扩展**。项目数量从 1 个变 3 个、从自己写到队友接手，这个流程会崩溃。

## 工程化的四层模型

工程化不是"用不用 CI"一个开关，而是渐变的多层体系。每一层都是对上一层的加固：

```
第 4 层   CI/CD + OTA
        编译→测试→发布全自动
        ─────────────────
第 3 层   构建标准化
        统一 Makefile/CMake，命令行可编译
        ─────────────────
第 2 层   代码质检
        自检模式、统一日志、Version 标记
        ─────────────────
第 1 层   目录统一
        所有项目长一个样，闭眼知道文件在哪
        ─────────────────
第 0 层   散装开发（你现在的位置）
```

**核心原则：每一层独立，不需要等到上层才做下层。**

- 你可以在所有项目里统一目录结构（第 1 层），哪怕还用 Keil 手动编译
- 你可以在固件里加自检代码和统一日志格式（第 2 层），哪怕没有 CI
- 你可以写 Makefile 让命令行能编译（第 3 层），哪怕没有自动触发
- 到你需要 CI 的时候，前面三层已经全部就绪，配个 yaml 就能跑

## 什么时候建哪一层

| 痛感 | 建哪层 |
|------|--------|
| "这个项目的 main.c 放哪了我忘了" | 第 1 层：目录统一 |
| "上次改完之后 IMU 精度变没变？忘了测" | 第 2 层：自检 + 日志 |
| "Keil 的 .uvprojx merge 冲突了想死" | 第 3 层：Makefile 替代 IDE 工程 |
| "三个项目扯在一起，改一个怕搞坏另外两个" | 第 4 层：CI 自动测试 |
| "给队友修 bug 每次借板子烧录" | 第 4 层：CD 自动烧录 |
| "设备装在外壳里，更新要拆螺丝" | OTA：无线更新 |

**痛到了哪一层，做到哪一层。超前建设是浪费。**

## 四层的投入产出

| 层 | 时间投入 | 维护成本 | 收益 |
|----|---------|---------|------|
| 第 1 层 目录统一 | 30 分钟，一次 | 几乎为零 | 所有项目找文件不再靠记忆 |
| 第 2 层 自检+日志 | 每个项目 10 分钟 | 零（写完不维护） | 每次烧录自动验证，有记录 |
| 第 3 层 构建标准化 | 一个 Makefile 模板 1 小时 | 低 | 命令行可编译，告别 IDE 锁定 |
| 第 4 层 CI/CD | 首次 2 小时 | 中等（runner 要更新） | 自动化，但只在多项目时值 |

## 第一性原则

工程化的每一步不是为了"看起来专业"，而是解决一个具体的痛苦。每上一层之前，问自己：

- **这层解决我现在的哪个痛？**
- 如果不痛，跳过

第 1 层和第 2 层对你现在的状态几乎零成本、高收益——可以先做。第 3 层以后的，什么时候痛什么时候做。
