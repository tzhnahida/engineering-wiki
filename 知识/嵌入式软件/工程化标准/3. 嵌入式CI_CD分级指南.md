# 3. 嵌入式 CI/CD 分级指南

> 对应工程化第 3 层（构建标准化）+ 第 4 层（CI/CD + OTA）。

## 先决条件

做 CI/CD 之前，必须先完成：

- 第 1 层（目录统一）——目录结构一致，构建脚本才能通用
- 第 2 层（自检 + 统一日志）——测试用例和日志格式就绪，CI 才有东西跑
- 第 3 层（Makefile 或 CMake，命令行可编译）——CI 不认识 Keil 的 `.uvprojx`

**没有这三层，CI 脚本只能帮你编译——这跟手动打开 Keil 点 Build 没区别。**

## 三级 CI 模型

### 第一级：纯软件 CI

**在哪跑**：GitHub Actions 免费 Ubuntu 虚拟机
**测什么**：编译 + 纯逻辑测试（算法、数据解析、状态机）
**硬件需求**：零

```
git push
  → GitHub Actions 启动 Ubuntu VM
  → 装 ARM GCC 交叉编译器
  → make → make test
  → Unity 单元测试
  → ✅ 或 ❌
```

适用场景：cJSON 解析正确性、CMSIS-DSP FFT 精度、姿态解算算法（预录 IMU 数据文件输入）、通信协议状态机。

不适用：LED、GPIO、I2C 寄存器操作、电机驱动、任何需要硬件反馈的测试。

### 第二级：QEMU 仿真 CI

**在哪跑**：GitHub Actions 免费 Ubuntu 虚拟机
**测什么**：固件整体行为（调度器切换、中断响应、外设寄存器级仿真）
**硬件需求**：零

```
git push
  → CI 编译 → qemu-system-arm -M stm32f4-discovery -kernel firmware.bin
  → 固件在虚拟 STM32 上运行
  → semihosting 输出串口日志
  → grep "[STATUS] ALL_PASS"
```

适用场景：Zephyr/FreeRTOS 调度验证、驱动寄存器读写正确性、中断嵌套时序。

不适用：引脚电平验证、模拟信号精度、时序精度 < 微秒级的场景。

**Zephyr 原生支持 QEMU**：`west build -t run`。裸机/FreeRTOS 需要自己写链接脚本 + 启动文件适配 semihosting。

### 第三级：硬件在环（HiL）

**在哪跑**：你自己的 PC（Self-hosted runner）
**测什么**：真实硬件上的完整系统测试
**硬件需求**：开发板 + PC 一直连接

```
git push
  → GitHub Actions 把任务发给你的 PC
  → 你的 PC 编译 → openocd 烧录 → Python 读串口 → 断言 TEST PASS
  → 结果回传 GitHub
```

Self-hosted runner 设置流程：

```powershell
# 在你的 PC 上跑一次
mkdir actions-runner && cd actions-runner
curl -o actions-runner-win-x64.zip https://github.com/actions/runner/releases/.../runner.zip
Expand-Archive runner.zip
./config.cmd --url https://github.com/你的仓库 --token TOKEN
./run.cmd
```

之后在 GitHub Actions yaml 里指定 `runs-on: self-hosted`，任务就在你的开发板 PC 上执行。

## 什么时候用哪级

| 条件 | 推荐 |
|------|------|
| 只有一个项目，手动测试足够 | 不建 CI。只做第 1、2 层（目录 + 自检） |
| 3+ 个项目维护，怕交叉影响 | 第一级（纯软件 CI）。每次 push 自动编译所有库的测试 |
| 固件复杂，改了调度器想验证 | 第一级 + 第二级（加 QEMU） |
| 有队友，不想每次借开发板 | 第三级（HiL）+ 硬件自动烧录 |
| 设备已部署，拆开太麻烦 | 第三级的终点：OTA 无线更新 |

## 触发策略

不要每次 push 都跑硬件测试——没用、烧 Flash 也折寿。

```yaml
on:
  push:
    paths:
      - 'src/**'        # 只有代码变动才触发
  workflow_dispatch:     # 手动触发——主要用这个
```

**硬件在环推荐策略**：纯软件 CI 在每次 push 自动跑（不烧 Flash，成本为零），硬件测试手动触发。每天晚上写完代码，点一下页面按钮，早上起来看结果。

## CI 脚本解析

以下是一个完整的三级 CI 脚本的骨架说明。不直接复制——理解每段做什么：

### 第一级：纯软件

GitHub Actions 起一台 Ubuntu VM，装 ARM GCC。对 `vendor/` 下的每个第三方库：安装依赖 → 编译 → 跑自带的 `make test`。

每个库独立一个 job（`cjson`、`unity`、`multibutton`、`flashdb`），因为它们互不依赖——哪个挂了哪个标红，不会"闪存数据库坏了导致 JSON 测试也看不到了"。

### 第二级：QEMU

同上，但编译固件后调 `qemu-system-arm`。关键参数：`-semihosting` 让 `printf` 的串口输出直接显示在 CI 日志里。`-nographic` 不弹窗口。

固件需要在自检跑完后进死循环，QEMU 超时退出。CI 脚本用 `timeout 30` 限制运行时间。

### 第三级：HiL

`runs-on: self-hosted` 把这台 job 甩给你自己的 PC。流程：

```yaml
steps:
  - uses: actions/checkout@v4
  - run: make                    # 编译
  - run: openocd flash           # 烧录
  - run: python test_read.py COM3    # Python 读串口，grep [STATUS]
```

你的 PC 必须一直在线、USB 一直连着开发板。如果 PC 关了，GitHub Actions 上这个 job 就排队等到超时。

## OTA 全自动链路

如果设备已经有无线连接，可以在 HiL 基础上加 OTA 升级：

```
git push → CI 编译 → 上传 firmware.bin 到 OTA 服务器
  → MQTT 通知设备 → 设备下载固件 → 写 Flash → 校验 CRC → 重启 → 跑新固件
```

**前提**：设备已有网络栈（WiFi/BLE/以太网）和 OTA Bootloader（参考 IAP 原理，Flash 双分区 + 回滚机制）。

**规则**：
1. 设备启动后先验证固件 CRC，失败自动回滚到旧版本
2. OTA 必须灰度——先推 1 台确认没问题，再批量推
3. 差分包优于全量包——500KB 全量固件在 WiFi 下 30 秒，差分包可能 20KB

## 决策框架

根据项目特征决定 CI 投入程度：

| 项目特征 | 推荐做法 |
|---------|------|
| 单模块、单人维护、硬件直连 | 不上 CI。手动烧录 + 自检模式验证 |
| 算法密集型（IMU、视觉、信号处理） | 纯软件 CI。预录数据驱动算法，测精度回归 |
| 多模块系统（通信总线、分布式节点） | 最值得上 HiL。交叉影响大，自动化回本 |
| 第三方库（cJSON、CMSIS-DSP、文件系统） | 不上 CI。这些是上游维护的库，不修改其代码 |

**原则**：CI 的投入必须低于"手动测试出错后的修复成本"。一个不经常改动的模块被 CI 测了一次 FAIL，这个 FAIL 的价值为零——但 CI 环境的维护成本是持续的。 |

**做 CI 之前：先把每个项目的自检和统一日志格式搞好。** 自检是第 2 层，CI 是第 4 层——第 2 层不做，第 4 层就没有东西可跑。第 2 层只需要在每个项目写 10 分钟代码，零持续成本。
