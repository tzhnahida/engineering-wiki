# RTOS vs Linux 本质区别

## 一句话

> **RTOS 关注任务怎么有秩序地跑，Linux 关注复杂系统怎么被组织和管理——它们解决的不是同一类复杂度。**

## 核心比喻

```
RTOS  = 精干班组：同一车间，高效协作，沟通快，
        但有人乱扔工具可能砸到旁边的人

Linux = 一座城市：有道路、仓库、管理部门、居民区，
        基础设施全，规则多，一个房间出事不砸整栋楼
```

## 六维对比

### 1. 运行单元：Task vs Process

| | RTOS Task | Linux Process |
|------|-----------|---------------|
| 地址空间 | 通常共享 | 通常独立（虚拟内存） |
| 崩溃影响 | 可能影响整个系统 | 通常只影响当前进程 |
| 部署方式 | 随固件整体编译 | 应用可单独编译和更新 |
| 通信 | 队列、信号量、事件组 | pipe、socket、共享内存、dbus |

> RTOS 的 Task 像车间里的工位——离得近、沟通快，但边界靠工程师自己守。

### 2. 内存模型：共享 vs 虚拟

**RTOS**：所有任务共享同一片地址空间。一个任务写飞指针 → 可能踩坏另一个任务的数据。很多 bug 特别阴：出错现场在 A，根因在 B 的越界写。

**Linux**（有 MMU）：每个进程看到自己的虚拟地址空间。内核负责虚拟→物理映射。

直接影响：
- 应用不能随便访问内核地址
- 进程间不能随便互相踩内存
- 非法访问触发 `Segmentation fault`
- 内核可做复杂的内存管理和权限控制

### 3. 实时性：确定性 vs 吞吐

| 关注点 | RTOS | Linux |
|--------|------|-------|
| 核心目标 | 关键任务在可预测时间内响应 | 整体吞吐、资源利用率、公平调度 |
| 中断响应 | 确定性延迟 | 不保证严格时间边界 |
| 适用 | 控制、电机、采样、保护 | Web 配置、视频、多服务设备 |

> [!tip] 工程上最常见组合
> **MCU/RTOS 管硬实时，Linux 管复杂应用和联网。** 这不是妥协，是分工。需要强实时 → PREEMPT_RT、Xenomai，或外挂 MCU/RTOS 处理实时部分。

| 场景 | 更适合 |
|------|--------|
| 电机闭环控制 | RTOS / 裸机 |
| 微秒级采样触发 | 硬件定时器 / RTOS |
| Web 配置页面 | Linux |
| 视频采集和网络传输 | Linux |
| 强实时 + 复杂应用 | RTOS + Linux 分工，或 PREEMPT_RT |

### 4. 驱动模型：直接控硬件 vs 接入框架

**RTOS**：初始化外设 → 提供函数 → 业务调用 `Uart_Send()`、`Sensor_Read()`。

**Linux**：驱动需接入内核框架。一个 I2C 传感器驱动要和 I2C 子系统配合；按键驱动接入 input 子系统；摄像头接入 V4L2；显示接入 DRM。

> **Linux 不是只要让硬件动起来，而是要让硬件以统一方式进入系统。** 应用不关心寄存器地址——看到的是 `/dev`、sysfs、input event、network interface 这类统一接口。

### 5. 软件形态与工具链

| 维度 | RTOS | Linux |
|------|------|-------|
| 软件形态 | 单一固件 | 内核 + RootFS + 应用 |
| 配置方式 | 固件内参数 / Flash 存储 | 配置文件、环境变量、systemd |
| 日志 | 自己设计输出链路 | syslog、journal、文件日志 |
| 应用更新 | 多数跟固件绑定 | 应用可独立部署 |
| 调试 | J-Link、串口、日志 | gdb、strace、top、dmesg、tcpdump |

### 6. 开发思维

| 思维问题 | RTOS 里常问 | Linux 里常问 |
|----------|------------|-------------|
| 谁在跑 | 哪个 Task | 哪个 process/thread/service |
| 硬件在哪 | 寄存器和驱动函数 | 设备树、驱动、/dev、/sys |
| 出错怎么看 | 串口日志、断点 | dmesg、日志、strace、gdb |
| 怎么升级 | 烧录固件 | 更新应用、RootFS、内核 |
| 怎么通信 | 队列/信号量 | socket、pipe、dbus、共享内存 |

> RTOS 工程师常站在"固件作者"角度：我掌控所有任务。Linux 工程师要站在"系统工程师"角度：应用在用户态、驱动在内核态、硬件由设备树描述、服务由 systemd 拉起。

## 选型决策

不只问"实时性够不够"，还要问：

1. 系统是否需要多应用和独立升级？
2. 是否需要复杂网络、文件系统和成熟工具生态？
3. 出错后是否希望问题被隔离在某个进程或服务里？
4. 硬件和应用是否会持续扩展？
