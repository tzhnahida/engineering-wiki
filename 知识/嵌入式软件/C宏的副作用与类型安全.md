# C宏的副作用与类型安全

函数式宏（function-like macro）在嵌入式 C 中极其常见——从 `min`/`max`、位操作到寄存器映射。它们的危险不在于"写错了"，而在于**写得太像函数了**——用法和函数相同，行为却完全不同。

## 核心原理：宏不是函数调用

```c
#define max(a, b) ((a) > (b) ? (a) : (b))

int y = max(i++, j++);
```

预处理展开后，编译器实际看到的是：

```c
int y = ((i++) > (j++) ? (i++) : (j++));
```

**不是**"先算 `i++` 和 `j++`，把结果传给 `max`"。是"把 `i++` 和 `j++` 原封不动复制进多个位置"。

| | 函数调用 | 宏展开 |
|------|----------|---------|
| 参数求值时机 | 调用前各求值一次 | 展开后出现几次就求值几次 |
| 参数类型检查 | 函数签名约束 | 无，运算符类型规则决定 |
| 作用域 | 局部副本 | 直接操作调用处的变量 |

## 副作用放大

### 示例：`max(i++, j++)`

```c
int i = 3, j = 5;
int m = max(i++, j++);
/* 展开: ((i++) > (j++) ? (i++) : (j++)) */

/* 实际执行路径:
   1. i++ > j++ → 3 > 5 → false，比较后 i=4, j=6
   2. 条件为假 → 执行第三个操作数 j++
   3. j++ 返回 6，j 再增到 7
   结果: m=6, i=4, j=7  ← 不是直觉的 m=5! */
```

`j++` 被执行了**两次**：比较时一次，返回时一次。副作用次数不可控。

### 升级为未定义行为：`max(k++, k++)`

```c
int k = 3;
int m = max(k++, k++);
/* 展开: ((k++) > (k++) ? (k++) : (k++))  */
/* 同一对象被无序修改多次 → undefined behavior   */
/* Clang 17: warning: multiple unsequenced modifications to 'k' */
```

`max(i++, j++)` 的问题是多算了一次（逻辑错误但语义明确）。`max(k++, k++)` 直接进入 C 标准放任不管的领域——不能再猜结果。

> `?:` 运算符的"第一个操作数先算，再算分支"规则只保证条件部分和选中分支之间有先后——**救不了条件内部自己已经打架的表达式。**

## 括号只解决了一半问题

```c
#define bad_max(a, b) a > b ? a : b
2 * bad_max(3, 4)
/* 展开: 2 * 3 > 4 ? 3 : 4  → 错误：* 优先级高于 > */
```

标题里的 `((a) > (b) ? (a) : (b))` 确实修好了优先级——但括号只解决"语法结合"，**不解决副作用次数，不解决类型边界**。

| 括号保护 | 做到了 | 没做到 |
|----------|--------|--------|
| 参数被括号括起 | ✅ `(a)`, `(b)` | — |
| 整个表达式被括号括起 | ✅ `((...) ? ...)` | — |
| 参数只求值一次 | — | ❌ 取决于出现次数 |
| 类型安全 | — | ❌ 没有函数签名 |

## 缺乏类型边界

```c
static inline int max_int(int a, int b) {
    return a > b ? a : b;
}
```

函数签名明确了：参数是 `int`、各求值一次、返回 `int`。宏没有这层契约——传入混合类型（`uint32_t` vs `int32_t`、`float` vs `double`）时，发生的是运算符默认的类型转换规则，不是 `max` 这个"接口"替你定义的行为。

## 工程方案

### 标准 C：`static inline`（首选）

```c
static inline int max_int(int a, int b) {
    return a > b ? a : b;
}

int i = 3, j = 5;
int m = max_int(i++, j++);
/* 结果: m=5, i=4, j=6  ← 函数语义，符合直觉 */
```

**保留了两个关键性质**：参数先各算一次；接口有明确类型。

### GNU C：Statement Expression（泛型场景）

```c
#define max_gnu(a, b)                    \
    ({ __typeof__(a) _a = (a);           \
       __typeof__(b) _b = (b);           \
       _a > _b ? _a : _b; })

int i = 3, j = 5;
int m = max_gnu(i++, j++);
/* 结果: m=5, i=4, j=6  ← 参数各算一次 */
```

`({...})` 是 GNU statement expression，`__typeof__` 是 GNU 扩展。Clang 在 `-Wpedantic` 下会报警。**锁定 GNU C/Clang 生态时是实用写法；需要标准可移植性时用 `static inline`。**

### 三种方案对比

| | 裸宏 `((a)>(b)?(a):(b))` | `static inline` | GNU `({...})` |
|------|------|------|------|
| 参数一次求值 | ❌ | ✅ | ✅ |
| 类型检查 | ❌ | ✅ 固定类型 | ✅ `typeof` 泛型 |
| 标准 C | ✅ | ✅ | ❌ GNU 扩展 |
| 内联保证 | 总是内联（文本） | 编译器决定 | 总是内联（文本） |
| 适用场景 | 极简单表达式 | 固定类型的函数替代 | GNU 生态的泛型工具 |

## 安全判断三问

看到任何函数式宏时按这三条过一遍：

1. **参数会不会在展开后出现多次？** 如果会 → 带副作用的实参（`++`、`--`、赋值、函数调用、寄存器读取）危险
2. **每个参数和整个结果，是否都被括号保护？** 如果没有 → 运算符优先级可能把表达式带偏
3. **你要的是文本替换，还是一个有类型边界、只求值一次的接口？** 如果是后者 → 用函数，别用宏硬演

这三条不只适用于 `max`——它们让你在看到任何函数式宏时都能先判断：它到底是"像函数"，还是只是"看起来像函数"。

## 提取完整性

| 类别 | 状态 | 说明 |
|------|------|------|
| 宏展开机制 | ✅ 完整 | 预处理文本替换，展开后代码与原代码的对应关系 |
| 副作用放大 | ✅ 完整 | `max(i++,j++)` 全流程逐步分析，结果 m=6 的原因 |
| 未定义行为边界 | ✅ 完整 | `max(k++,k++)` 与 `max(i++,j++)` 的区分 |
| 括号的局限性 | ✅ 完整 | 语法保护 vs 语义保护 |
| 类型边界缺失 | ✅ 完整 | 宏没有函数签名，类型规则由运算符决定 |
| static inline 方案 | ✅ 完整 | 标准 C，一次求值 + 类型明确 |
| GNU expression 方案 | ✅ 完整 | 泛型 + 无副作用，非标准，需标注 |
| 安全判断框架 | ✅ 完整 | 三问方法论 |
