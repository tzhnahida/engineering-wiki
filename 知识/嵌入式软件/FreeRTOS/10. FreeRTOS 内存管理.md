# FreeRTOS 内存管理

## 动态 vs 静态创建

FreeRTOS 内核对象（任务、队列、信号量、定时器）有两种创建方式：

| | 动态创建 | 静态创建 |
|------|---------|---------|
| 内存来源 | FreeRTOS 堆（`pvPortMalloc`） | 用户提供静态缓冲区 |
| API | `xTaskCreate`, `xQueueCreate` ... | `xTaskCreateStatic`, `xQueueCreateStatic` ... |
| 控制宏 | `configSUPPORT_DYNAMIC_ALLOCATION` | `configSUPPORT_STATIC_ALLOCATION` |
| 优点 | 运行时灵活增减 | 零运行时分配风险，确定性 |
| 适合 | 开发阶段、资源灵活 | 安全关键、资源预算严格的生产系统 |

静态创建时，用户定义栈数组和 TCB 空间：

```c
StackType_t xTaskStack[ configMINIMAL_STACK_SIZE ];
StaticTask_t xTaskTCB;
xTaskCreateStatic( vTask, "name", configMINIMAL_STACK_SIZE,
                   NULL, 1, xTaskStack, &xTaskTCB );
```

当 `configSUPPORT_DYNAMIC_ALLOCATION` 为 0 时，所有 `pvPortMalloc` 调用被禁用，必须使用静态 API。

---

## 五种堆实现 — 总览

| | heap_1 | heap_2 | heap_3 | heap_4 | heap_5 |
|------|--------|--------|--------|--------|--------|
| `vPortFree()` | ❌ | ✅ | ✅ (wrap libc) | ✅ | ✅ |
| 相邻块合并 | N/A | ❌ | 依赖 libc | ✅ | ✅ |
| 空闲链表顺序 | N/A | 按大小升序 | 依赖 libc | 按地址升序 | 按地址升序 |
| `configTOTAL_HEAP_SIZE` | ✅ | ✅ | ❌ | ✅ | ❌ |
| 内存来源 | 静态数组 | 静态数组 | 系统堆 (linker) | 静态数组 | 多区域 |
| 碎片风险 | 无 | 严重的 | 依赖 libc 实现 | 较低的 | 较低的 |
| 所在文件 | `heap_1.c` | `heap_2.c` | `heap_3.c` | `heap_4.c` | `heap_5.c` |

## 核心数据结构 — BlockLink_t

heap_2/4/5 共用同一链表结点定义：

```c
typedef struct A_BLOCK_LINK
{
    struct A_BLOCK_LINK * pxNextFreeBlock;  /* 下一空闲块（或 NULL） */
    size_t xBlockSize;                       /* 本块大小（含 BlockLink_t 自身） */
} BlockLink_t;
```

- `xBlockSize` 包含 `BlockLink_t` 结构体的空间 + 可用数据空间
- 对齐后的结构体大小：`xHeapStructSize = ( sizeof(BlockLink_t) + 7 ) & ~7`（8 字节对齐）
- `heapMINIMUM_BLOCK_SIZE = 2 * xHeapStructSize` — 分裂后剩余空间必须大于此值，否则不分（会产生无法再分配的外部碎片）

**heap_4/5 的区别**：block size 的最高有效位（MSB）用作 `xBlockAllocatedBit`：

```c
xBlockAllocatedBit = ((size_t)1) << (sizeof(size_t) * 8 - 1);
// 设此位 → 块已分配；清此位 → 块空闲
pxBlock->xBlockSize |= xBlockAllocatedBit;   // 分配时置位
pxLink->xBlockSize &= ~xBlockAllocatedBit;   // 释放时清除
```

这允许在释放时校验：`configASSERT(pxLink->xBlockSize & xBlockAllocatedBit)` 防止重复释放。

## heap_1 — 最简单的分配器

**原理**：单向 bump allocator，无释放能力。适合"创建即永远"的应用。

```c
static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];   // 堆空间
static size_t xNextFreeByte = 0;                   // 当前空闲偏移
```

**分配流程**：
1. 对齐请求大小到 `portBYTE_ALIGNMENT` 边界
2. 挂起调度器（`vTaskSuspendAll`）
3. 首次调用时计算对齐起始地址（`pucAlignedHeap`）
4. 检查 `xNextFreeByte + xWantedSize` 不超过 `configADJUSTED_HEAP_SIZE`
5. 返回 `pucAlignedHeap + xNextFreeByte`，递增偏移
6. 恢复调度器

**配置**：
- `configTOTAL_HEAP_SIZE` — 堆总大小（字节）
- `configAPPLICATION_ALLOCATED_HEAP` — 为 1 时用户自行定义 `ucHeap[]`（可放在特定 RAM 段）
- `configADJUSTED_HEAP_SIZE = configTOTAL_HEAP_SIZE - portBYTE_ALIGNMENT`（因对齐可能损失几个字节）

**vPortFree**：调用会触发 `configASSERT(pv == NULL)` — 从不释放。

**碎片**：不存在。按顺序分配，永不释放。

---

## heap_2 — 可释放但无合并

**原理**：heap_2 维护一个**按块大小升序排列**的空闲链表。`pvPortMalloc` 使用 best-fit 搜索。vPortFree 只是重新插入链表，不尝试合并相邻块。

```c
static BlockLink_t xStart, xEnd;                 // 链表哨兵
static size_t xFreeBytesRemaining = configADJUSTED_HEAP_SIZE;
```

**初始化**（`prvHeapInit`）：
1. 对齐 `ucHeap` 起始地址
2. `xStart.pxNextFreeBlock = pucAlignedHeap; xStart.xBlockSize = 0`
3. `xEnd.xBlockSize = configADJUSTED_HEAP_SIZE; xEnd.pxNextFreeBlock = NULL`
4. 首个（也是唯一）空闲块覆盖整个对齐后堆空间
5. 将这块通过 `xStart → 空闲块 → xEnd` 链入

**分配流程**：
1. 请求大小增加 `heapSTRUCT_SIZE`（容纳 BlockLink_t）
2. 对齐到 `portBYTE_ALIGNMENT`
3. 从 `xStart` 开始遍历链表，找到第一个 **xBlockSize >= xWantedSize** 的块（因链表按大小排序，这是 best-fit）
4. 如果块大小超过所需 + `heapMINIMUM_BLOCK_SIZE`，则分裂：在分配块末尾创建新 BlockLink_t，剩余部分插回自由链表
5. 将分配块从链表中移除
6. 递减 `xFreeBytesRemaining`

**插入宏**（`prvInsertBlockIntoFreeList`）：
```c
#define prvInsertBlockIntoFreeList( pxBlockToInsert )
    // 按 xBlockSize 升序遍历链表，找到插入位置
    // 将 pxBlockToInsert 链入
    // 不做相邻地址判断 → 无合并
```

**碎片**：严重。典型的"多次分配后释放块大小不匹配，无法满足后续大分配"模式。比如 alloc(100)、alloc(200)、free(第一个)、alloc(300) — 1100 的空闲空间可能不足以满足 300，因为释放的 100 块在链表最前面，而 300 可能在链表后面某个小块前面就停住了... 实际上 best-fit 会找到大小最合适的而不是第一个足够大的...让我纠正：链表按大小升序，所以它找到的第一个满足 `xBlockSize >= xWantedSize` 的就是最小的满足块（best-fit）。但释放的块尺寸小（100）放在链表前面，大块在后面。如果申请的 300 找不到 ≥300 的块，即使总剩余够也会失败。

> 由于不合并相邻空闲块，heap_2 碎片化不可逆。不被新项目推荐。

## heap_3 — 包装标准库 malloc/free

**原理**：最简单的实现 — 直接将 FreeRTOS 的 `pvPortMalloc` / `vPortFree` 委托给 C 标准库的 `malloc` / `free`，用 `vTaskSuspendAll` 做线程保护。

```c
void * pvPortMalloc( size_t xWantedSize )
{
    void * pvReturn;
    vTaskSuspendAll();
    {
        pvReturn = malloc( xWantedSize );
    }
    ( void ) xTaskResumeAll();
    return pvReturn;
}
```

**特点**：
- **不使用 `configTOTAL_HEAP_SIZE`** — 堆大小由链接脚本的堆区域定义
- 线程安全通过挂起调度器实现：`vTaskSuspendAll` 阻止其他任务运行，但**不屏蔽中断**。因此 heap_3 的 `pvPortMalloc` **不能在 ISR 中调用**（即使是从 ISR 安全的任务创建函数也不行）
- 碎片化特性完全依赖 C 标准库实现
- 适合已有成熟 libc malloc 的平台（如 Linux 模拟、带 MMU 的 MCU）

> heap_3 是唯一依赖系统 linker 堆配置的实现。对于裸机 MCU 通常不用它，因为标准库 malloc 未必线程安全且可能较大。

## heap_4 — 生产推荐（带相邻块合并）

**原理**：与 heap_2 类似但有两个关键区别：（1）空闲链表按**地址升序**排列；（2）`prvInsertBlockIntoFreeList` 会合并左右相邻的空闲块。

```c
static BlockLink_t xStart;          // 链表头哨兵
static BlockLink_t * pxEnd = NULL;  // 堆结束哨兵
static size_t xBlockAllocatedBit;   // MSB 标记位
```

**初始化**：类似 heap_2，但在堆末尾放置 `pxEnd` 哨兵（`xBlockSize=0, pxNextFreeBlock=NULL`），并使首个空闲块覆盖从对齐起始到 `pxEnd` 之前的所有空间。

**prvInsertBlockIntoFreeList** — 核心合并逻辑：

```c
static void prvInsertBlockIntoFreeList( BlockLink_t * pxBlockToInsert )
{
    // 1. 按 地址升序 遍历，找到插入位置
    for( pxIterator = &xStart;
         pxIterator->pxNextFreeBlock < pxBlockToInsert;
         pxIterator = pxIterator->pxNextFreeBlock ) { }

    // 2. 尝试与前面的块合并：
    //    (prev_addr + prev_size) == insert_addr → 可合并
    if( (puc + pxIterator->xBlockSize) == (uint8_t *)pxBlockToInsert )
    {
        pxIterator->xBlockSize += pxBlockToInsert->xBlockSize;
        pxBlockToInsert = pxIterator;  // 指向已扩展的 prev 块
    }

    // 3. 尝试与后面的块合并：
    //    (insert_addr + insert_size) == next_addr → 可合并
    if( (puc + pxBlockToInsert->xBlockSize) == (uint8_t *)pxIterator->pxNextFreeBlock )
    {
        if( pxIterator->pxNextFreeBlock != pxEnd )
        {
            pxBlockToInsert->xBlockSize += pxIterator->pxNextFreeBlock->xBlockSize;
            pxBlockToInsert->pxNextFreeBlock = pxIterator->pxNextFreeBlock->pxNextFreeBlock;
        }
        else
        {
            pxBlockToInsert->pxNextFreeBlock = pxEnd;  // 合并到末尾
        }
    }

    // 4. 更新前驱指向合并后的块
    if( pxIterator != pxBlockToInsert )
        pxIterator->pxNextFreeBlock = pxBlockToInsert;
}
```

合并条件公式：`地址A + 大小A == 地址B` → A 和 B 在内存中相邻 → 可合并。

**分配中的 MSB 标记**：
```c
pxBlock->xBlockSize |= xBlockAllocatedBit;  // 标记已分配
pxBlock->pxNextFreeBlock = NULL;             // 分配的块无 next 指针
```

**释放中的 MSB 校验**：
```c
configASSERT( (pxLink->xBlockSize & xBlockAllocatedBit) != 0 );  // 防止重复释放
configASSERT( pxLink->pxNextFreeBlock == NULL );                   // 防止 double free
pxLink->xBlockSize &= ~xBlockAllocatedBit;  // 清除占用标记
prvInsertBlockIntoFreeList( pxLink );        // 插回并合并
```

**统计信息**（heap_4 独有 `vPortGetHeapStats`）：

```c
typedef struct xHeapStats {
    size_t xAvailableHeapSpaceInBytes;       // 总剩余字节
    size_t xSizeOfLargestFreeBlockInBytes;   // 最大连续块（关键指标）
    size_t xSizeOfSmallestFreeBlockInBytes;  // 最小空闲块
    size_t xNumberOfFreeBlocks;              // 空闲块数量
    size_t xMinimumEverFreeBytesRemaining;   // 历史最低剩余
    size_t xNumberOfSuccessfulAllocations;   // 成功分配次数
    size_t xNumberOfSuccessfulFrees;         // 成功释放次数
} HeapStats_t;
```

**碎片**：较低。合并相邻块能回收大部分碎片，但无法消除所有碎片（例如分配器内部分裂导致的 `BlockLink_t` 开销无法回收）。

> heap_4 是**生产环境的首选**。平衡了代码大小（~500 字节）、性能（O(n) 分配）和防碎片能力。

## heap_5 — 多区域非连续堆

**原理**：算法与 heap_4 完全一致，但**堆由多个不连续的内存区域组成**。区域通过 `vPortDefineHeapRegions()` 预先传入。

```c
typedef struct HeapRegion
{
    uint8_t * pucStartAddress;  // 起始地址
    size_t   xSizeInBytes;      // 区域大小
} HeapRegion_t;

void vPortDefineHeapRegions( const HeapRegion_t * const pxHeapRegions );
```

**约束**：
1. **必须在首次 `pvPortMalloc` 之前调用** — 通常作为 `main()` 的第一条语句
2. 数组以 `{NULL, 0}` 终止
3. 区域必须**按地址升序排列**
4. 只能调用一次

**初始化过程**：
1. 遍历每个区域，对齐起始地址
2. 首个区域的起始设为 `xStart.pxNextFreeBlock`
3. 每个区域末尾放置 `pxEnd` 哨兵
4. 将相邻区域通过 `pxNextFreeBlock` 串联：前一个区域的哨兵指向后一个区域的首个空闲块
5. 所有区域的第一个空闲块的 `xBlockSize = 对齐后区域大小 - xHeapStructSize`

```c
// 串联关系：
// xStart → 区域1首块 → ... → 区域1哨兵(pxEnd) → 区域2首块 → ... → 区域2哨兵(pxEnd)
//                               ↑ pxPreviousFreeBlock 指向的正是区域1末尾
```

**使用示例**：
```c
HeapRegion_t xHeapRegions[] =
{
    { (uint8_t *)0x20000000, 0x10000 },  // CCM / 内部 SRAM 64KB
    { (uint8_t *)0x80000000, 0x80000 },  // 外部 SDRAM 512KB
    { NULL, 0 }
};
vPortDefineHeapRegions( xHeapRegions );
// 现在 pvPortMalloc 可用
```

**碎片**：与 heap_4 相同（有合并），但跨区域的碎片无法消除 — 因为不同区域的块物理上不相邻，无法跨区域合并。

## 选型指南

| 使用场景 | 推荐 | 原因 |
|---------|------|------|
| 启动时创建所有对象，永不释放 | heap_1 | 零开销、零碎片、最小编译体积 |
| 需要 malloc/free，代码简洁不挑剔 | heap_3 | 让 libc 负责，但注意 ISR 安全性 |
| 单 RAM 区域，需要动态创建/删除 | heap_4 | 合并策略使碎片可控，生产首选 |
| 内部 SRAM + 外部 SDRAM 混合使用 | heap_5 | 唯一支持多区域的方案 |
| ❌ 新项目 | heap_2 | 无合并 → 不可逆碎片 → 不可靠 |

**内存监控**：
```c
xPortGetFreeHeapSize();             // 即时剩余（heap_1/2/4/5）
xPortGetMinimumEverFreeHeapSize();  // 历史最低（heap_4/5）
vPortGetHeapStats( &stats );        // 完整状态（heap_4/5）
```

## 碎片图解

### heap_2 — 无合并（空间浪费）

```
初始: [ FREE 1024 ]
alloc(200): [ALLOC 200][ FREE 824 ]
alloc(300): [ALLOC 200][ALLOC 300][ FREE 524 ]
free(200):  [FREE 200][ALLOC 300][ FREE 524 ]
               ↑ 无法与相邻 ALLOC 合并
alloc(400): FAIL! — 最大连续 524，但 200+524 在逻辑上不连续
```

### heap_4 — 可合并（空间回收）

```
初始: [ FREE 1024 ]
alloc(200): [ALLOC 200][ FREE 824 ]
alloc(300): [ALLOC 200][ALLOC 300][ FREE 524 ]
free(200):  [ FREE 200][ALLOC 300][ FREE 524 ]
               ← 试图与前后合并，但 ALLOC 300 阻止
free(300):  [ FREE 200][ FREE 300][ FREE 524 ]
               ← 释放后触发合并: 200+300+524 = 1024
结果: [ FREE 1024 ] ✅ 完全恢复
```

## 配置宏速查

| 宏 | 作用 | 适用 heap |
|------|------|----------|
| `configTOTAL_HEAP_SIZE` | 堆数组总大小（字节） | heap_1/2/4 |
| `configAPPLICATION_ALLOCATED_HEAP` | 1=用户自定 `ucHeap[]` | heap_1/2/4 |
| `configSUPPORT_DYNAMIC_ALLOCATION` | 0=禁用动态分配 | 所有 |
| `configSUPPORT_STATIC_ALLOCATION` | 1=启用静态分配 API | 所有 |
| `configUSE_MALLOC_FAILED_HOOK` | 1=使能分配失败回调 | 所有 |
| `portBYTE_ALIGNMENT` | 对齐粒度（默认 8） | 所有 |
| `configSTACK_ALLOCATION_FROM_SEPARATE_HEAP` | 1=任务栈从独立堆分配 | 所有 |
