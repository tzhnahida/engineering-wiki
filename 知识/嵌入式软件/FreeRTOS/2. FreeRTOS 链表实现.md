# FreeRTOS 链表实现

FreeRTOS 内核中几乎所有核心调度操作（就绪队列、阻塞/延时队列、事件等待队列）都建立在一个统一的链表数据结构之上。该实现是**带哨兵节点的循环双链表**，针对调度器的使用模式做了专门优化：支持 O(1) 插入尾部、O(1) 删除，以及按 `xItemValue` 升序插入。

## 数据结构

### `xLIST_ITEM`（`ListItem_t`）

```c
struct xLIST_ITEM
{
    listFIRST_LIST_ITEM_INTEGRITY_CHECK_VALUE
    configLIST_VOLATILE TickType_t xItemValue;
    struct xLIST_ITEM * configLIST_VOLATILE pxNext;
    struct xLIST_ITEM * configLIST_VOLATILE pxPrevious;
    void * pvOwner;
    struct xLIST * configLIST_VOLATILE pxContainer;
    listSECOND_LIST_ITEM_INTEGRITY_CHECK_VALUE
};
typedef struct xLIST_ITEM ListItem_t;
```

| 字段 | 用途 |
|------|------|
| `xItemValue` | 列表排序依据的值。在就绪队列中为任务优先级；在延时队列中为任务唤醒的 tick 计数值。类型为 `TickType_t`（通常为 `uint32_t` 或 `uint16_t`）。 |
| `pxNext` | 指向链表中下一个节点。`configLIST_VOLATILE` 修饰（默认展开为空），支持中断中访问。 |
| `pxPrevious` | 指向链表中前一个节点。 |
| `pvOwner` | 指向包含该列表项的对象，通常为 **TCB（任务控制块）**。建立列表项与任务之间的双向关联。 |
| `pxContainer` | 指向当前所在的列表。`NULL` 表示该列表项未加入任何列表。这使得删除时无需传入列表指针。 |
| 完整性检查值 | 当 `configUSE_LIST_DATA_INTEGRITY_CHECK_BYTES == 1` 时启用，在列表项前后加入固定标记以检测内存越界覆盖。 |

关键设计：`pvOwner` 与 `pxContainer` 建立了**对象 → 列表项 → 列表**的双向链路。给定 TCB 能找到其列表项，给定列表项能找到其所属列表和所属任务。

---

### `xMINI_LIST_ITEM`（`MiniListItem_t`）

```c
struct xMINI_LIST_ITEM
{
    listFIRST_LIST_ITEM_INTEGRITY_CHECK_VALUE
    configLIST_VOLATILE TickType_t xItemValue;
    struct xLIST_ITEM * configLIST_VOLATILE pxNext;
    struct xLIST_ITEM * configLIST_VOLATILE pxPrevious;
};
typedef struct xMINI_LIST_ITEM MiniListItem_t;
```

与 `xLIST_ITEM` 的区别：

- **去掉了 `pvOwner` 和 `pxContainer` 两个指针字段**。
- 该结构仅用于列表的**哨兵节点（sentinel）** —— 哨兵不需要所属对象，也不属于另一个列表。
- 每节省 2 个指针（32 位系统 8 字节，64 位系统 16 字节），系统中所有就绪队列、延时队列等加起来节省可观。
- **类型转换**：代码中大量将 `MiniListItem_t *` 强制转为 `ListItem_t *`，因为两个结构的内存布局在 `pxNext`/`pxPrevious`/`xItemValue` 部分完全对齐。

### `xLIST`（`List_t`）

```c
typedef struct xLIST
{
    listFIRST_LIST_INTEGRITY_CHECK_VALUE
    volatile UBaseType_t uxNumberOfItems;
    ListItem_t * configLIST_VOLATILE pxIndex;
    MiniListItem_t xListEnd;
    listSECOND_LIST_INTEGRITY_CHECK_VALUE
} List_t;
```

| 字段 | 用途 |
|------|------|
| `uxNumberOfItems` | 列表中**实际元素**的数量（不含哨兵）。`volatile` 修饰，确保中断修改后主循环读取的正确性。 |
| `pxIndex` | **漫游指针**，用于 `listGET_OWNER_OF_NEXT_ENTRY` 宏实现轮询调度。初始指向 `xListEnd`，每次调用推进到下一元素。 |
| `xListEnd` | 嵌入式哨兵节点（`MiniListItem_t`），不在 `uxNumberOfItems` 计数中。始终在列表"末尾"。 |

哨兵节点是列表结构的一部分，**嵌入在 `List_t` 内部**而非堆分配，因此列表的创建和销毁无需额外的内存管理。

## 哨兵节点机制

FreeRTOS 链表是一个**带哨兵的循环双链表**：

```
初始（空列表）：
  xListEnd.pxNext → [xListEnd]
  xListEnd.pxPrevious → [xListEnd]
  uxNumberOfItems = 0

有 N 个元素时：
  [xListEnd] ←→ [Item 1] ←→ [Item 2] ←→ ... ←→ [Item N] ←→ [xListEnd]
  -- pxNext 方向循环 --
  -- pxPrevious 方向循环 --
```

- 哨兵的 `xItemValue` 固定为 `portMAX_DELAY`（`TickType_t` 的最大值），确保在按值升序排列时**始终位于列表末尾**。
- `listGET_HEAD_ENTRY(pxList)` 展开为 `pxList->xListEnd.pxNext`，即哨兵之后第一个元素。
- `listGET_END_MARKER(pxList)` 返回哨兵引用，用于迭代终止判断。
- 循环结构消除了对 `NULL` 的边界检查，简化了插入和删除操作。

## 核心函数分析

### `vListInitialise` — 列表初始化

```c
void vListInitialise( List_t * const pxList )
{
    pxList->pxIndex = ( ListItem_t * ) &( pxList->xListEnd );
    pxList->xListEnd.xItemValue = portMAX_DELAY;
    pxList->xListEnd.pxNext = ( ListItem_t * ) &( pxList->xListEnd );
    pxList->xListEnd.pxPrevious = ( ListItem_t * ) &( pxList->xListEnd );
    pxList->uxNumberOfItems = ( UBaseType_t ) 0U;
    listSET_LIST_INTEGRITY_CHECK_1_VALUE( pxList );
    listSET_LIST_INTEGRITY_CHECK_2_VALUE( pxList );
}
```

**逻辑步骤**：

1. `pxIndex` 指向哨兵。初始时列表中无元素，漫游指针和哨兵重合。
2. `xListEnd.xItemValue = portMAX_DELAY` —— 保证后续按值插入时，哨兵始终位于末尾。
3. 哨兵的 `pxNext` 和 `pxPrevious` 都指向自身 —— 自循环的空列表模式。
4. `uxNumberOfItems = 0` —— 哨兵不计入计数。
5. 写入完整性检查值（可选）。

`listLIST_IS_INITIALISED(pxList)` 宏通过检查 `xListEnd.xItemValue == portMAX_DELAY` 来判断列表是否已初始化。

### `vListInitialiseItem` — 列表项初始化

```c
void vListInitialiseItem( ListItem_t * const pxItem )
{
    pxItem->pxContainer = NULL;
    listSET_FIRST_LIST_ITEM_INTEGRITY_CHECK_VALUE( pxItem );
    listSET_SECOND_LIST_ITEM_INTEGRITY_CHECK_VALUE( pxItem );
}
```

**逻辑**：

- 只将 `pxContainer` 置 `NULL`，表示该列表项不在任何列表中。
- **不初始化** `pxNext`、`pxPrevious`、`xItemValue` 和 `pvOwner`。这些字段在插入/设置时由调用者赋值。
- 这种最小化初始化是经过设计的 —— 列表项在被插入前，这些字段的值无关紧要；插入时会重新设置。减少初始化操作提升性能。

### `vListInsert` — 按值排序插入（核心调度功能）

```c
void vListInsert( List_t * const pxList, ListItem_t * const pxNewListItem )
{
    ListItem_t * pxIterator;
    const TickType_t xValueOfInsertion = pxNewListItem->xItemValue;

    listTEST_LIST_INTEGRITY( pxList );
    listTEST_LIST_ITEM_INTEGRITY( pxNewListItem );

    if( xValueOfInsertion == portMAX_DELAY )
    {
        pxIterator = pxList->xListEnd.pxPrevious;
    }
    else
    {
        for( pxIterator = ( ListItem_t * ) &( pxList->xListEnd );
             pxIterator->pxNext->xItemValue <= xValueOfInsertion;
             pxIterator = pxIterator->pxNext )
        {
            /* empty loop body */
        }
    }

    pxNewListItem->pxNext = pxIterator->pxNext;
    pxNewListItem->pxNext->pxPrevious = pxNewListItem;
    pxNewListItem->pxPrevious = pxIterator;
    pxIterator->pxNext = pxNewListItem;

    pxNewListItem->pxContainer = pxList;
    ( pxList->uxNumberOfItems )++;
}
```

**排序逻辑**：

1. **遍历起点**：从哨兵 `xListEnd` 开始（通过 `&(pxList->xListEnd)`）。
2. **遍历条件**：`pxIterator->pxNext->xItemValue <= xValueOfInsertion`
   - 只要下一个节点的值 <= 插入值，就继续前进。
   - 遇到第一个值**大于**插入值的节点时停止，插入位置就在 `pxIterator` 之后。
3. **等值处理**：条件使用 `<=` 而非 `<`，因此新元素插入到**所有同值元素之后**。这对就绪队列至关重要——同等优先级的任务按 FIFO 顺序调度（轮询 round-robin）。
4. **特殊分支**：当 `xValueOfInsertion == portMAX_DELAY` 时，直接取哨兵的前一个节点作为 `pxIterator`。原因：哨兵本身的值也是 `portMAX_DELAY`，若进入循环便会无限遍历（哨兵的 `pxNext` 永远指向列表中有 `<=` 值的项）。
5. **时间复杂度**：O(n)，n 为列表长度。在 FreeRTOS 中，列表通常很短（就绪队列条数 <= 优先级数，延时队列条数 <= 任务数），因此线性遍历可以接受。

**插入后链表结构**（假设插入值为 3）：

```
Before:  [Sentinel] ↔ [1] ↔ [2] ↔ [4] ↔ [Sentinel]
After:   [Sentinel] ↔ [1] ↔ [2] ↔ [3] ↔ [4] ↔ [Sentinel]
                         ↑              ↑
                      pxIterator   pxIterator->pxNext (原来的)
```

**关键注释**：源代码中有一段重要的 NOTE，列出了 5 种导致 `vListInsert` 崩溃的常见原因：
1. 栈溢出
2. Cortex-M 上中断优先级配置错误（数值大 = 优先级低，反直觉）
3. 在临界区或调度器挂起时调用 API，或从中断调用了非 `FromISR` 版本的 API
4. 队列/信号量未初始化即使用
5. 嵌套中断场景下 tick 中断优先级高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY`

### `vListInsertEnd` — 尾部插入（轮询调度）

```c
void vListInsertEnd( List_t * const pxList, ListItem_t * const pxNewListItem )
{
    ListItem_t * const pxIndex = pxList->pxIndex;

    listTEST_LIST_INTEGRITY( pxList );
    listTEST_LIST_ITEM_INTEGRITY( pxNewListItem );

    pxNewListItem->pxNext = pxIndex;
    pxNewListItem->pxPrevious = pxIndex->pxPrevious;

    pxIndex->pxPrevious->pxNext = pxNewListItem;
    pxIndex->pxPrevious = pxNewListItem;

    pxNewListItem->pxContainer = pxList;
    ( pxList->uxNumberOfItems )++;
}
```

**不同于 `vListInsert` 的关键点**：

- **不按值排序**。直接插入到 `pxIndex` 之前。
- `pxIndex` 是轮询漫游指针，每次 `listGET_OWNER_OF_NEXT_ENTRY` 调用后推进。
- 插入位置是 `pxIndex` **之前**，即**当前轮询指针刚才跳过的位置之后**。

**使用场景**：
- 当任务被添加到就绪队列时，如果它和其他任务同优先级，使用 `vListInsertEnd` 将其放到轮询队列末尾，而非按值排序（因为值相同）。
- `vListInsertEnd` 实际上是 `vListInsert` 的简化 + 优化版本 —— O(1) 而非 O(n)。

**`vListInsertEnd` vs `vListInsert` 的选择**：

| 场景 | 函数 | 原因 |
|------|------|------|
| 首次加入就绪队列（可能改变优先级） | `vListInsert` | 需要按优先级排序 |
| 从阻塞中唤醒，恢复原优先级就绪队列 | `vListInsertEnd` | 优先级不变，放在同优先级末尾确保公平 |
| 加入延时队列 | `vListInsert` | 需要按唤醒时间排序 |
| 加入事件等待队列 | `vListInsert` | 需要按优先级排序 |

**内联宏版本 `listINSERT_END`**：定义了与 `vListInsertEnd` 完全相同的宏版本，用于 `xTaskIncrementTick()` 等高频调用路径，避免函数调用开销。

### `uxListRemove` — 删除列表项

```c
UBaseType_t uxListRemove( ListItem_t * const pxItemToRemove )
{
    List_t * const pxList = pxItemToRemove->pxContainer;

    pxItemToRemove->pxNext->pxPrevious = pxItemToRemove->pxPrevious;
    pxItemToRemove->pxPrevious->pxNext = pxItemToRemove->pxNext;

    if( pxList->pxIndex == pxItemToRemove )
    {
        pxList->pxIndex = pxItemToRemove->pxPrevious;
    }

    pxItemToRemove->pxContainer = NULL;
    ( pxList->uxNumberOfItems )--;

    return pxList->uxNumberOfItems;
}
```

**逻辑**：

1. `pxContainer` 存储了所属列表指针，因此调用者只需传入列表项本身，不需要列表指针。
2. 标准双链表删除：前后节点互相链接，跳过当前项。
3. **`pxIndex` 修复**：如果被删除的项恰好是 `pxIndex` 当前指向的项，将 `pxIndex` 回退到前一个节点。这保证后续 `listGET_OWNER_OF_NEXT_ENTRY` 不会悬挂。
4. `pxContainer` 置 `NULL` —— 列表项不再属于任何列表。
5. **返回值**：剩余元素数量。调用者（调度器）可用此判断就绪队列是否变空，以决定是否需要进行任务切换。
6. **时间复杂度**：O(1)。

**内联宏版本 `listREMOVE_ITEM`**：功能相同但不返回值，用于 `xTaskIncrementTick()` 中微优化。

### `listGET_OWNER_OF_NEXT_ENTRY` — 轮询迭代宏

```c
#define listGET_OWNER_OF_NEXT_ENTRY( pxTCB, pxList )
    {
        List_t * const pxConstList = ( pxList );
        ( pxConstList )->pxIndex = ( pxConstList )->pxIndex->pxNext;
        if( ( void * ) ( pxConstList )->pxIndex == ( void * ) &( ( pxConstList )->xListEnd ) )
        {
            ( pxConstList )->pxIndex = ( pxConstList )->pxIndex->pxNext;
        }
        ( pxTCB ) = ( pxConstList )->pxIndex->pvOwner;
    }
```

**机制**：

1. 局部变量 `pxConstList` 防止宏参数多次求值。
2. `pxIndex` 步进到下一个元素。
3. **哨兵跳过**：如果步进后正好跳到哨兵 `xListEnd`，则再步进一次（即从哨兵的下一个节点，也就是真正的链表头开始）。
4. 返回当前 `pxIndex->pvOwner`（通常为 TCB 指针）。

**效果**：

- 每次调用返回一个不同的任务，循环遍历所有元素。
- 由于跳过哨兵，遍历自动在链表头尾之间循环 —— 实现了**轮询调度（Round-Robin）**。
- 典型用法：调度器选择下一个要运行的任务时，对就绪队列不断调用此宏。

```
初始（假设就绪队列有 TaskA、TaskB、TaskC）：
  pxIndex → [S] ↔ [A] ↔ [B] ↔ [C] ↔ [S]
第1次调用：pxIndex → [A], 返回 TaskA
第2次调用：pxIndex → [B], 返回 TaskB
第3次调用：pxIndex → [C], 返回 TaskC
第4次调用：pxIndex → [S], 跳过, pxIndex → [A], 返回 TaskA
```

## 设计分析

### 为什么使用循环双链表？

| 操作 | 复杂度 | 原因 |
|------|--------|------|
| 尾部插入（`vListInsertEnd`） | O(1) | 通过 `pxIndex` 直接定位插入点 |
| 按值插入（`vListInsert`） | O(n) | 需要线性遍历找位置。但 n 通常很小。 |
| 删除（`uxListRemove`） | O(1) | 双链表 + 列表项自带 `pxNext`/`pxPrevious` |
| 遍历 | O(n) | 轮询调度 |
| 获取头元素 | O(1) | `xListEnd.pxNext` |

- **循环**消除了边界检查（无需判断 `NULL`），简化了插入和删除的指针操作。
- **双向**使删除操作无需重新遍历找前驱，实现 O(1) 删除。
- **哨兵**统一了空列表和非空列表的处理，消除了大量分支。

### `xItemValue` 的实际用途

| 列表类型 | `xItemValue` | 排序依据 |
|----------|-------------|----------|
| 就绪队列（`ReadyList`） | 任务优先级 | 高优先级在前；同优先级用 `vListInsertEnd` 维护轮询顺序 |
| 延时列表（`DelayedList`） | 任务唤醒 tick 值 | 最早唤醒的任务在表头 |
| 挂起列表（`SuspendedList`） | 任务优先级 | 高优先级在前 |
| 事件等待列表（`EventList`） | 任务优先级 | 高优先级优先获得事件 |

哨兵值 `portMAX_DELAY` 在所有情况下都保证位于排序后的"末尾"。

### MiniListItem 优化

- `xLIST` 结构体中嵌入的是 `MiniListItem_t` 而非 `ListItem_t` 作为哨兵。
- 节省两个指针字段（`pvOwner` + `pxContainer`）= 8 字节（32 位）或 16 字节（64 位）。
- FreeRTOS 内核中有数十个列表（每个优先级一个就绪队列 + 延时列表 + 挂起列表 + 事件列表 × 最大任务数），这个优化累计节省显著。
- 代码中使用显式强制类型转换 `(ListItem_t *)&(pxList->xListEnd)`，利用 C 结构体内存布局兼容性 —— 两个结构体开头字段完全一致，只是 `xLIST_ITEM` 多出末尾的字段。

### 线程安全与临界区

- `list.c` 中的函数**自身不包含任何临界区保护**（无 `taskENTER_CRITICAL()`/`taskEXIT_CRITICAL()`）。
- 所有链表操作必须由**调用者在临界区或调度器挂起状态下**执行。
- 列表字段使用 `configLIST_VOLATILE` 修饰（默认定义为空），用于防止编译器在跨模块优化时误删关键访问。如果需要在 `FreeRTOSConfig.h` 中定义为 `volatile`。
- `uxNumberOfItems` 被声明为 `volatile`，确保中断修改后主循环看到的值是正确的。
- 完整性检查字节（`configUSE_LIST_DATA_INTEGRITY_CHECK_BYTES`）用于**运行时检测内存越界**，但不能预防竞态条件。

### 内联宏优化

`list.h` 中提供了三个关键操作的**内联宏版本**：

| 函数版本 | 宏版本 | 差异 |
|---------|--------|------|
| `uxListRemove` | `listREMOVE_ITEM` | 无返回值（移除返回值赋值语句） |
| `vListInsertEnd` | `listINSERT_END` | 完全相同，避免函数调用开销 |

这些宏用于 `xTaskIncrementTick()` —— tick 中断处理函数中，每次 tick 都会遍历延时队列，性能敏感。

### 内存布局兼容性

`MiniListItem_t` 和 `ListItem_t` 的 `pxNext`、`pxPrevious`、`xItemValue` 排列完全相同。源码中大量 `(ListItem_t *)&(pxList->xListEnd)` 类型转换依赖这一布局兼容性。这是安全的，因为：

- 访问 `MiniListItem_t` 的字段时通过 `ListItem_t *` 指针，只访问两个结构体共有的前三个成员。
- 额外的 `pvOwner` 和 `pxContainer` 字段只在新插入的**真实**列表项上访问。
- 哨兵节点的 `pvOwner` 和 `pxContainer` 永远不会被访问（跳过哨兵的宏逻辑保证了这一点）。
