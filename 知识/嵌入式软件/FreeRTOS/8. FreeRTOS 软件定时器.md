# FreeRTOS 软件定时器 — 实现分析

基于 FreeRTOS Kernel V10.4.6 源码 `timers.c` 和 `include/timers.h` 逐函数精读。

## 数据结构的精妙设计

### xTIMER — 定时器控制块

```c
typedef struct tmrTimerControl {
    const char * pcTimerName;           // 调试用名称
    ListItem_t xTimerListItem;          // 链表节点——定时器本身就是一个列表项
    TickType_t xTimerPeriodInTicks;     // 定时器周期
    void * pvTimerID;                   // 用户自定义 ID（回调中区分定时器）
    TimerCallbackFunction_t pxCallbackFunction; // 到期回调函数
    #if (configUSE_TRACE_FACILITY == 1)
        UBaseType_t uxTimerNumber;      // 跟踪工具（如 FreeRTOS+Trace）使用
    #endif
    uint8_t ucStatus;                   // 状态位
} xTIMER;
```

关键设计：**xTimerListItem 直接嵌入在结构体中**。这意味着定时器结构体本身就是一个 ListNode——通过 `listGET_OWNER_OF_HEAD_ENTRY()` 宏可以从链表项反推出 Timer_t 指针。所有 FreeRTOS 内核对象都用同一套链表基础设施。

#### ucStatus 状态位

| 位掩码 | 宏 | 含义 |
|--------|-----|------|
| `0x01` | `tmrSTATUS_IS_ACTIVE` | 定时器是否在活动列表中 |
| `0x02` | `tmrSTATUS_IS_STATICALLY_ALLOCATED` | 是否静态分配（影响删除时是否 free） |
| `0x04` | `tmrSTATUS_IS_AUTORELOAD` | 是否为周期模式 |

### 命令队列消息类型

所有对定时器的操作都通过消息发送到守护任务。消息体是一个联合体：

```c
typedef struct tmrTimerQueueMessage {
    BaseType_t xMessageID;              // 命令标识符（正数=定时器命令，负数=pended callback）
    union {
        TimerParameter_t xTimerParameters;     // 定时器操作参数
        CallbackParameters_t xCallbackParameters; // pended function call 参数
    } u;
} DaemonTaskMessage_t;
```

```c
typedef struct tmrTimerParameters {
    TickType_t xMessageValue;   // 命令相关值（新周期、启动时的 tick 计数等）
    Timer_t * pxTimer;          // 要操作的定时器
} TimerParameter_t;

typedef struct tmrCallbackParameters {
    PendedFunction_t pxCallbackFunction;
    void * pvParameter1;
    uint32_t ulParameter2;
} CallbackParameters_t;
```

**重点**：`DaemonTaskMessage_t` 是队列元素类型。队列深度 = `configTIMER_QUEUE_LENGTH`。一个消息要么是定时器命令（大部分情况），要么是 pended function call（`xTimerPendFunctionCall` 功能）。

### 全局状态

```c
static List_t xActiveTimerList1;
static List_t xActiveTimerList2;
static List_t * pxCurrentTimerList;    // 指向当前列表
static List_t * pxOverflowTimerList;   // 指向溢出列表
static QueueHandle_t xTimerQueue = NULL;
static TaskHandle_t xTimerTaskHandle = NULL;
```

## 定时器命令协议

### 为什么用命令队列架构？

**所有定时器操作都在守护任务上下文中执行**，而非调用者上下文中。原因：

1. **定时器链表不是线程安全的**——如果多个任务同时 `xTimerStart()`，直接操作链表需要锁
2. **ISR 不能阻塞**——如果 ISR 直接操作链表，可能导致优先级反转或死锁
3. **集中化时间处理**——所有定时器的过期时间判断在同一任务中，逻辑统一
4. **回调在统一上下文执行**——避免了不同任务栈上执行回调的数据一致性问题

代价：调用 `xTimerStart()` 到定时器实际生效之间存在延迟（消息排队等待守护任务处理）。

### 命令类型一览

```c
// 负数 = pended function call（非定时器操作）
#define tmrCOMMAND_EXECUTE_CALLBACK_FROM_ISR    ( ( BaseType_t ) -2 )
#define tmrCOMMAND_EXECUTE_CALLBACK             ( ( BaseType_t ) -1 )

// 正数 = 定时器命令
#define tmrCOMMAND_START_DONT_TRACE             ( ( BaseType_t ) 0 )
#define tmrCOMMAND_START                        ( ( BaseType_t ) 1 )
#define tmrCOMMAND_RESET                        ( ( BaseType_t ) 2 )
#define tmrCOMMAND_STOP                         ( ( BaseType_t ) 3 )
#define tmrCOMMAND_CHANGE_PERIOD                ( ( BaseType_t ) 4 )
#define tmrCOMMAND_DELETE                       ( ( BaseType_t ) 5 )

// ISR 版本从 6 开始
#define tmrFIRST_FROM_ISR_COMMAND               ( ( BaseType_t ) 6 )
#define tmrCOMMAND_START_FROM_ISR               ( ( BaseType_t ) 6 )
#define tmrCOMMAND_RESET_FROM_ISR               ( ( BaseType_t ) 7 )
#define tmrCOMMAND_STOP_FROM_ISR                ( ( BaseType_t ) 8 )
#define tmrCOMMAND_CHANGE_PERIOD_FROM_ISR       ( ( BaseType_t ) 9 )
```

**命令编号的设计意图**：
- 负数（-1, -2）用于 pended function call，在命令处理中走另一分支
- 0~5 是任务上下文使用的命令
- 6~9 是 ISR 上下文使用的命令（值 >= tmrFIRST_FROM_ISR_COMMAND = 6）
- `xTimerGenericCommand` 根据此阈值决定用 `xQueueSendToBack` 还是 `xQueueSendToBackFromISR`

### xTimerGenericCommand — 统一命令分发器

```c
BaseType_t xTimerGenericCommand(
    TimerHandle_t xTimer,
    const BaseType_t xCommandID,
    const TickType_t xOptionalValue,
    BaseType_t * const pxHigherPriorityTaskWoken,
    const TickType_t xTicksToWait )
```

所有公共 API 函数都展开为对这个函数的宏调用：

```c
// 每个宏都捕获当前 tick 计数作为 xOptionalValue
#define xTimerStart(xTimer, xTicksToWait) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_START, \
        (xTaskGetTickCount()), NULL, (xTicksToWait))

#define xTimerStop(xTimer, xTicksToWait) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_STOP, \
        0U, NULL, (xTicksToWait))

#define xTimerReset(xTimer, xTicksToWait) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_RESET, \
        (xTaskGetTickCount()), NULL, (xTicksToWait))

#define xTimerChangePeriod(xTimer, xNewPeriod, xTicksToWait) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_CHANGE_PERIOD, \
        (xNewPeriod), NULL, (xTicksToWait))

#define xTimerDelete(xTimer, xTicksToWait) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_DELETE, \
        0U, NULL, (xTicksToWait))

// ISR 版本——用 xTaskGetTickCountFromISR() 获取时间戳
#define xTimerStartFromISR(xTimer, pxHigherPriorityTaskWoken) \
    xTimerGenericCommand((xTimer), tmrCOMMAND_START_FROM_ISR, \
        (xTaskGetTickCountFromISR()), (pxHigherPriorityTaskWoken), 0U)
```

**关键细节**：`xOptionalValue` 对于 START/RESET 是当前 tick 计数（命令发出时刻的 tick），对于 CHANGE_PERIOD 是新周期值。这个值会在 `prvProcessReceivedCommands` 中被用于计算定时器的下一个到期时间。

`xTimerGenericCommand` 的调度策略：

```c
if (xCommandID < tmrFIRST_FROM_ISR_COMMAND) {
    // 任务上下文：如果调度器未运行，用 0 超时（不阻塞）
    if (xTaskGetSchedulerState() == taskSCHEDULER_RUNNING)
        xReturn = xQueueSendToBack(xTimerQueue, &xMessage, xTicksToWait);
    else
        xReturn = xQueueSendToBack(xTimerQueue, &xMessage, tmrNO_DELAY);
} else {
    // ISR 上下文：只能用 FromISR 版本
    xReturn = xQueueSendToBackFromISR(xTimerQueue, &xMessage, pxHigherPriorityTaskWoken);
}
```

**调度器运行前的特殊处理**：在调度器启动前调用 `xTimerStart()` 等函数时，用 `tmrNO_DELAY`（0）超时入队，不阻塞。此时消息会排队，等调度器启动后守护任务开始处理，定时器才真正生效。

## 守护任务 — prvTimerTask

### 任务创建

```c
BaseType_t xTimerCreateTimerTask(void)
```

在调度器启动时（内部被调用）：
1. 确保队列和链表已初始化（`prvCheckForValidListAndQueue`）
2. 创建守护任务 `prvTimerTask`，优先级 = `configTIMER_TASK_PRIORITY | portPRIVILEGE_BIT`
3. 任务名称可配置：默认 `"Tmr Svc"`，通过 `configTIMER_SERVICE_TASK_NAME` 重载

根据 `configSUPPORT_STATIC_ALLOCATION` 使用 `xTaskCreate` 或 `xTaskCreateStatic`。静态版本需要应用实现 `vApplicationGetTimerTaskMemory()`。

### 任务主循环

```c
static portTASK_FUNCTION(prvTimerTask, pvParameters) {
    // 可选启动钩子
    #if (configUSE_DAEMON_TASK_STARTUP_HOOK == 1)
        vApplicationDaemonTaskStartupHook();
    #endif

    for (;;) {
        // 1. 获取最早到期的定时器时间
        xNextExpireTime = prvGetNextExpireTime(&xListWasEmpty);

        // 2. 如果到期就处理，否则阻塞等待
        prvProcessTimerOrBlockTask(xNextExpireTime, xListWasEmpty);

        // 3. 处理所有排队命令
        prvProcessReceivedCommands();
    }
}
```

**每个循环周期的顺序很关键**：
- 先处理到期的定时器（时间驱动）
- 再处理命令队列中的请求（事件驱动）
- 这意味着：如果定时器到期和命令同时到达，到期先处理

### prvProcessTimerOrBlockTask — 阻塞决策

```c
static void prvProcessTimerOrBlockTask(xNextExpireTime, xListWasEmpty)
```

这个函数实现了精细的阻塞逻辑，其分叉如下：

1. `vTaskSuspendAll()`
2. `xTimeNow = prvSampleTimeNow(&xTimerListsWereSwitched)`
3. 如果 tick 溢出（`xTimerListsWereSwitched == pdTRUE`）：
   - 列表已交换，放弃处理（溢出时列表中的定时器已在 switch 中处理过）
   - `vTaskResumeAll()`
4. 如果 tick 未溢出：
   - **有定时器到期**（`xNextExpireTime <= xTimeNow`）：
     - `vTaskResumeAll()`
     - `prvProcessExpiredTimer()`
   - **没有定时器到期**：
     - 如果当前列表为空，检查溢出列表是否也为空
     - `vQueueWaitForMessageRestricted(xTimerQueue, (xNextExpireTime - xTimeNow), xListWasEmpty)`
       - 超时间隔 = 下一个到期时间 - 当前时间
       - 唤醒条件：有命令到达 OR 超时（下一个定时器到期）

**核心原理**：守护任务并非每个 tick 都唤醒——它精确阻塞到下一个定时器到期时刻，由 tick 中断或命令队列事件唤醒。这实现了 O(1) 的空闲开销。

### vQueueWaitForMessageRestricted

这个 Queue API 函数让任务在队列上阻塞，同时带有超时。超时值为 `xNextExpireTime - xTimeNow`。

- 如果在超时前有命令到达 → 处理命令
- 如果超时 → 回到循环头部，检查是否有定时器到期
- 这是守护任务"自动化"的核心机制

## 定时器链表管理

### 为什么需要两条链表？

32 位 tick 计数器会溢出（`0xFFFFFFFF → 0x00000000`）。如果只有一条链表，溢出后的时间比较会出错。

解决方案是**双链表机制**：

- `pxCurrentTimerList`：当前 tick 范围内的定时器
- `pxOverflowTimerList`：跨越 tick 溢出边界的定时器

### 插入逻辑 — prvInsertTimerInActiveList

```c
static BaseType_t prvInsertTimerInActiveList(
    Timer_t * const pxTimer,
    const TickType_t xNextExpiryTime,    // 期望到期 tick
    const TickType_t xTimeNow,           // 当前 tick
    const TickType_t xCommandTime)       // 命令发出时的 tick
```

这是最精妙的函数之一。它判断将一个定时器插入哪条链表，或是否需要立即触发：

如果 `xNextExpiryTime <= xTimeNow`（到期时间已过）：
- `(xTimeNow - xCommandTime) >= xTimerPeriodInTicks`？
  - **YES**：命令延迟超过一个完整周期 → 需要立即触发（返回 `pdTRUE`）
  - **NO**：只是轻微延迟 → 插入 overflow 列表（当前 tick 空间已满，到期时间在溢出后的 tick 空间中）

如果 `xNextExpiryTime > xTimeNow`（到期时间在未来）：
- `xTimeNow < xCommandTime` 且 `xNextExpiryTime >= xCommandTime`？
  - **YES**：tick 在命令发出后溢出，但到期时间没溢出 → 定时器已经应该触发了 → 立即处理（返回 `pdTRUE`）
  - **NO**：正常情况 → 插入 current 列表

**直观理解**：
- 加入 current 列表：到期时间在未来，且在本次 tick 周期内
- 加入 overflow 列表：到期时间已过，但只是稍早于命令被处理（因排队延迟），或者到期时间在当前 tick 溢出后
- 立即触发：排队延迟超过了一个完整周期，或者 tick 已溢出导致定时器实际已到期

### prvSwitchTimerLists — 溢出切换

```c
static void prvSwitchTimerLists(void)
```

当 `prvSampleTimeNow` 检测到 tick 溢出（`xTimeNow < xLastTime`）时调用：

1. 处理当前列表中所有未处理的定时器（它们都已经到期）
2. 交换 `pxCurrentTimerList` 和 `pxOverflowTimerList` 指针
3. 原来的 overflow 列表变成当前列表，空的当前列表变成 overflow 列表

**为什么切换前要处理完当前列表？** 因为当前列表中的定时器都设定了到期时间 <= 溢出前的最大 tick 值。溢出发生后，这些定时器确实都到齐了。

### prvProcessExpiredTimer — 定时器触发

```c
static void prvProcessExpiredTimer(xNextExpireTime, xTimeNow) {
    // 1. 从链表中取出队首定时器（最近到期的）
    Timer_t *pxTimer = listGET_OWNER_OF_HEAD_ENTRY(pxCurrentTimerList);
    uxListRemove(&(pxTimer->xTimerListItem));

    // 2. 如果是周期模式，重新计算下次到期时间
    if (pxTimer->ucStatus & tmrSTATUS_IS_AUTORELOAD) {
        prvReloadTimer(pxTimer, xNextExpireTime, xTimeNow);
    } else {
        // 单次模式：清除活跃标记
        pxTimer->ucStatus &= ~tmrSTATUS_IS_ACTIVE;
    }

    // 3. 调用回调函数
    pxTimer->pxCallbackFunction((TimerHandle_t)pxTimer);
}
```

### prvReloadTimer — 周期重载与 backlog 处理

```c
static void prvReloadTimer(pxTimer, xExpiredTime, xTimeNow) {
    while (prvInsertTimerInActiveList(
        pxTimer, xExpiredTime + pxTimer->xTimerPeriodInTicks,
        xTimeNow, xExpiredTime) != pdFALSE)
    {
        // 插入返回 pdTRUE = 背靠背到期
        xExpiredTime += pxTimer->xTimerPeriodInTicks;
        pxTimer->pxCallbackFunction((TimerHandle_t)pxTimer); // 补调回调
    }
}
```

**backlog 补偿**：如果定时器任务被更高优先级的任务阻塞了多个周期，这个 `while` 循环会：

1. 尝试插入 `(已过时间 + 周期)` 到列表
2. 如果返回 pdTRUE（再次到期），说明当前 tick 仍然超过了新到期时间
3. 累加到期时间，再执行一次回调
4. 重复直到到期时间真正在未来

这意味着：**一个被阻塞了 N 个周期的 auto-reload 定时器，会在恢复后连续 N 次调用回调**。这对计数器类应用很重要（它们依赖准确的触发次数）。

### prvGetNextExpireTime

```c
static TickType_t prvGetNextExpireTime(pxListWasEmpty) {
    *pxListWasEmpty = listLIST_IS_EMPTY(pxCurrentTimerList);

    if (*pxListWasEmpty == pdFALSE) {
        // 列表非空：返回最早到期时间
        return listGET_ITEM_VALUE_OF_HEAD_ENTRY(pxCurrentTimerList);
    } else {
        // 列表空：返回 0，使任务在 tick 溢出时自动唤醒
        return (TickType_t)0U;
    }
}
```

**空列表返回 0 的设计意图**：当当前列表为空时，定时器任务会阻塞到 tick 计数回绕到 0（即 `xNextExpireTime - xTimeNow` 约等于 32 位 tick 的最大值）。但实际目的并不是等到回绕——而是在 tick 溢出时 `prvSampleTimeNow` 检测到溢出并切换列表，这时 overflow 列表中的定时器可能被移到 current 列表中。所以空列表时阻塞到溢出是为了"等列表切换"。

## 命令处理 — prvProcessReceivedCommands

这是守护任务中处理所有排队的定时器命令的函数。

```c
static void prvProcessReceivedCommands(void) {
    DaemonTaskMessage_t xMessage;

    // 非阻塞地接收所有排队的消息
    while (xQueueReceive(xTimerQueue, &xMessage, tmrNO_DELAY) != pdFAIL) {

        // Step 1: 如果是 pended function call（负命令 ID），直接执行
        if (xMessage.xMessageID < 0) {
            // 调用 xTimerPendFunctionCallFromISR() 排入的函数
            pxCallback->pxCallbackFunction(pvParameter1, ulParameter2);
        }

        // Step 2: 对正命令 ID（定时器操作），先统一从列表中移除
        if (xMessage.xMessageID >= 0) {
            pxTimer = xMessage.u.xTimerParameters.pxTimer;

            // 如果定时器在列表中，先移除（为了重新插入）
            if (listIS_CONTAINED_WITHIN(NULL, &(pxTimer->xTimerListItem)) == pdFALSE) {
                uxListRemove(&(pxTimer->xTimerListItem));
            }

            // 获取当前时间（必须在消息接收之后）
            xTimeNow = prvSampleTimeNow(&xTimerListsWereSwitched);

            // Step 3: 按命令类型处理
            switch (xMessage.xMessageID) {
                case tmrCOMMAND_START:
                case tmrCOMMAND_START_FROM_ISR:
                case tmrCOMMAND_RESET:
                case tmrCOMMAND_RESET_FROM_ISR:
                    // 标记为活跃，插入列表
                    // expiry = xMessageValue + xTimerPeriodInTicks
                    // 如果立即触发（prvInsertTimerInActiveList 返回 TRUE）：
                    //   周期模式 → prvReloadTimer 补偿
                    //   单次模式 → 清除 ACTIVE 位
                    //   执行回调
                    break;

                case tmrCOMMAND_STOP:
                case tmrCOMMAND_STOP_FROM_ISR:
                    // 清除 ACTIVE 位（定时器已被移除）
                    break;

                case tmrCOMMAND_CHANGE_PERIOD:
                case tmrCOMMAND_CHANGE_PERIOD_FROM_ISR:
                    // 更新周期并重新激活
                    pxTimer->xTimerPeriodInTicks = xMessageValue;
                    // expiry = xTimeNow + 新周期（以当前时间为参考）
                    prvInsertTimerInActiveList(pxTimer, xTimeNow + 新周期, xTimeNow, xTimeNow);
                    break;

                case tmrCOMMAND_DELETE:
                    // 如果动态分配则释放内存
                    // 如果静态分配则只清 ACTIVE 位
                    break;
            }
        }
    }
}
```

**关键协议细节**：

对于 START/RESET 命令：
- `xMessageValue` = 命令发出时的 tick 计数（由 `xTaskGetTickCount()` 捕获）
- 到期时间 = `xMessageValue + xTimerPeriodInTicks`
- 传入 `prvInsertTimerInActiveList` 的 `xCommandTime` = `xMessageValue`
- 这使得 `prvInsertTimerInActiveList` 能判断排队延迟是否超过一个周期

对于 CHANGE_PERIOD 命令：
- `xMessageValue` = 新周期值
- 到期时间 = `xTimeNow + 新周期`（以当前时刻为基准）
- `xCommandTime` = `xTimeNow`（当前在处理命令时的时刻）
- 文档注释说"新周期没有参考点，可长可短"——所以用当前时间作为基准

**命令到达时为什么需要先移除定时器**：
- 无论定时器是否在列表中，先 `uxListRemove` 确保它从之前的位置移除
- 然后重新计算到期时间并插入到合适位置
- `listIS_CONTAINED_WITHIN(NULL, ...)` 检查列表项是否在某个列表中——如果返回 pdFALSE，说明在列表中

## 关键函数详解

### xTimerCreate / xTimerCreateStatic

```c
TimerHandle_t xTimerCreate(...) {
    Timer_t *pxNewTimer = pvPortMalloc(sizeof(Timer_t));
    if (pxNewTimer != NULL) {
        pxNewTimer->ucStatus = 0x00;    // 初始为 0（未活跃，未静态分配）
        prvInitialiseNewTimer(...);      // 填充字段
    }
    return pxNewTimer;
}
```

**定时器创建时处于休眠态**——`ucStatus` 的 `tmrSTATUS_IS_ACTIVE` 位未置位。不加入任何链表。除非显式调用 `xTimerStart()`，否则永远不会触发。

`prvInitialiseNewTimer` 内部：
```c
static void prvInitialiseNewTimer(...) {
    configASSERT(xTimerPeriodInTicks > 0);  // 周期必须 > 0
    prvCheckForValidListAndQueue();          // 确保队列和链表已初始化

    pxNewTimer->pcTimerName = pcTimerName;
    pxNewTimer->xTimerPeriodInTicks = xTimerPeriodInTicks;
    pxNewTimer->pvTimerID = pvTimerID;
    pxNewTimer->pxCallbackFunction = pxCallbackFunction;
    vListInitialiseItem(&(pxNewTimer->xTimerListItem));  // 初始化链表项

    if (uxAutoReload != pdFALSE) {
        pxNewTimer->ucStatus |= tmrSTATUS_IS_AUTORELOAD;
    }
}
```

### xTimerStart (宏)

```c
#define xTimerStart(xTimer, xTicksToWait)
    xTimerGenericCommand(xTimer, tmrCOMMAND_START,
        xTaskGetTickCount(), NULL, xTicksToWait)
```

- 向命令队列发送 `tmrCOMMAND_START`
- `xOptionalValue` = 当前 tick 计数（作为命令时间基准）
- 如果定时器已启动，行为等同于 `xTimerReset`（重新设置到期时间）

### xTimerStop (宏)

```c
#define xTimerStop(xTimer, xTicksToWait)
    xTimerGenericCommand(xTimer, tmrCOMMAND_STOP, 0U, NULL, xTicksToWait)
```

- 向命令队列发送 `tmrCOMMAND_STOP`
- `xOptionalValue` = 0（未使用）
- 守护任务处理时清除 `tmrSTATUS_IS_ACTIVE` 位

### xTimerReset (宏)

```c
#define xTimerReset(xTimer, xTicksToWait)
    xTimerGenericCommand(xTimer, tmrCOMMAND_RESET,
        xTaskGetTickCount(), NULL, xTicksToWait)
```

- 与 START 几乎相同，只是命令 ID 不同
- 两者的处理分支在 `prvProcessReceivedCommands` 中合并（`case tmrCOMMAND_START: case tmrCOMMAND_RESET:`）

### xTimerChangePeriod (宏)

```c
#define xTimerChangePeriod(xTimer, xNewPeriod, xTicksToWait)
    xTimerGenericCommand(xTimer, tmrCOMMAND_CHANGE_PERIOD,
        xNewPeriod, NULL, xTicksToWait)
```

- `xOptionalValue` = 新周期值（注意不是 tick 计数）
- 在守护任务中处理时以当前时间为参考点设置为到期时间
- 新周期立即生效，不等待当前周期结束

### ISR 安全版本

```c
#define xTimerStartFromISR(xTimer, pxHigherPriorityTaskWoken)
    xTimerGenericCommand(xTimer, tmrCOMMAND_START_FROM_ISR,
        xTaskGetTickCountFromISR(), pxHigherPriorityTaskWoken, 0U)
```

ISR 版本和任务上下文版本的区别：
1. 命令 ID 不同（≥ tmrFIRST_FROM_ISR_COMMAND）
2. 时间戳使用 `xTaskGetTickCountFromISR()` 而非 `xTaskGetTickCount()`
3. 使用 `xQueueSendToBackFromISR` 入队
4. 可选的 `pxHigherPriorityTaskWoken` 返回值
5. `xTicksToWait` 被忽略（ISR 中不能阻塞）

### xTimerPendFunctionCall / xTimerPendFunctionCallFromISR

这两个函数利用定时器命令队列在守护任务上下文中执行任意函数：

```c
xMessage.xMessageID = tmrCOMMAND_EXECUTE_CALLBACK;
// 或 tmrCOMMAND_EXECUTE_CALLBACK_FROM_ISR
xMessage.u.xCallbackParameters.pxCallbackFunction = xFunctionToPend;
xMessage.u.xCallbackParameters.pvParameter1 = pvParameter1;
xMessage.u.xCallbackParameters.ulParameter2 = ulParameter2;
```

守护任务识别到负命令 ID，直接调用函数。这是一个通用的"延后执行"机制。

## 配置参数

| 宏 | 默认值 | 说明 |
|-----|--------|------|
| `configUSE_TIMERS` | — | 必须设为 1 才能启用软件定时器 |
| `configTIMER_TASK_PRIORITY` | — | 定时器守护任务的优先级，通常设为高优先级 |
| `configTIMER_TASK_STACK_DEPTH` | `configMINIMAL_STACK_SIZE` | 守护任务栈大小 |
| `configTIMER_QUEUE_LENGTH` | — | 命令队列深度 |
| `configTIMER_SERVICE_TASK_NAME` | `"Tmr Svc"` | 守护任务名称（调试用） |

**守护任务优先级的含义**：如果设为高优先级，定时器回调能及时执行，但代价是可能大量抢占其他任务。`configTIMER_TASK_PRIORITY` 通常设为 `configMAX_PRIORITIES - 1`（最高），确保定时器响应及时，但也要考虑回调不能执行太久。

## 关键设计点

### 回调在守护任务上下文中执行

**这是最重要的设计决策**，其影响：

| 限制 | 原因 |
|------|------|
| 回调必须尽快返回 | 阻塞会延迟所有其他定时器 |
| 不能在回调中调用阻塞 API 且 timeout > 0 | 会导致命令队列满时死锁 |
| 回调中操作同样定时器必须用 timeout=0 | 同上 |
| 回调中触发其他定时器是安全的 | 通过命令队列，不会递归 |
| 回调执行期间没有其他定时器能到期 | 都在同一个循环中串行处理 |

**为什么不能在回调中等待**：
```
死锁场景：
1. 回调 A 调用 xTimerStop(timerB, 100)
2. xTimerStop 试图入队 tmrCOMMAND_STOP
3. 命令队列满
4. 回调 A 阻塞 100 tick 等待队列空间
5. 但守护任务本身被阻塞（回调 A 就是守护任务）
6. 没有人处理队列 → 死锁
```

这就是官方文档反复强调"从回调中调用定时器 API 必须用 timeout=0"的原因。

### Tick 溢出处理

32 位 tick 计数器最大约 49.7 天（以 1000Hz tick 频率计算）。FreeRTOS 必须正确处理溢出。

检测机制（`prvSampleTimeNow`）：
```c
static TickType_t prvSampleTimeNow(pxTimerListsWereSwitched) {
    static TickType_t xLastTime = 0;

    xTimeNow = xTaskGetTickCount();

    if (xTimeNow < xLastTime) {
        prvSwitchTimerLists();      // 溢出 → 切换列表
        *pxTimerListsWereSwitched = pdTRUE;
    }
    // ...

    xLastTime = xTimeNow;
    return xTimeNow;
}
```

溢出检测通过**观察 tick 是否递减**来判断——因为正常情况下 tick 只递增。当 `xTimeNow < xLastTime` 时，说明 tick 计数从 `0xFFFFFFFF` 回到了 `0x00000000`。

**为什么这能正常工作**：假设 `xLastTime = 0xFFFFFFF0`，`xTimeNow = 0x00000010`（溢出了 32 个 tick）。通过无符号整数比较，`0x00000010 < 0xFFFFFFF0` 为真（因为无符号整数没有负数）。但如果两次采样之间的间隔使得 tick 两次溢出（从 0xFFFFFFF0 到 0xFFFFFFF0+20 → 0x00000014，中间隔了两次溢出），这无法检测——但在 1000Hz 下两次溢出需要约 100 天，在实际系统中不可能发生。

### 定时器按到期时间排序

```c
listSET_LIST_ITEM_VALUE(&(pxTimer->xTimerListItem), xNextExpiryTime);
vListInsert(pxCurrentTimerList, &(pxTimer->xTimerListItem));
```

定时器链表按 `xItemValue`（= 到期 tick）升序排列。`vListInsert` 在 FreeRTOS 链表实现中是插入排序——找到合适位置插入。最早到期的定时器在链表头部。

### prvCheckForValidListAndQueue — 惰性初始化

```c
static void prvCheckForValidListAndQueue(void) {
    taskENTER_CRITICAL();
    if (xTimerQueue == NULL) {
        // 第一次调用时初始化所有全局状态
        vListInitialise(&xActiveTimerList1);
        vListInitialise(&xActiveTimerList2);
        pxCurrentTimerList = &xActiveTimerList1;
        pxOverflowTimerList = &xActiveTimerList2;

        // 创建队列（静态或动态分配）
        xTimerQueue = xQueueCreate(configTIMER_QUEUE_LENGTH,
            sizeof(DaemonTaskMessage_t));
    }
    taskEXIT_CRITICAL();
}
```

这个函数在每次 `xTimerCreate` 和 `xTimerCreateTimerTask` 时被调用。使用临界区保护，确保只初始化一次。队列的元素大小 = `sizeof(DaemonTaskMessage_t)`。

## 函数调用关系总结

1. **应用代码**：
   - `xTimerCreate()` → `prvInitialiseNewTimer()` → `prvCheckForValidListAndQueue()`
   - `xTimerStart(xTimer, 0)` [宏] → `xTimerGenericCommand(...)` → `xQueueSendToBack(xTimerQueue, message, 0)`
   - **调度器启动** → `xTimerCreateTimerTask()` → `prvCheckForValidListAndQueue()` + `xTaskCreate(prvTimerTask, ...)`
     - `prvTimerTask()` [循环]：
       - `prvGetNextExpireTime()` — 读取最早到期时间
       - `prvProcessTimerOrBlockTask()` — 处理到期或阻塞
         - `prvSampleTimeNow()` — 采样当前 tick
           - `prvSwitchTimerLists()` — 溢出切换
         - `prvProcessExpiredTimer()` — 处理到期的定时器
           - `uxListRemove()`
           - `prvReloadTimer()` + `pxCallbackFunction()` [周期]
           - `pxCallbackFunction()` [单次]
       - `prvProcessReceivedCommands()` — 处理命令队列
         - `xQueueReceive(xTimerQueue)` — 接收消息
         - `uxListRemove()`
         - `prvSampleTimeNow()`
         - 按命令类型：插入/停止/改周期/删除
