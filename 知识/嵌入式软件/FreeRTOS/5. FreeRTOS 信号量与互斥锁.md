# FreeRTOS 信号量与互斥锁 -- 源码级分析

## 核心设计思想：一切皆是队列

FreeRTOS 的信号量和互斥锁**不是独立的内核对象**。`semphr.h` 中的每一个宏都直接映射到 `queue.c` 中的队列函数：

```c
// semphr.h —— 全部是宏，没有自己的实现
typedef QueueHandle_t SemaphoreHandle_t;

#define xSemaphoreCreateBinary()    xQueueGenericCreate(1, 0, queueQUEUE_TYPE_BINARY_SEMAPHORE)
#define xSemaphoreGive(x)           xQueueGenericSend((QueueHandle_t)(x), NULL, 0, queueSEND_TO_BACK)
#define xSemaphoreTake(x, t)        xQueueSemaphoreTake((x), (t))
#define xSemaphoreCreateMutex()     xQueueCreateMutex(queueQUEUE_TYPE_MUTEX)
```

`QueueHandle_t` 与 `SemaphoreHandle_t` 是同一类型，互转只是指针类型的重命名。一切状态都存储在 `Queue_t` 结构体中。

---

## 数据结构：Queue_t 的复用艺术

`queue.c` 第 100-137 行定义了 `Queue_t`（即 `xQUEUE`），其核心是一个**联合体**，根据类型不同，同一块内存有不同的解读方式：

```c
typedef struct QueueDefinition {
    int8_t * pcHead;           // 队列：指向存储区首地址；互斥锁：NULL = 互斥锁
    int8_t * pcWriteTo;        // 指向存储区中下一个写入位置

    union {
        QueuePointers_t xQueue;     // 用于普通队列
        SemaphoreData_t xSemaphore; // 用于信号量/互斥锁
    } u;

    List_t xTasksWaitingToSend;     // 等待"给"信号量的任务列表
    List_t xTasksWaitingToReceive;  // 等待"取"信号量的任务列表

    volatile UBaseType_t uxMessagesWaiting; // 队列：消息数；信号量：计数值
    UBaseType_t uxLength;                   // 最大容量
    UBaseType_t uxItemSize;                 // 信号量始终为 0

    volatile int8_t cRxLock, cTxLock;       // 中断锁定计数
    uint8_t ucQueueType;                    // 仅在 configUSE_TRACE_FACILITY 时存在
} xQUEUE;
```

### 联合体：QueuePointers_t vs SemaphoreData_t

```c
// 队列模式——管理环形缓冲区的读写指针
typedef struct QueuePointers {
    int8_t * pcTail;        // 存储区末尾
    int8_t * pcReadFrom;    // 上一次读取位置
} QueuePointers_t;

// 信号量/互斥锁模式——管理所有权和递归计数
typedef struct SemaphoreData {
    TaskHandle_t xMutexHolder;        // 互斥锁持有者（NULL = 未持有）
    UBaseType_t uxRecursiveCallCount; // 递归互斥锁的重入计数
} SemaphoreData_t;
```

**关键差异**：
- 普通队列需要 `pcTail` 和 `pcReadFrom` 实现环形缓冲区，`uxItemSize > 0`。
- 信号量不需要数据存储，`uxItemSize = 0`，联合体使用 `xSemaphore` 来记录互斥锁持有者和递归计数。
- 当作为普通队列时，`uxMessagesWaiting` 是队列中的消息数；当作为信号量时，它就是**信号量的当前计数值**。

### pcHead 的双重含义

```c
#define uxQueueType   pcHead          // pcHead 的别名
#define queueQUEUE_IS_MUTEX  NULL     // NULL 就是"我是互斥锁"的标记
```

- **普通队列/信号量**：`pcHead` 指向存储区起始地址。当 `uxItemSize == 0` 时（信号量），没有分配存储区，`pcHead` 被设为指向队列结构体自身（一个已知的内存地址，作为无害占位值——见 `prvInitialiseNewQueue`）。
- **互斥锁**：`prvInitialiseMutex` 将 `pcHead` 设置为 `NULL`（即 `queueQUEUE_IS_MUTEX`）。此后，任何代码检查 `pxQueue->uxQueueType == queueQUEUE_IS_MUTEX` 就是在检测 `pcHead == NULL`。

### ucQueueType 枚举值

```c
#define queueQUEUE_TYPE_BASE              0  // 普通队列
#define queueQUEUE_TYPE_MUTEX             1  // 互斥锁
#define queueQUEUE_TYPE_COUNTING_SEMAPHORE 2 // 计数信号量
#define queueQUEUE_TYPE_BINARY_SEMAPHORE  3  // 二值信号量
#define queueQUEUE_TYPE_RECURSIVE_MUTEX   4  // 递归互斥锁
```

`ucQueueType` 仅在 `configUSE_TRACE_FACILITY == 1` 时存储于结构体中，用于调试器识别。内核内部区分互斥锁与其他类型的方式是检查 `pcHead == NULL`（`queueQUEUE_IS_MUTEX`），而不是检查 `ucQueueType`。

## 二值信号量

### 创建

```c
#define xSemaphoreCreateBinary() \
    xQueueGenericCreate(1, 0, queueQUEUE_TYPE_BINARY_SEMAPHORE)
```

- `uxQueueLength = 1`：计数值只能在 0 和 1 之间。
- `uxItemSize = 0`：不分配数据存储区。
- 初始 `uxMessagesWaiting = 0`（由 `xQueueGenericReset` 设置）——即信号量初始为"空"（不可用），必须先 `give` 才能 `take`。

**废弃的 `vSemaphoreCreateBinary`** 宏在创建后立刻调用 `xSemaphoreGive`，使初始计数值为 1。

### Give（从任务上下文）

```c
#define xSemaphoreGive(xSemaphore) \
    xQueueGenericSend((QueueHandle_t)(xSemaphore), NULL, 0, queueSEND_TO_BACK)
```

调用 `xQueueGenericSend`，`pvItemToQueue = NULL`。进入 `xQueueGenericSend` 后：
1. 检查 `uxMessagesWaiting < uxLength`（即计数值 < 1，有空间）。
2. 调用 `prvCopyDataToQueue`。

`prvCopyDataToQueue` 中，当 `uxItemSize == 0`（信号量路径）时：
- 如果是互斥锁类型，执行优先级降级逻辑。
- 非互斥锁的信号量：只执行 `pxQueue->uxMessagesWaiting = uxMessagesWaiting + 1`。

**也就是说，"给信号量"本质上就是让 `uxMessagesWaiting` 计数+1。** 没有数据拷贝，没有环形缓冲区操作。

### Give（从 ISR 上下文）

```c
#define xSemaphoreGiveFromISR(xSemaphore, pxHigherPriorityTaskWoken) \
    xQueueGiveFromISR((QueueHandle_t)(xSemaphore), (pxHigherPriorityTaskWoken))
```

`xQueueGiveFromISR` 是专门的优化路径，与 `xQueueGenericSendFromISR` 不同：
- 它不调用 `prvCopyDataToQueue`，直接执行 `pxQueue->uxMessagesWaiting++`。
- 注释明确说明："ISR 版本不需要处理优先级降级，因为互斥锁不能从 ISR 释放"。
- 包含断言 `configASSERT(!(pxQueue->uxQueueType == queueQUEUE_IS_MUTEX && pxQueue->u.xSemaphore.xMutexHolder != NULL))`。

为什么不直接用 `xQueueGenericSendFromISR(x, NULL, woken, SEND_TO_BACK)`？因为 `xQueueGenericSendFromISR` 会调用 `prvCopyDataToQueue`，而该函数在互斥锁路径下会调用 `xTaskPriorityDisinherit`，这涉及调度器就绪列表操作，在 ISR 中不安全。`xQueueGiveFromISR` 直接操作计数，避免了这个风险。

### Take

```c
#define xSemaphoreTake(xSemaphore, xBlockTime) \
    xQueueSemaphoreTake((xSemaphore), (xBlockTime))
```

`xQueueSemaphoreTake` 与 `xQueueReceive` 有本质区别：

| 方面 | xQueueReceive | xQueueSemaphoreTake |
|------|---------------|---------------------|
| 数据拷贝 | 调用 `prvCopyDataFromQueue` 拷贝数据 | **不拷贝数据**——只有计数-1 |
| 阻塞等待 | 等待消息到达 | 等待计数 > 0 |
| 互斥锁特殊处理 | 无 | 设置 `xMutexHolder`，触发优先级继承 |
| 超时后处理 | 简单返回 | 超时后可能需要撤销优先级继承 |

`xQueueSemaphoreTake` 的核心流程：
1. 检查 `uxMessagesWaiting > 0`：如果是，计数减 1；如果类型是互斥锁，调用 `pvTaskIncrementMutexHeldCount()` 记录持有者。
2. 如果计数为 0 且 `xTicksToWait > 0`：若为互斥锁，调用 `xTaskPriorityInherit(mutexHolder)` 提升持有者优先级，然后将自己挂到 `xTasksWaitingToReceive` 列表。
3. 超时后：如果发生了优先级继承，调用 `prvGetDisinheritPriorityAfterTimeout` + `vTaskPriorityDisinheritAfterTimeout` 撤销继承。

## 计数信号量

### 创建

```c
#define xSemaphoreCreateCounting(uxMaxCount, uxInitialCount) \
    xQueueCreateCountingSemaphore((uxMaxCount), (uxInitialCount))
```

```c
QueueHandle_t xQueueCreateCountingSemaphore(uxMaxCount, uxInitialCount) {
    xHandle = xQueueGenericCreate(uxMaxCount, 0, queueQUEUE_TYPE_COUNTING_SEMAPHORE);
    if (xHandle != NULL) {
        ((Queue_t *)xHandle)->uxMessagesWaiting = uxInitialCount;  // 直接设置初始计数
    }
    return xHandle;
}
```

- `uxLength = uxMaxCount`：计数可以从 0 到 `uxMaxCount`。
- 初始 `uxMessagesWaiting = uxInitialCount`，而不是像二值信号量那样从 0 开始。
- **不调用 `xQueueGenericSend` 来初始化**，而是直接写 `uxMessagesWaiting` 字段，避免不必要的任务唤醒逻辑。

Give 和 Take 的函数路径完全与二值信号量相同（`xQueueGenericSend` / `xQueueSemaphoreTake`），区别仅在于 `uxLength` 的值。

## 互斥锁（Mutual Exclusion）

### 创建

```c
QueueHandle_t xQueueCreateMutex(uint8_t ucQueueType) {
    xNewQueue = xQueueGenericCreate(1, 0, ucQueueType);  // uxLength=1, uxItemSize=0
    prvInitialiseMutex((Queue_t *)xNewQueue);
    return xNewQueue;
}
```

```c
static void prvInitialiseMutex(Queue_t *pxNewQueue) {
    pxNewQueue->u.xSemaphore.xMutexHolder = NULL;          // 初始无持有者
    pxNewQueue->uxQueueType = queueQUEUE_IS_MUTEX;         // pcHead = NULL
    pxNewQueue->u.xSemaphore.uxRecursiveCallCount = 0;     // 递归计数清零
    (void)xQueueGenericSend(pxNewQueue, NULL, 0, queueSEND_TO_BACK);  // 计数值设为 1
}
```

初始化过程的三个关键动作：
1. `pcHead = NULL`（`queueQUEUE_IS_MUTEX`）——这是内核判断互斥锁的**唯一依据**。
2. `xMutexHolder = NULL`——初始未被持有。
3. 调用 `xQueueGenericSend` 将 `uxMessagesWaiting` 设为 1，表示互斥锁可用。

### 持有者追踪：xMutexHolder

当 `xQueueSemaphoreTake` 成功获取互斥锁时（`uxQueueType == queueQUEUE_IS_MUTEX`）：

```c
pxQueue->u.xSemaphore.xMutexHolder = pvTaskIncrementMutexHeldCount();
```

`pvTaskIncrementMutexHeldCount`（tasks.c 第 4687 行）将当前任务的 `uxMutexesHeld` 计数加 1，并返回当前任务句柄。这意味着：

- **只有持有者才能释放互斥锁**：`prvCopyDataToQueue` 在释放互斥锁时清除 `xMutexHolder`。
- **`xTaskPriorityDisinherit` 检查 `uxMutexesHeld`**：只有所有互斥锁都释放后才降级优先级。

### 优先级继承（Priority Inheritance）

这是互斥锁与二值信号量的**根本区别**。当高优先级任务 H 试图获取一个被低优先级任务 L 持有的互斥锁时：

**步骤 1：提升持有者优先级**（`xQueueSemaphoreTake` 第 1635 行）

```c
if (pxQueue->uxQueueType == queueQUEUE_IS_MUTEX) {
    xInheritanceOccurred = xTaskPriorityInherit(pxQueue->u.xSemaphore.xMutexHolder);
}
```

**`xTaskPriorityInherit`（tasks.c 第 4074 行）的逻辑**：

```c
if (pxMutexHolderTCB->uxPriority < pxCurrentTCB->uxPriority) {
    // 持有者优先级低于当前任务 → 提升到当前任务的优先级
    pxMutexHolderTCB->uxPriority = pxCurrentTCB->uxPriority;
    // 如果持有者在就绪列表中，将其移到新的优先级就绪列表
    prvAddTaskToReadyList(pxMutexHolderTCB);
}
```

**步骤 2：释放时降级**（`prvCopyDataToQueue` 第 2171-2180 行）

```c
if (pxQueue->uxItemSize == 0) {        // 信号量路径
    if (pxQueue->uxQueueType == queueQUEUE_IS_MUTEX) {
        xReturn = xTaskPriorityDisinherit(pxQueue->u.xSemaphore.xMutexHolder);
        pxQueue->u.xSemaphore.xMutexHolder = NULL;    // 清除持有者
    }
}
```

**`xTaskPriorityDisinherit`（tasks.c 第 4164 行）的逻辑**：

```c
(pxTCB->uxMutexesHeld)--;        // 持有的互斥锁计数减 1
if (pxTCB->uxPriority != pxTCB->uxBasePriority) {
    if (pxTCB->uxMutexesHeld == 0) {   // 仅当不再持有任何互斥锁时才降级
        pxTCB->uxPriority = pxTCB->uxBasePriority;  // 恢复基础优先级
        prvAddTaskToReadyList(pxTCB);
        xReturn = pdTRUE;   // 请求上下文切换
    }
}
```

**关键边界条件：多互斥锁持有**

如果一个任务连续获取了多个互斥锁（互斥锁 A、B、C），释放时顺序可能与获取时不同。内核的处理策略是：

- `xTaskPriorityDisinherit` 检查 `uxMutexesHeld`：只有当所有互斥锁都释放（`uxMutexesHeld == 0`）时才降级。
- 但如果释放顺序与获取顺序不同：第一个释放可能触发 `pdTRUE`（请求切换），但此时优先级并未实际降低。`xQueueGenericSend` 中针对这种情况有特殊处理（第 884-892 行）：
  ```c
  } else if (xYieldRequired != pdFALSE) {
      // 特殊路径：多个互斥锁以不同顺序释放时触发
      queueYIELD_IF_USING_PREEMPTION();
  }
  ```

**步骤 3：超时后的优先级撤销**

这是最复杂的边界情况。当一个任务因等待互斥锁而导致持有者被提升优先级，但等待者**超时**了，持有者的优先级需要被撤销——但只能降到"其他等待此互斥锁的任务中最高优先级"。

```c
// xQueueSemaphoreTake 第 1683-1698 行（超时路径）
if (xInheritanceOccurred != pdFALSE) {
    uxHighestWaitingPriority = prvGetDisinheritPriorityAfterTimeout(pxQueue);
    vTaskPriorityDisinheritAfterTimeout(pxQueue->u.xSemaphore.xMutexHolder,
                                        uxHighestWaitingPriority);
}
```

**`prvGetDisinheritPriorityAfterTimeout`（queue.c 第 2135 行）**：

```c
if (listCURRENT_LIST_LENGTH(&(pxQueue->xTasksWaitingToReceive)) > 0) {
    // 从等待接收列表中获取最高优先级任务的优先级
    uxHighestWaitingPriority = configMAX_PRIORITIES -
        listGET_ITEM_VALUE_OF_HEAD_ENTRY(&(pxQueue->xTasksWaitingToReceive));
} else {
    uxHighestWaitingPriority = tskIDLE_PRIORITY;  // 没有其他等待者 → 空闲优先级
}
```

**`vTaskPriorityDisinheritAfterTimeout`（tasks.c 第 4244 行）**：

```c

uxPriorityToUse = max(pxTCB->uxBasePriority, uxHighestPriorityWaitingTask);

// 仅当只持有一个互斥锁时才降级
if (pxTCB->uxMutexesHeld == 1) {
    pxTCB->uxPriority = uxPriorityToUse;
    // 如果持有者在就绪列表中，移到新的优先级就绪列表
    prvAddTaskToReadyList(pxTCB);
}
```

## 递归互斥锁

递归互斥锁允许同一任务多次获取同一把锁，适用于函数递归调用或嵌套访问的场景。

### 数据结构

```c
typedef struct SemaphoreData {
    TaskHandle_t xMutexHolder;
    UBaseType_t uxRecursiveCallCount;   // 重入计数
} SemaphoreData_t;
```

`uxRecursiveCallCount` 跟踪当前持有者已经"取"了多少次。

### TakeRecursive

```c
BaseType_t xQueueTakeMutexRecursive(xMutex, xTicksToWait) {
    if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) {
        // 已经是持有者 → 直接增加递归计数，立即返回
        (pxMutex->u.xSemaphore.uxRecursiveCallCount)++;
        return pdPASS;
    } else {
        // 不是持有者 → 通过 xQueueSemaphoreTake 正常获取
        xReturn = xQueueSemaphoreTake(pxMutex, xTicksToWait);
        if (xReturn != pdFAIL) {
            (pxMutex->u.xSemaphore.uxRecursiveCallCount)++;
        }
        return xReturn;
    }
}
```

**注意**：如果当前任务已经是持有者，`xQueueTakeMutexRecursive` **不阻塞直接返回**，即使 `xTicksToWait` 非零。

### GiveRecursive

```c
BaseType_t xQueueGiveMutexRecursive(xMutex) {
    if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) {
        (pxMutex->u.xSemaphore.uxRecursiveCallCount)--;
        if (pxMutex->u.xSemaphore.uxRecursiveCallCount == 0) {
            // 递归计数归零 → 真正释放互斥锁
            (void)xQueueGenericSend(pxMutex, NULL, 0, queueSEND_TO_BACK);
        }
        return pdPASS;
    }
    return pdFAIL;  // 非持有者尝试释放 → 失败
}
```

只有当递归计数归零时，才调用 `xQueueGenericSend` 将计数值设回 1，并触发优先级降级。

### 所有权严格检查

```c
// TakeRecursive：非持有者不能仅通过递归计数拿到锁
if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) { ... }

// GiveRecursive：非持有者返回 pdFAIL
if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) { ... }
```

注释明确说明这些检查不需要临界区保护——因为 `xMutexHolder` 只被持有者修改，而只有持有者才能写入，所以不存在竞态。

## 关键设计要点

### 1. `pcHead = NULL` 作为互斥锁标记

```c
#define uxQueueType    pcHead
#define queueQUEUE_IS_MUTEX  NULL
```

这是一个精妙的内存复用技巧。普通队列的 `pcHead` 指向数据存储区起始地址；对于信号量（`uxItemSize == 0`），由于没有数据存储区，`pcHead` 被设为指向结构体自身（一个无害值）。而互斥锁进一步将其设为 `NULL`，使得**检查 `pcHead == NULL` 即可判断是否为互斥锁**，无需额外的标志位。

这意味着互斥锁本质上是一个"被特别标记的信号量"，标记就藏在 `pcHead` 字段中。

### 2. `uxMessagesWaiting` 的双重语义

这是 FreeRTOS 统一队列和信号量模型的关键：

- 作为队列：`uxMessagesWaiting` = 队列中当前消息数。
- 作为信号量：`uxMessagesWaiting` = 信号量的当前计数值。

计数信号量创建时直接写 `uxMessagesWaiting = uxInitialCount`，跳过了队列的发送路径。`uxSemaphoreGetCount` 宏直接就是：

```c
#define uxSemaphoreGetCount(xSemaphore)  uxQueueMessagesWaiting((QueueHandle_t)(xSemaphore))
```

### 3. 为什么信号量没有优先级继承

二值信号量和计数信号量**没有"所有者"概念**。任何任务（甚至 ISR）都可以 give 一个信号量，内核不追踪"谁最后 take 了它"。没有所有者，就无从谈起"提升谁的优先级"。

互斥锁严格要求：**谁 take 的，谁 give**。内核在 take 时记录 `xMutexHolder = currentTask`，give 时清除它。有了确定的持有者，优先级继承才有操作对象。

### 4. 优先级继承的三层防御

| 场景 | 机制 | 代码位置 |
|------|------|---------|
| 正常阻塞 → 持有者被提升 | `xTaskPriorityInherit` | `xQueueSemaphoreTake` 第 1635 行 |
| 正常释放 → 持有者降级 | `xTaskPriorityDisinherit` | `prvCopyDataToQueue` 第 2178 行 |
| 等待者超时 → 持有者适当降级 | `prvGetDisinheritPriorityAfterTimeout` + `vTaskPriorityDisinheritAfterTimeout` | `xQueueSemaphoreTake` 第 1689-1696 行 |

第三层**必须在超时路径中单独处理**，因为此时等待者已经超时退出，不会通过 `prvCopyDataToQueue` 触发降级。如果不处理，持有者将永久以继承的高优先级运行——这就是优先级继承与超时机制的竞态。

### 5. 多互斥锁持有的复杂度

当任务持有多个互斥锁时，优先级降级决策变得复杂：

- 如果任务持有锁 A（有高优先级任务等待）和锁 B（没有等待者），释放锁 B 时**不应该降级**，因为锁 A 还需要高优先级。
- 解决方案：`uxMutexesHeld` 计数。只有当计数归零时才完全降级到基础优先级。
- 但 `xTaskPriorityDisinheritAfterTimeout` 更进一步：即使不归零，也将优先级降到"其他等待此锁的任务的最高优先级"。这是超时场景下的安全措施。

### 6. 为什么互斥锁不能用于 ISR

有三个层面的原因：
1. **ISR 不阻塞**：互斥锁的优先级继承假设等待者会阻塞，ISR 不能阻塞。
2. **`xQueueGiveFromISR` 不处理优先级降级**：该函数直接操作计数，跳过了 `prvCopyDataToQueue` 中的 `xTaskPriorityDisinherit` 调用路径。
3. **断言保护**：`xQueueGiveFromISR` 包含 `configASSERT(!(uxQueueType == queueQUEUE_IS_MUTEX && xMutexHolder != NULL))`，如果在 ISR 中 give 一个被持有的互斥锁，断言会触发。

### 7. xQueueGiveFromISR 的优化

这是专门为信号量优化的 ISR 路径，与 `xQueueGenericSendFromISR` 的区别：

```c
// xQueueGiveFromISR —— 轻量版
pxQueue->uxMessagesWaiting = uxMessagesWaiting + 1;  // 直接计数+1

// xQueueGenericSendFromISR —— 完整版
(void)prvCopyDataToQueue(pxQueue, pvItemToQueue, xCopyPosition);  // 走完整拷贝路径
```

`prvCopyDataToQueue` 在互斥锁路径下会调用 `xTaskPriorityDisinherit`，该函数操作任务的就绪列表——这在 ISR 上下文中不安全。`xQueueGiveFromISR` 跳过了这一层，仅做原子计数递增。

### 8. Take 与 Receive 的差异

`xQueueSemaphoreTake` 和 `xQueueReceive` 虽然都是"从队列取数据"，但有根本差异：

| 方面 | xQueueReceive | xQueueSemaphoreTake |
|------|---------------|---------------------|
| 数据拷贝 | `prvCopyDataFromQueue`（环形缓冲读取） | 无拷贝 |
| 计数调整 | 读取后计数-1 | 直接 `uxMessagesWaiting--` |
| 互斥锁处理 | 无 | 设置 `xMutexHolder`、优先级继承 |
| 可用性 | 任意队列 | 仅 `uxItemSize == 0` 的对象 |

## 源码路径总结图

```c
// Binary semaphore creation
xSemaphoreCreateBinary()
    -> xQueueGenericCreate(1, 0, BINARY_SEMAPHORE)   // uxMessagesWaiting = 0

// Counting semaphore creation
xSemaphoreCreateCounting(n, i)
    -> xQueueGenericCreate(n, 0, COUNTING_SEMAPHORE)
        -> uxMessagesWaiting = i                      // 直接设初始值

// Mutex creation
xSemaphoreCreateMutex()
    -> xQueueCreateMutex(MUTEX)
        -> xQueueGenericCreate(1, 0, MUTEX)
            -> prvInitialiseMutex()                   // pcHead=NULL, xMutexHolder=NULL
                -> xQueueGenericSend()                // uxMessagesWaiting = 1

// Give
xSemaphoreGive(x)
    -> xQueueGenericSend(x, NULL, 0, BACK)
        -> prvCopyDataToQueue()
            -> uxMessagesWaiting++
            -> [if mutex] xTaskPriorityDisinherit()

// Take
xSemaphoreTake(x, t)
    -> xQueueSemaphoreTake(x, t)
        -> uxMessagesWaiting--                        // 获取成功
        -> [if mutex] xMutexHolder = currentTask
        -> [if mutex & block] xTaskPriorityInherit()
        -> [if mutex & timeout] prvGetDisinheritPriorityAfterTimeout()
                                vTaskPriorityDisinheritAfterTimeout()

// Give from ISR
xSemaphoreGiveFromISR(x, woken)
    -> xQueueGiveFromISR(x, woken)                   // 不走 prvCopyDataToQueue
        -> uxMessagesWaiting++                        // 直接计数+1
        -> [assert] 不是被持有的互斥锁
```
