# FreeRTOS 概述与架构

## 一句话

> 任务承载业务，调度器分配 CPU，内核对象管理任务之间的数据、事件和资源，移植层连接具体处理器，内存管理为所有对象提供空间。

## 内核组件全景

FreeRTOS 内核由四层架构构成：**独立子系统**（上层应用接口）、**内核对象层**（队列及其派生原语）、**核心引擎**（任务管理与队列基座）、**基础设施**（链表、内存、移植层）。所有子系统都建立在统一的**环形双链表**数据结构之上。

## 源码架构洞察

以下是从源码分析中提炼的核心设计架构，理解这些就能从"使用者"升级为"理解者"。

### 链表：一切调度的基础

FreeRTOS 内核中**几乎所有数据都挂在链表上**：

- 每个 TCB 内嵌两个 `ListItem_t`：`xStateListItem`（状态链表）和 `xEventListItem`（事件链表）
- `pxReadyTasksLists[configMAX_PRIORITIES]` — 就绪队列数组，每个优先级一个链表
- `xDelayedTaskList[2]` — 双缓冲延时链表，处理 tick 计数器溢出
- `xSuspendedTaskList` — 挂起任务链表
- `xPendingReadyList` — 调度器挂起期间就绪的任务暂存
- `xTasksWaitingTermination` — 待删除任务（由空闲任务回收）
- 每个队列/信号量持有两个事件列表：`xTasksWaitingToSend` 和 `xTasksWaitingToReceive`

链表设计要点：

- **带哨兵的循环双链表**：哨兵 `xListEnd` 嵌入 `List_t` 结构体内部，消除了对 NULL 的边界检查
- **`pvOwner` 反向链路**：从列表项可直接获取所属 TCB 指针，实现从链表到对象的路由
- **`pxIndex` 漫游指针**：`listGET_OWNER_OF_NEXT_ENTRY()` 的轮询推进实现了同优先级的时间片轮转
- **`MiniListItem_t` 优化**：哨兵节点使用精简版本（去掉了 `pvOwner` 和 `pxContainer`），每个列表节省 8 字节（32 位）

> 详细实现见 [2. FreeRTOS 链表实现](2.%20FreeRTOS%20%E9%93%BE%E8%A1%A8%E5%AE%9E%E7%8E%B0.md) — 包括 `vListInsert`（O(n) 按值排序）、`vListInsertEnd`（O(1) 尾部插入）、`uxListRemove`（O(1) 删除，依赖 `pxContainer` 自反指针）的完整源码分析。

### 调度器的就绪列表选择算法

FreeRTOS 支持两种就绪列表查找算法，由 `configUSE_PORT_OPTIMISED_TASK_SELECTION` 控制：

| 实现 | 数据结构 | 查找算法 | 架构 |
|------|---------|---------|------|
| 通用 C 实现 | 每个优先级一个 `List_t`，`uxTopReadyPriority` 记录最高优先级 | 从 `uxTopReadyPriority` 向下线性扫描 O(n) | 所有架构默认 |
| 位图优化 | 32 位位图 (`uxTopReadyPriority`)，bit N 表示优先级 N 非空 | ARM CLZ 指令一次计算 O(1) | Cortex-M3/M4/M7 (要求 `configMAX_PRIORITIES ≤ 32`) |

通用实现中：

```c
#define taskSELECT_HIGHEST_PRIORITY_TASK()
    UBaseType_t uxTopPriority = uxTopReadyPriority;
    while( listLIST_IS_EMPTY( &( pxReadyTasksLists[ uxTopPriority ] ) ) )
        --uxTopPriority;
    listGET_OWNER_OF_NEXT_ENTRY( pxCurrentTCB, &( pxReadyTasksLists[ uxTopPriority ] ) );
    uxTopReadyPriority = uxTopPriority;
```

ARM CM3 位图版本：

```c
#define portGET_HIGHEST_PRIORITY( uxTopPriority, uxReadyPriorities )
    uxTopPriority = ( 31UL - ( uint32_t ) ucPortCountLeadingZeros( ( uxReadyPriorities ) ) )
```

> 详细分析见 [3. FreeRTOS 任务管理与调度](3.%20FreeRTOS%20%E4%BB%BB%E5%8A%A1%E7%AE%A1%E7%90%86%E4%B8%8E%E8%B0%83%E5%BA%A6.md) 第 §3 节。

### 队列的统一设计：信号量和互斥锁都是队列

这是 FreeRTOS 最核心的设计决策 — **一个数据结构支撑五种同步原语**：

```c
typedef struct QueueDefinition {
    ...
    union {
        QueuePointers_t xQueue;          // 队列模式：pcTail, pcReadFrom
        SemaphoreData_t xSemaphore;      // 信号量/互斥锁模式：xMutexHolder, uxRecursiveCallCount
    } u;
    ...
} Queue_t;
```

| 原语 | `ucQueueType` | `uxItemSize` | `uxLength` | 存储区 | 特殊行为 |
|------|--------------|-------------|------------|--------|---------|
| 普通队列 | `queueQUEUE_TYPE_BASE` | >0 | N | 环形缓冲区 | 数据拷贝 |
| 二值信号量 | `queueQUEUE_TYPE_BINARY_SEMAPHORE` | 0 | 1 | 无（0字节） | `uxMessagesWaiting` = 计数值 |
| 计数信号量 | `queueQUEUE_TYPE_COUNTING_SEMAPHORE` | 0 | maxCount | 无 | `uxMessagesWaiting` 设初值 |
| 互斥锁 | `queueQUEUE_TYPE_MUTEX` | 0 | 1 | 无（`pcHead=NULL`标记） | 优先级继承 + 初始 give 一次 |
| 递归互斥锁 | `queueQUEUE_TYPE_RECURSIVE_MUTEX` | 0 | 1 | 无 | 加递归计数 |

```c
SemaphoreHandle_t == QueueHandle_t  // 相同的指针类型
#define xSemaphoreCreateBinary() xQueueGenericCreate(1, 0, queueQUEUE_TYPE_BINARY_SEMAPHORE)
#define xSemaphoreGive(s) xQueueGenericSend(s, NULL, 0, queueSEND_TO_BACK)
#define xSemaphoreTake(s, t) xQueueSemaphoreTake(s, t)
```

**事件组**、**任务通知**和**流/消息缓冲区**则另有自己的实现，不基于队列。

> 详细分析见 [4. FreeRTOS 队列管理](4.%20FreeRTOS%20%E9%98%9F%E5%88%97%E7%AE%A1%E7%90%86.md)（双锁机制、环形缓冲区指针计算、阻塞路径全流程）和 [5. FreeRTOS 信号量与互斥锁](5.%20FreeRTOS%20%E4%BF%A1%E5%8F%B7%E9%87%8F%E4%B8%8E%E4%BA%92%E6%96%A5%E9%94%81.md)（用户视角的 API 映射）。

### 双锁机制：ISR 安全的队列操作

当任务在队列操作中决定阻塞时，调度器被挂起、队列被锁定。此时 ISR 仍可向队列发送/接收数据，但**不直接操作任务事件列表**，而是通过 `cTxLock` / `cRxLock` 计数器记录延迟操作：

```c
// ISR 中，队列被锁定时
if (cTxLock == queueUNLOCKED) {
    // 正常路径：直接唤醒任务
    xTaskRemoveFromEventList(...);
} else {
    // 队列锁定：只递增计数
    pxQueue->cTxLock = (int8_t)(cTxLock + 1);
}
```

| cTxLock / cRxLock 值 | 含义 |
|---------------------|------|
| `-1` (`queueUNLOCKED`) | 队列未锁定，ISR 可直接操作事件列表 |
| `0` (`queueLOCKED_UNMODIFIED`) | 队列已锁定，尚无 ISR 操作 |
| `>0` | 锁定期间有 N 次 ISR 操作积压 |

任务恢复时在 `prvUnlockQueue()` 中**批量处理**所有积压的 ISR 操作：

```c
while (cTxLock > queueLOCKED_UNMODIFIED) {
    xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToReceive));
    --cTxLock;
}
```

这个模式在队列和流缓冲区中普遍使用，是理解 FreeRTOS ISR 安全性的核心。

> 详细分析见 [4. FreeRTOS 队列管理](4.%20FreeRTOS%20%E9%98%9F%E5%88%97%E7%AE%A1%E7%90%86.md) 的"双锁机制"节。

### 任务通知：最轻量的 IPC

任务通知是 TCB 内嵌的字段，**无需创建内核对象**：

```c
typedef struct tskTaskControlBlock {
    ...
    #if ( configUSE_TASK_NOTIFICATIONS == 1 )
        volatile uint32_t ulNotifiedValue[ configTASK_NOTIFICATION_ARRAY_ENTRIES ];
        volatile uint8_t ucNotifyState[ configTASK_NOTIFICATION_ARRAY_ENTRIES ];
    #endif
    ...
} tskTCB;
```

- 每个任务有 `configTASK_NOTIFICATION_ARRAY_ENTRIES` 个通知槽（默认 1 个）
- 四种通知行为：`eNoAction`（仅唤醒）、`eSetBits`（按位或）、`eIncrement`（计数）、`eSetValueWithOverwrite` / `eSetValueWithoutOverwrite`（直接赋值）
- 接收任务阻塞在 `ulTaskNotifyTake()` 或 `xTaskNotifyWait()`，无中间队列对象

**性能对比**：任务通知的发送/接收比信号量快约 45%（无队列结构体、无事件列表操作），但只能一对一。当需要一对多广播或多对一汇聚时仍需信号量或队列。

> 详细分析见 [6. FreeRTOS 任务通知](6.%20FreeRTOS%20%E4%BB%BB%E5%8A%A1%E9%80%9A%E7%9F%A5.md)。

### 延时链表双缓冲：处理 tick 溢出

Tick 计数器的 32 位无符号值会回绕（约 49.7 天 @ 1ms/tick）。FreeRTOS 使用**两个延时链表**解决：

- `pxDelayedTaskList` — 当前使用的延时链表
- `pxOverflowDelayedTaskList` — tick 溢出后使用的延时链表

```c
if( xTickCount == 0 )                    /* tick 溢出 */
    taskSWITCH_DELAYED_LISTS();          /* 交换两个链表指针 */
```

当任务的唤醒时间 < 当前时间（计算时发生了溢出），该任务被放入溢出链表。tick 溢出时交换指针，原溢出链表成为新的当前链表。

`xNextTaskUnblockTime` 缓存了延时链表头部任务的唤醒时间，避免每次 tick 都扫描整个链表。

> 详细分析见 [3. FreeRTOS 任务管理与调度](3.%20FreeRTOS%20%E4%BB%BB%E5%8A%A1%E7%AE%A1%E7%90%86%E4%B8%8E%E8%B0%83%E5%BA%A6.md) 第 §4.5-4.7 节。

## 任务（Task）

任务是**可被调度器暂停和恢复的 C 函数**。每个任务拥有：

- 任务函数（通常是无限循环 `for(;;)`）
- 独立栈空间
- 任务控制块（TCB）
- 优先级
- 当前状态

```c
static void CommunicationTask(void *pvParameters) {
    (void)pvParameters;
    for (;;) {
        Communication_WaitEvent();  // 阻塞等待
        Communication_Process();    // 处理数据
    }
}
```

### TCB 关键设计

TCB (`tskTaskControlBlock`) 是调度器管理的核心，其设计体现了几项关键权衡：

- **`pxTopOfStack` 必须是第一个成员** — PendSV 汇编代码通过 `ldr r0, [r2]` 直接读取第一个字作为栈顶指针，不依赖 C 结构体偏移计算
- **双列表项**：`xStateListItem` 用于挂入状态链表（就绪/延时/挂起），`xEventListItem` 用于挂入事件链表（队列等待），允许一个任务同时处于两种列表中（阻塞在某个对象上）
- **`xItemValue` 双重含义**：状态链表中存储唤醒时间（tick count），事件链表中存储优先级倒序值（`configMAX_PRIORITIES - uxPriority`）

> 详细分析见 [3. FreeRTOS 任务管理与调度](3.%20FreeRTOS%20%E4%BB%BB%E5%8A%A1%E7%AE%A1%E7%90%86%E4%B8%8E%E8%B0%83%E5%BA%A6.md) 第 §1 节。

## 调度器（Scheduler）

**固定优先级抢占式调度 + 同优先级时间片轮转**。

核心规则：**调度器始终选择处于就绪态的最高优先级任务运行。**

| 配置 | 行为 |
|------|------|
| `configUSE_PREEMPTION=1, configUSE_TIME_SLICING=1` | 抢占 + 自动时间片（默认） |
| `configUSE_PREEMPTION=1, configUSE_TIME_SLICING=0` | 抢占 + 同优先级需主动 yield |
| `configUSE_PREEMPTION=0` | 协作式：仅 yield/阻塞时切换 |

### 上下文切换机制（Cortex-M）

1. **SysTick 中断**触发
2. `xTaskIncrementTick()` 执行：
   - 递增 `xTickCount`，处理到期任务（延时→就绪）
   - 时间片轮转请求切换
   - 如果需要切换：悬起 PendSV（写 NVIC PENDSVSET bit）
3. 返回

PendSV 处理（最低优先级中断）：
1. `mrs r0, psp` — 读取当前栈指针
2. `stmdb r0!, {r4-r11}` — 保存 callee-saved 寄存器
3. `bl vTaskSwitchContext` — C 函数：选择下一个任务
4. `ldmia r0!, {r4-r11}` — 恢复新任务的寄存器
5. `msr psp, r0` — 更新 PSP
6. `bx r14` — 异常返回（硬件自动恢复 R0-R3,R12,LR,PC,xPSR）

PendSV 被设计为**最低优先级中断**，确保上下文切换在所有 ISR 完成之后才执行，中断响应延迟最小化。

## 四种任务状态

- Running → Ready: scheduler preemption or yield
- Ready → Running: scheduler selects highest priority task
- Running → Blocked: blocking API call (queue/semaphore/delay...)
- Blocked → Ready: condition satisfied (timeout/event)
- Running/Suspended ⇄ Suspended: vTaskSuspend/vTaskResume

> 阻塞 = 等待条件（队列/信号量/延时/通知/事件组），条件满足时自动恢复。挂起 = 必须显式调用 `vTaskResume()` 恢复。

### 无限阻塞的特殊处理

当 `xTicksToWait == portMAX_DELAY` 且 `INCLUDE_vTaskSuspend == 1` 时，任务不放入延时链表，而是放入 `xSuspendedTaskList`。这种任务不会被时间到期唤醒，只能由事件满足或显式 `vTaskResume()` 恢复：

```c
if( ( xTicksToWait == portMAX_DELAY ) && ( xCanBlockIndefinitely != pdFALSE ) )
{
    listINSERT_END( &xSuspendedTaskList, &( pxCurrentTCB->xStateListItem ) );
    /* 不入延时链表！*/
    return;
}
```

## Tick — 内核心跳

- 周期性硬件定时器中断（通常 1ms）
- 用途：更新节拍计数、检查延时到期、时间片轮转
- 配置：`configTICK_RATE_HZ 1000` → 1ms/tick

### Tick 中的处理流程

1. `xTickCount++`
2. 如果 tick 溢出 → 切换延时链表
3. 处理到期任务：延时链表头部 → 移除 → 放回就绪链表
   - 超时也从事件链表移除（！）
   - 如果优先级 ≥ 当前 → 请求切换
4. 时间片轮转：同一优先级 >1 任务 → 请求切换
5. `xYieldPending` 检查

调度器挂起期间，tick 中断不处理延时任务，只递增 `xPendedTicks`。恢复时补处理。

## 内核对象的统一原理

> 所有内核对象都在做同一件事：**条件不满足时让任务阻塞，条件满足后唤醒合适的任务**。

这一原理的三种实现路径：

| 路径 | 实现 | 代表对象 |
|------|------|---------|
| **队列路径** | 统一 `Queue_t` 数据结构 + `cRxLock/cTxLock` 双锁 | 普通队列、二值/计数信号量、互斥锁 |
| **独立实现路径** | 自有数据结构 + 自有等待列表 | 事件组（按位等待）、流/消息缓冲区（触发级）、软件定时器（守护任务） |
| **TCB 内置路径** | 无需内核对象，直接在 TCB 字段上操作 | 任务通知 |

## 选型速查

| 需求 | 优先选择 | 次选 | 说明 |
|------|----------|------|------|
| 传递固定大小数据 | 队列 | 消息缓冲区 | 队列拷贝数据到缓冲区；消息缓冲区传变长消息 |
| ISR → 单个任务唤醒 | 任务通知 | 二值信号量 | 任务通知快 ~45%，无需创建内核对象 |
| ISR → 多个任务唤醒 | 二值信号量（广播） | 事件组 | 信号量每个接收任务一个；事件组可用位组合广播 |
| 累计事件次数 | 计数信号量 | 任务通知(eIncrement) | 计数信号量上限可配置；任务通知上限始终为 ULONG_MAX |
| 保护共享资源 | 互斥锁 | 二值信号量 | 互斥锁有优先级继承，防止优先级反转 |
| 等待多个状态位 | 事件组 | — | 可任意组合 AND/OR 等待多个位 |
| 延时执行低频动作 | 软件定时器 | 任务 + vTaskDelay | 定时器基于守护任务，回调中不可阻塞 |
| 连续字节流 | 流缓冲区 | — | 无消息边界，触发级发送 |
| 变长消息 | 消息缓冲区 | 流缓冲区 + 头部 | 有消息边界，一个发送对应一个接收 |
| 一次读取不消耗数据 | 队列 Peek | — | 读指针恢复，消息仍在队列中 |
| 紧急插队发送 | 队列 SendToFront | — | 写指针改为回退读指针实现"插队" |

## Kernel vs 生态资源使用对比

| 资源 | Kernel (最小) | Kernel (完整) | 生态 (典型) |
|------|-------------|-------------|------------|
| ROM (Flash) | ~4 KB | ~12 KB | >50 KB |
| RAM (堆) | 取决于任务数 | 取决于任务数 | 依赖协议栈 |
| 对外依赖 | 无 | 无 | 网络/安全协议栈 |
