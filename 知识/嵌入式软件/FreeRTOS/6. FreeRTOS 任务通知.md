# FreeRTOS 任务通知 — 源码级分析

## 设计哲学

任务通知（Task Notification）是 FreeRTOS 中最轻量的任务间同步机制。其核心思想是：**每个 Task Control Block（TCB）中内嵌一个 32 位值和状态位**，发送方直接写入目标任务的 TCB，无需经过任何中间内核对象（队列、信号量、事件组）。省掉的正是这些对象所需的独立分配、初始化、以及发送/接收等待列表管理。

> 从源码看，整个机制由 `tasks.c` 中约 570 行代码实现（`#if configUSE_TASK_NOTIFICATIONS == 1` 包围），全部是直接的 TCB 字段操作——没有独立的数据结构，没有动态内存分配。

---

## TCB 中的通知字段

定义在 `tasks.c` 第 255-332 行的 `tskTaskControlBlock` 结构体中：

```c
#if ( configUSE_TASK_NOTIFICATIONS == 1 )
    volatile uint32_t ulNotifiedValue[ configTASK_NOTIFICATION_ARRAY_ENTRIES ];
    volatile uint8_t  ucNotifyState[ configTASK_NOTIFICATION_ARRAY_ENTRIES ];
#endif
```

两个字段都是 `volatile` 数组，维度由 `configTASK_NOTIFICATION_ARRAY_ENTRIES` 决定（默认 1，向后兼容 V10.4.0 之前的单通知值设计）。

### `ucNotifyState` — 通知状态机

定义在 `tasks.c` 第 70-73 行：

```c
#define taskNOT_WAITING_NOTIFICATION   ( ( uint8_t ) 0 )  /* 初始值（memset 清零） */
#define taskWAITING_NOTIFICATION       ( ( uint8_t ) 1 )  /* 任务已阻塞等待通知 */
#define taskNOTIFICATION_RECEIVED      ( ( uint8_t ) 2 )  /* 通知已送达待消费 */
```

三态转移：

- `taskNOT_WAITING_NOTIFICATION (0)` — initial state
  - Sender calls `xTaskGenericNotify` → `taskNOTIFICATION_RECEIVED (2)`
  - Receiver calls `xTaskNotifyWait`/`ulTaskNotifyTake` (value == 0) → `taskWAITING_NOTIFICATION (1)`
    - Sender notification arrives → `taskNOTIFICATION_RECEIVED (2)` — task is unblocked
    - Timeout/suspended → `taskNOT_WAITING_NOTIFICATION (0)`

### `ulNotifiedValue` — 32 位通知值

可表示：
- 计数（用作轻量信号量，递增/递减）
- 位掩码（用作轻量事件组，按位 OR/AND）
- 单值消息（覆盖写入）

### 初始化

`tasks.c` 第 984-988 行，在 `prvInitialiseNewTCB` 中：

```c
#if ( configUSE_TASK_NOTIFICATIONS == 1 )
    {
        memset( &( pxNewTCB->ulNotifiedValue[ 0 ] ), 0x00,
                sizeof( pxNewTCB->ulNotifiedValue ) );
        memset( &( pxNewTCB->ucNotifyState[ 0 ] ), 0x00,
                sizeof( pxNewTCB->ucNotifyState ) );
    }
#endif
```

全部初始化为 0。两个数组用 `sizeof` 计算总大小：`4 * configTASK_NOTIFICATION_ARRAY_ENTRIES` 字节（value）+ `1 * configTASK_NOTIFICATION_ARRAY_ENTRIES` 字节（state）。

## 公共 API 宏

所有公共 API 都是宏，统一转发到形如 `xTaskGeneric*` 的内核函数。源文件 `include/task.h`：

```c
/* 发送 — 全功能 */
#define xTaskNotify( xTaskToNotify, ulValue, eAction ) \
    xTaskGenericNotify( ( xTaskToNotify ), ( tskDEFAULT_INDEX_TO_NOTIFY ), \
                        ( ulValue ), ( eAction ), NULL )

/* 发送 — 轻量 Give (eIncrement) */
#define xTaskNotifyGive( xTaskToNotify ) \
    xTaskGenericNotify( ( xTaskToNotify ), ( tskDEFAULT_INDEX_TO_NOTIFY ), \
                        ( 0 ), eIncrement, NULL )

/* 接收 — 邮箱风格 */
#define xTaskNotifyWait( ulBitsToClearOnEntry, ulBitsToClearOnExit, \
                         pulNotificationValue, xTicksToWait ) \
    xTaskGenericNotifyWait( tskDEFAULT_INDEX_TO_NOTIFY, \
                            ( ulBitsToClearOnEntry ), ( ulBitsToClearOnExit ), \
                            ( pulNotificationValue ), ( xTicksToWait ) )

/* 接收 — 信号量风格 */
#define ulTaskNotifyTake( xClearCountOnExit, xTicksToWait ) \
    ulTaskGenericNotifyTake( ( tskDEFAULT_INDEX_TO_NOTIFY ), \
                             ( xClearCountOnExit ), ( xTicksToWait ) )

/* ISR 发送 */
#define xTaskNotifyFromISR( xTaskToNotify, ulValue, eAction, pxHigherPriorityTaskWoken ) \
    xTaskGenericNotifyFromISR( ( xTaskToNotify ), ( tskDEFAULT_INDEX_TO_NOTIFY ), \
                               ( ulValue ), ( eAction ), NULL, \
                               ( pxHigherPriorityTaskWoken ) )

#define vTaskNotifyGiveFromISR( xTaskToNotify, pxHigherPriorityTaskWoken ) \
    vTaskGenericNotifyGiveFromISR( ( xTaskToNotify ), ( tskDEFAULT_INDEX_TO_NOTIFY ), \
                                   ( pxHigherPriorityTaskWoken ) )
```

`tskDEFAULT_INDEX_TO_NOTIFY` 定义为 0。`xTaskNotifyAndQuery` 变体只是传入非 NULL 的 `pulPreviousNotificationValue` 指针。

## 发送函数源码分析

### `xTaskGenericNotify` — 全功能发送

`tasks.c` 第 4862-4978 行。这是任务通知的核心入口。发送方**从不阻塞**。

```
xTaskGenericNotify(xTaskToNotify, uxIndexToNotify, ulValue, eAction, pulPreviousNotificationValue)
```

**执行流程：**

1. `taskENTER_CRITICAL()`
2. 如果 `pulPreviousNotificationValue != NULL`：`*pulPreviousNotificationValue = pxTCB->ulNotifiedValue[uxIndexToNotify]`（保存旧值）
3. `ucOriginalNotifyState = pxTCB->ucNotifyState[uxIndexToNotify]`（保存旧状态）
4. `pxTCB->ucNotifyState[uxIndexToNotify] = taskNOTIFICATION_RECEIVED`（置为"已通知"）
5. 根据 `eAction` 分支：
   - `eSetBits`: `pxTCB->ulNotifiedValue |= ulValue`
   - `eIncrement`: `pxTCB->ulNotifiedValue++`
   - `eSetValueWithOverwrite`: `pxTCB->ulNotifiedValue = ulValue`
   - `eSetValueWithoutOverwrite`: 如果 `ucOriginalNotifyState != taskNOTIFICATION_RECEIVED` 则写入，否则返回 `pdFAIL`
   - `eNoAction`: 只修改状态，不改值
6. 如果 `ucOriginalNotifyState == taskWAITING_NOTIFICATION`：
   - `listREMOVE_ITEM(&(pxTCB->xStateListItem))`（从 delay/suspend 列表移除）
   - `prvAddTaskToReadyList(pxTCB)`（加入就绪列表）
   - 如果 `pxTCB->uxPriority > pxCurrentTCB->uxPriority`：`taskYIELD_IF_USING_PREEMPTION()`（请求上下文切换）
7. `taskEXIT_CRITICAL()`

关键观察：

- **`eSetValueWithoutOverwrite` 的原子性**：通过检查 `ucOriginalNotifyState` 是否已是 `taskNOTIFICATION_RECEIVED` 来判断接收方是否已消费旧值。如果尚未消费，写入被拒绝并返回 `pdFAIL`。这保证了"无覆盖"语义——但注意它只检查消费状态，不检查值本身。
- **解除阻塞即从状态链表移除**：第 4937 行的 `listREMOVE_ITEM` 将目标任务从延时列表或挂起列表中取出，第 4938 行放入就绪列表。这是通知解除阻塞的全部操作——不需要信号量那样的复杂出队逻辑。
- **优先级比较**：第 4959 行，如果被通知任务的优先级高于当前任务，调用 `taskYIELD_IF_USING_PREEMPTION()`（在抢占模式下展开为 `portYIELD_WITHIN_API()`）。

### `eNotifyAction` 动作枚举

定义在 `include/task.h` 第 107-114 行：

```c
typedef enum
{
    eNoAction = 0,                /* 仅唤醒，不修改通知值 */
    eSetBits,                     /* 按位或：ulNotifiedValue |= ulValue */
    eIncrement,                   /* 递增：ulNotifiedValue++ */
    eSetValueWithOverwrite,       /* 覆盖写入（立即写入，不管旧值是否被消费） */
    eSetValueWithoutOverwrite     /* 条件写入（仅当旧值已被消费） */
} eNotifyAction;
```

### `xTaskNotifyGive` — 轻量 Give

宏展开为 `xTaskGenericNotify(xTaskToNotify, 0, 0, eIncrement, NULL)`。值 `ulValue=0` 在 `eIncrement` 分支中被忽略——无论传什么值，都只做 `ulNotifiedValue++`。

## ISR 安全版本

### `xTaskGenericNotifyFromISR`

`tasks.c` 第 4985-5117 行。与任务上下文版本的关键区别：

- 使用 `portSET_INTERRUPT_MASK_FROM_ISR()` / `portCLEAR_INTERRUPT_MASK_FROM_ISR()` 替代 `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`。这是因为 ISR 上下文中的临界区保护必须通过中断屏蔽寄存器操作，而不是锁调度器。
- 包含 `portASSERT_IF_INTERRUPT_PRIORITY_INVALID()` 断言，验证 ISR 优先级不超过 `configMAX_SYSCALL_INTERRUPT_PRIORITY`。
- 解除阻塞时多了一个**调度器挂起检查**（第 5082 行）：

```c
if( uxSchedulerSuspended == ( UBaseType_t ) pdFALSE )
{
    listREMOVE_ITEM( &( pxTCB->xStateListItem ) );
    prvAddTaskToReadyList( pxTCB );
}
else
{
    /* 调度器挂起时不能操作就绪列表，放入待处理列表 */
    listINSERT_END( &( xPendingReadyList ), &( pxTCB->xEventListItem ) );
}
```

当调度器挂起时，不能直接操作就绪列表——任务被临时放入 `xPendingReadyList`，等 `xTaskResumeAll()` 时再处理。

- 通过 `pxHigherPriorityTaskWoken` 参数通知调用者是否需要上下文切换：

```c
if( pxTCB->uxPriority > pxCurrentTCB->uxPriority )
{
    if( pxHigherPriorityTaskWoken != NULL )
    {
        *pxHigherPriorityTaskWoken = pdTRUE;
    }
    xYieldPending = pdTRUE;  /* 兜底标记 */
}
```

### `vTaskGenericNotifyGiveFromISR`

`tasks.c` 第 5124-5206 行。专用于"Give"的简化 ISR 版本——不处理 `eAction`，直接递增：

```c
ucOriginalNotifyState = pxTCB->ucNotifyState[ uxIndexToNotify ];
pxTCB->ucNotifyState[ uxIndexToNotify ] = taskNOTIFICATION_RECEIVED;

/* 'Giving' is equivalent to incrementing a count in a counting semaphore. */
( pxTCB->ulNotifiedValue[ uxIndexToNotify ] )++;
```

解除阻塞逻辑与 `xTaskGenericNotifyFromISR` 完全相同。

## 接收函数源码分析

### `ulTaskGenericNotifyTake` — 信号量风格接收

`tasks.c` 第 4704-4769 行。模拟二值/计数信号量的 `take` 操作。

```
ulTaskGenericNotifyTake(uxIndexToWait, xClearCountOnExit, xTicksToWait)
```

**两阶段设计：** 接收函数被拆成两个临界区，中间是一个可能发生的上下文切换（portYIELD_WITHIN_API）。

**阶段一 — 条件阻塞（第 4712-4741 行）：**

1. `taskENTER_CRITICAL()`
2. 如果 `ulNotifiedValue[uxIndexToWait] == 0`（当前没有未处理的通知）：
   - `ucNotifyState = taskWAITING_NOTIFICATION`
   - 如果 `xTicksToWait > 0`：
     - `prvAddCurrentTaskToDelayedList(xTicksToWait, pdTRUE)`
     - `portYIELD_WITHIN_API()`（交出 CPU）
3. `taskEXIT_CRITICAL()`

如果进入阻塞，当前任务被加入延时列表。`portYIELD_WITHIN_API()` 触发上下文切换，任务在此被挂起。恢复执行后从 `portYIELD_WITHIN_API()` 返回，继续到阶段二。

**阶段二 — 读取并清除（第 4743-4765 行）：**

1. `taskENTER_CRITICAL()`
2. `ulReturn = ulNotifiedValue[uxIndexToWait]`
3. 如果 `ulReturn != 0`：
   - 如果 `xClearCountOnExit != pdFALSE`（二值信号量模式）：`ulNotifiedValue[uxIndexToWait] = 0`（清零）
   - 否则（计数信号量模式）：`ulNotifiedValue[uxIndexToWait] = ulReturn - 1`（减 1）
4. `ucNotifyState = taskNOT_WAITING_NOTIFICATION`
5. `taskEXIT_CRITICAL()`
6. `return ulReturn`

**`xClearCountOnExit` 的两种行为：**

| `xClearCountOnExit` | 语义 | `ulNotifiedValue` 变化 |
|---|---|---|
| `pdTRUE` | 二值信号量 | 清零为 0 |
| `pdFALSE` | 计数信号量 | 减 1 |

返回值始终是**变更前的值**。这使得调用者可以通过返回值判断是否真正等到了一次通知（返回 0 表示超时）。

### `xTaskGenericNotifyWait` — 邮箱风格接收

`tasks.c` 第 4776-4855 行。提供更细粒度的位控制——可以指定进入时清除哪些位、退出时清除哪些位。

```
xTaskGenericNotifyWait(uxIndexToWait, ulBitsToClearOnEntry,
                       ulBitsToClearOnExit, pulNotificationValue, xTicksToWait)
```

**阶段一 — 条件阻塞（第 4786-4820 行）：**

1. `taskENTER_CRITICAL()`
2. 如果 `ucNotifyState != taskNOTIFICATION_RECEIVED`（没有待处理通知）：
   - `ulNotifiedValue &= ~ulBitsToClearOnEntry`（进入时按位清除）
   - `ucNotifyState = taskWAITING_NOTIFICATION`
   - 如果 `xTicksToWait > 0`：
     - `prvAddCurrentTaskToDelayedList(xTicksToWait, pdTRUE)`
     - `portYIELD_WITHIN_API()`
3. `taskEXIT_CRITICAL()`

**阶段二 — 读取并清除（第 4822-4851 行）：**

1. `taskENTER_CRITICAL()`
2. 如果 `pulNotificationValue != NULL`：`*pulNotificationValue = ulNotifiedValue`（输出当前值）
3. 如果 `ucNotifyState != taskNOTIFICATION_RECEIVED`：`xReturn = pdFALSE`（超时）
4. 否则：
   - `ulNotifiedValue &= ~ulBitsToClearOnExit`（退出时按位清除）
   - `xReturn = pdTRUE`（收到通知）
5. `ucNotifyState = taskNOT_WAITING_NOTIFICATION`
6. `taskEXIT_CRITICAL()`
7. `return xReturn`

**`ulBitsToClearOnEntry` vs `ulBitsToClearOnExit` 的作用：**

| 参数 | 执行时机 | 典型值 | 用途 |
|---|---|---|---|
| `ulBitsToClearOnEntry` | 进入阻塞前 | `0` 或 `0xFFFFFFFF` | 阻塞前清空，避免旧数据干扰 |
| `ulBitsToClearOnExit` | 退出阻塞后 | `0` 或 `0xFFFFFFFF` | 读取后清空，准备下次接收 |

模拟事件组时 `ulBitsToClearOnEntry = 0`（保持位不变），`ulBitsToClearOnExit = 0xFFFFFFFF`（收到后全部清空再根据值判断哪些位被置位）。

超时判断：第 4837 行，函数返回后检查 `ucNotifyState` 是否变为 `taskNOTIFICATION_RECEIVED`。如果没有，说明是超时唤醒而非通知唤醒，返回 `pdFALSE`。

## 辅助函数

### `xTaskGenericNotifyStateClear` — 清除通知状态

`tasks.c` 第 5213-5240 行。静默清除通知状态——不阻塞、不改值，仅将 `ucNotifyState` 从 `taskNOTIFICATION_RECEIVED` 回退到 `taskNOT_WAITING_NOTIFICATION`。

```c
taskENTER_CRITICAL();
{
    if( pxTCB->ucNotifyState[ uxIndexToClear ] == taskNOTIFICATION_RECEIVED )
    {
        pxTCB->ucNotifyState[ uxIndexToClear ] = taskNOT_WAITING_NOTIFICATION;
        xReturn = pdPASS;
    }
    else
    {
        xReturn = pdFAIL;
    }
}
taskEXIT_CRITICAL();
```

### `ulTaskGenericNotifyValueClear` — 清除通知值的指定位

`tasks.c` 第 5247-5268 行。原子地读取旧值并清除指定位（`ulNotifiedValue &= ~ulBitsToClear`），返回变更前的完整值。

## 与调度器的交互

### 挂起中的通知处理

`vTaskSuspend()`（`tasks.c` 第 1751-1763 行）在挂起任务时会检查所有通知索引：

```c
for( x = 0; x < configTASK_NOTIFICATION_ARRAY_ENTRIES; x++ )
{
    if( pxTCB->ucNotifyState[ x ] == taskWAITING_NOTIFICATION )
    {
        /* 任务曾因等待通知而阻塞，但被挂起——未收到通知 */
        pxTCB->ucNotifyState[ x ] = taskNOT_WAITING_NOTIFICATION;
    }
}
```

这防止了任务被挂起后又恢复时意外收到早已过期的通知。

### 状态查询中的通知识别

`eTaskGetState()`（`tasks.c` 第 1429-1448 行）在判断任务状态时会检查通知状态：

```c
/* 任务不在任何对象的 event list 上，但可能因等待通知而阻塞 */
if( pxTCB->ucNotifyState[ x ] == taskWAITING_NOTIFICATION )
{
    eReturn = eBlocked;  /* 不是 eSuspended */
}
```

这确保因等待通知而阻塞的任务被正确报告为 `eBlocked` 而非 `eSuspended`。

### Tickless Idle 优化

当通知解除阻塞一个任务时，`xTaskGenericNotify` 会调用 `prvResetNextTaskUnblockTime()`（第 4955 行，由 `configUSE_TICKLESS_IDLE` 保护）。这确保 tickless idle 模式下系统尽早退出休眠，因为被通知任务的唤醒时间已不再受原始超时控制。

## 五种动作的发送方行为对比

| eAction | `ulNotifiedValue` 变化 | 可能阻塞 | 返回 |
|---|---|---|---|
| `eNoAction` | 不变 | 否 | `pdPASS` |
| `eSetBits` | `\|= ulValue` | 否 | `pdPASS` |
| `eIncrement` | `++` | 否 | `pdPASS` |
| `eSetValueWithOverwrite` | `= ulValue` | 否 | `pdPASS` |
| `eSetValueWithoutOverwrite` | `= ulValue`（仅当未 pending） | 否 | `pdPASS` 或 `pdFAIL` |

**`eSetValueWithoutOverwrite` 返回 `pdFAIL` 的条件**：目标 TCB 的 `ucNotifyState` 在调用时已是 `taskNOTIFICATION_RECEIVED`，表明接收方尚未通过 `xTaskNotifyWait`/`ulTaskNotifyTake` 或 `xTaskNotifyStateClear` 消费前一次通知。

## 性能优势的源码根源

| 对比 | 信号量（基于队列） | 任务通知 |
|---|---|---|
| 数据结构 | `Queue_t` + 计数变量 + 等待列表 | 两个 `uint32_t` + 两个 `uint8_t` 数组（在 TCB 内） |
| 发送路径 | 临界区 + `listINSERT_END`（入队）+ 可能 `prvCopyDataToQueue` | 临界区 + 直接写 TCB 字段 + 条件 `listREMOVE_ITEM`/`prvAddTaskToReadyList` |
| 接收阻塞 | 从队列 event list 上等待，需维护优先级排序 | 直接从当前 TCB 状态判断，加入延时列表 |
| 动态内存 | 需要 `pvPortMalloc` 分配队列对象 | TCB 已预分配，零额外分配 |

源码层面的核心差异：**任务通知没有发送者等待列表**。信号量和队列为了实现"多个任务可以等待同一个对象"，需要维护独立的 `xTasksWaitingToSend` 和 `xTasksWaitingToReceive` 列表。任务通知是**点对点**的——每个通知属于特定的 TCB，因此不需要这些列表。

## 典型使用模式的源码映射

### ISR 唤醒任务（最推荐）

```c
/* ISR 上下文 */
void UART_ISR(void) {
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    vTaskNotifyGiveFromISR(xHandlerTask, &xHigherPriorityTaskWoken);
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
    /* 源码路径：
     *   vTaskGenericNotifyGiveFromISR → ulNotifiedValue[0]++,
     *   ucNotifyState[0] = taskNOTIFICATION_RECEIVED,
     *   如果 ucNotifyState 原为 taskWAITING_NOTIFICATION,
     *   则从延时列表移除并加入就绪列表 */
}

/* 任务上下文 */
void vHandlerTask(void *pvParameters) {
    for (;;) {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);
        /* 阻塞时：
         *   ucNotifyState = taskWAITING_NOTIFICATION
         *   prvAddCurrentTaskToDelayedList(portMAX_DELAY, pdTRUE) */
        ProcessData();
        /* 唤醒后：
         *   ulNotifiedValue[0] 被清零（pdTRUE 模式）
         *   ucNotifyState = taskNOT_WAITING_NOTIFICATION */
    }
}
```

### 事件组模拟

```c
/* 发送方 */
xTaskNotify(xEventTask, 0x01, eSetBits);  /* 按位 OR */

/* 接收方 */
uint32_t ulBits;
xTaskNotifyWait(0, 0xFFFFFFFF, &ulBits, portMAX_DELAY);
/* 进入阻塞时 ulNotifiedValue 保持不变（ulBitsToClearOnEntry==0）
 * 收到后 ulNotifiedValue 被清零（ulBitsToClearOnExit==0xFFFFFFFF） */
if (ulBits & 0x01) { /* 事件1发生 */ }
```

### 带超时的 1:1 数据传递

```c
/* 发送方 */
xTaskNotify(xReceiverTask, 0xDEADBEEF, eSetValueWithOverwrite);

/* 接收方 */
uint32_t ulValue;
if (xTaskNotifyWait(0xFFFFFFFF, 0xFFFFFFFF, &ulValue, pdMS_TO_TICKS(100)) == pdTRUE)
{
    /* 收到 ulValue == 0xDEADBEEF；ulBitsToClearOnEntry=0xFFFFFFFF
     * 在进入阻塞前就清空了 ulNotifiedValue，
     * ulBitsToClearOnExit=0xFFFFFFFF 在退出时再次清零 */
}
```

## 限制的源码根源

| 限制 | 源码原因 |
|---|---|
| 单接收者 | 通知直接写入特定 TCB 的 `ulNotifiedValue`——没有"广播"机制 |
| 邮箱容量=1 | `ucNotifyState` 只有三种状态，无法区分"收到 1 条"和"收到 N 条"（接收方不消费时状态一直是 `taskNOTIFICATION_RECEIVED`） |
| 仅 32 位值 | `ulNotifiedValue` 是 `uint32_t`，没有额外缓冲区 |
