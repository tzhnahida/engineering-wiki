# FreeRTOS 队列管理 — 逐函数深度分析

## 队列的统一设计

FreeRTOS 的队列机制是整个内核的**基石**。它通过一个 `QueueDefinition` (即 `Queue_t`) 结构体实现了五种不同的同步原语：

| 原语 | ucQueueType | 说明 |
|------|-------------|------|
| 普通队列 | `queueQUEUE_TYPE_BASE` (0) | 存储数据的环形 FIFO |
| 队列集 (Queue Set) | `queueQUEUE_TYPE_SET` (0) | 哨兵/容器，本身也是一个队列 |
| 互斥锁 | `queueQUEUE_TYPE_MUTEX` (1) | 带优先级继承的互斥锁 |
| 计数信号量 | `queueQUEUE_TYPE_COUNTING_SEMAPHORE` (2) | 可计数的信号量 |
| 二进制信号量 | `queueQUEUE_TYPE_BINARY_SEMAPHORE` (3) | 取值为 0/1 的信号量 |
| 递归互斥锁 | `queueQUEUE_TYPE_RECURSIVE_MUTEX` (4) | 支持递归加锁的互斥锁 |

SemaphoreHandle_t 就是 QueueHandle_t 的类型重定义（`typedef QueueHandle_t SemaphoreHandle_t`）。这意味着所有信号量/互斥锁 API 最终都调用队列代码。

## 数据结构

### Queue_t (QueueDefinition) 结构体 — 每个字段详解

```c
typedef struct QueueDefinition {
    int8_t *pcHead;           // 指向队列存储区起始位置
    int8_t *pcWriteTo;        // 指向下一个可写入位置（环形缓冲区写指针）

    union {
        QueuePointers_t xQueue;      // 队列模式：含 pcTail 和 pcReadFrom
        SemaphoreData_t xSemaphore;  // 信号量/互斥锁模式：含 xMutexHolder 和 uxRecursiveCallCount
    } u;

    List_t xTasksWaitingToSend;      // 因队列满而阻塞、等待发送的任务链表（按优先级排序）
    List_t xTasksWaitingToReceive;   // 因队列空而阻塞、等待接收的任务链表（按优先级排序）

    volatile UBaseType_t uxMessagesWaiting;  // 当前队列中的消息数（对于信号量就是计数值）
    UBaseType_t uxLength;            // 队列最大容量（条目数）
    UBaseType_t uxItemSize;          // 每个条目的字节数（信号量为 0）

    volatile int8_t cRxLock;         // 队列锁定时接收操作的计数（见下文"双锁机制"）
    volatile int8_t cTxLock;         // 队列锁定时发送操作的计数

#if (configSUPPORT_STATIC_ALLOCATION == 1) && (configSUPPORT_DYNAMIC_ALLOCATION == 1)
    uint8_t ucStaticallyAllocated;   // 是否静态分配（影响删除时的内存释放）
#endif

#if (configUSE_QUEUE_SETS == 1)
    struct QueueDefinition *pxQueueSetContainer;  // 指向所属的队列集（非空时表示该队列是某个队列集的成员）
#endif

#if (configUSE_TRACE_FACILITY == 1)
    UBaseType_t uxQueueNumber;       // 调试用队列编号
    uint8_t ucQueueType;             // 队列类型（见上表）
#endif
} xQUEUE;
typedef xQUEUE Queue_t;
```

#### 关键技巧：联合体复用

```c
typedef struct QueuePointers {
    int8_t *pcTail;        // 存储区末尾标记（pcHead + uxLength * uxItemSize）
    int8_t *pcReadFrom;    // 最近一次读取位置（环形缓冲区读指针）
} QueuePointers_t;

typedef struct SemaphoreData {
    TaskHandle_t xMutexHolder;         // 当前持有互斥锁的任务句柄
    UBaseType_t uxRecursiveCallCount;  // 递归互斥锁的计数值
} SemaphoreData_t;
```

当用作**普通队列**时，联合体使用 `xQueue` 部分（pcTail, pcReadFrom）；
当用作**信号量/互斥锁**时，联合体使用 `xSemaphore` 部分（xMutexHolder, uxRecursiveCallCount）。

#### 关键技巧：pcHead 的复用

```c
#define uxQueueType    pcHead
#define queueQUEUE_IS_MUTEX  NULL
```

对互斥锁而言，`pcHead` 被设为 `NULL`，作为"此队列是互斥锁"的标志。在代码中检查 `pxQueue->uxQueueType == queueQUEUE_IS_MUTEX` 实际就是检查 `pcHead == NULL`。这避免了给结构体增加额外字段。

### 内存布局：一分配连续的块

动态创建时，`xQueueGenericCreate` 只调用一次 `pvPortMalloc`：

```
|  Queue_t 结构体  |  存储区 (uxLength * uxItemSize 字节)  |
^                  ^
pxNewQueue         pucQueueStorage = pxNewQueue + sizeof(Queue_t)
```

```c
xQueueSizeInBytes = (size_t)(uxQueueLength * uxItemSize);
pxNewQueue = (Queue_t *)pvPortMalloc(sizeof(Queue_t) + xQueueSizeInBytes);

// 存储区紧跟在结构体之后
pucQueueStorage = (uint8_t *)pxNewQueue;
pucQueueStorage += sizeof(Queue_t);
```

对于信号量（`uxItemSize == 0`），存储区大小为 0，`pcHead` 被设为指向自身（队列结构体地址）作为一个无害值，因为 `NULL` 已被用于标记互斥锁：

```c
if (uxItemSize == 0) {
    pxNewQueue->pcHead = (int8_t *)pxNewQueue;  // 指向自身，非 NULL
} else {
    pxNewQueue->pcHead = (int8_t *)pucQueueStorage;
}
```

### 环形缓冲区的指针计算

队列存储区是一个**字节寻址的环形缓冲区**。所有指针类型为 `int8_t *`（即字节指针），可通过简单的指针算术计算偏移：

```
pcHead → [ item 0 ]  ← pcReadFrom 初始指向最后一个位置
         [ item 1 ]
         [ item 2 ]
         [ item 3 ]  ← pcWriteTo 初始指向第一个位置
         ...
         [ item N-1 ] ← pcTail = pcHead + N * itemSize
```

初始化（`xQueueGenericReset`）：
```c
pxQueue->u.xQueue.pcTail = pxQueue->pcHead + (uxLength * uxItemSize);
pxQueue->pcWriteTo = pxQueue->pcHead;
pxQueue->u.xQueue.pcReadFrom = pxQueue->pcHead + ((uxLength - 1) * uxItemSize);
```

**为什么 pcReadFrom 初始指向最后一个位置？** 因为 `prvCopyDataFromQueue` 先移动读指针再读取：

```c
// prvCopyDataFromQueue 伪逻辑
pcReadFrom += itemSize;
if (pcReadFrom >= pcTail) pcReadFrom = pcHead;
memcpy(buffer, pcReadFrom, itemSize);
```

这种设计让读指针永远指向**最近一次读取的位置**，读之前先前进一格，实现 FIFO。

### 写操作 (prvCopyDataToQueue)

**写向后（queueSEND_TO_BACK）**：
```c
memcpy(pcWriteTo, pvItemToQueue, uxItemSize);
pcWriteTo += uxItemSize;
if (pcWriteTo >= pcTail) pcWriteTo = pcHead;  // 回绕
```

**写向前（queueSEND_TO_FRONT）**：
```c
pcReadFrom -= uxItemSize;
if (pcReadFrom < pcHead) pcReadFrom = pcTail - uxItemSize;  // 回绕
memcpy(pcReadFrom, pvItemToQueue, uxItemSize);
```

向前的实质是将读指针**回退一格**并覆盖写入——下次读取就能立刻读到这个"插队"的数据。

### 读操作 (prvCopyDataFromQueue)

```c
pcReadFrom += uxItemSize;
if (pcReadFrom >= pcTail) pcReadFrom = pcHead;  // 回绕
memcpy(pvBuffer, pcReadFrom, uxItemSize);
```

先前进再读取，且**不修改写指针**。写指针只在发送时推进，这样读写指针各自独立追踪位置。

## 核心队列操作

### xQueueGenericCreate — 分配策略详解

```c
QueueHandle_t xQueueGenericCreate(
    const UBaseType_t uxQueueLength,
    const UBaseType_t uxItemSize,
    const uint8_t ucQueueType);
```

**步骤**：

1. **溢出检查**：
   ```c
   if ((uxQueueLength > 0) &&
       (SIZE_MAX / uxQueueLength >= uxItemSize) &&          // 乘法不溢出
       (SIZE_MAX - sizeof(Queue_t) >= (uxQueueLength * uxItemSize)))  // 加法不溢出
   ```

2. **一分配**：
   ```c
   pxNewQueue = pvPortMalloc(sizeof(Queue_t) + (uxQueueLength * uxItemSize));
   ```

3. **计算存储区地址**（跳过结构体头部）：
   ```c
   pucQueueStorage = (uint8_t *)pxNewQueue + sizeof(Queue_t);
   ```

4. **调用 `prvInitialiseNewQueue`** 初始化所有字段，然后调用 `xQueueGenericReset(pxQueue, pdTRUE)` 设置环形缓冲区指针和清空等待列表。

5. **对于互斥锁**，创建后额外调用 `prvInitialiseMutex`，该函数会：
   - 设置 `xMutexHolder = NULL`
   - 设置 `uxQueueType = queueQUEUE_IS_MUTEX`（即 `pcHead = NULL`）
   - 初始化 `uxRecursiveCallCount = 0`
   - 调用 `xQueueGenericSend` 赠送一次（使初始计数值为 1，表示互斥锁可用）

### xQueueGenericSend — 完整数据路径

```c
BaseType_t xQueueGenericSend(
    QueueHandle_t xQueue,
    const void *const pvItemToQueue,
    TickType_t xTicksToWait,
    const BaseType_t xCopyPosition);  // queueSEND_TO_BACK / _FRONT / queueOVERWRITE
```

**主循环**：整个函数在一个 `for(;;)` 循环中执行，最多可以经历以下阶段：

#### 阶段 1：快速路径（临界区内）

```c
taskENTER_CRITICAL();
if ((pxQueue->uxMessagesWaiting < pxQueue->uxLength) || (xCopyPosition == queueOVERWRITE)) {
    // 有空位 → 直接拷贝
    xYieldRequired = prvCopyDataToQueue(pxQueue, pvItemToQueue, xCopyPosition);
    
    // 队列集通知（如需要）
    if (pxQueue->pxQueueSetContainer != NULL) {
        prvNotifyQueueSetContainer(pxQueue);
    }
    
    // 唤醒等待接收的任务
    if (listLIST_IS_EMPTY(&(pxQueue->xTasksWaitingToReceive)) == pdFALSE) {
        xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToReceive));
        // 若被唤醒的任务优先级更高，则在临界区内直接请求上下文切换
        queueYIELD_IF_USING_PREEMPTION();
    }
    
    taskEXIT_CRITICAL();
    return pdPASS;
}
```

**prvCopyDataToQueue 内部流程**：

1. **若 `uxItemSize == 0`（信号量/互斥锁）**：
   - 仅递增 `uxMessagesWaiting`（信号量计数值加 1）
   - 如果是互斥锁，调用 `xTaskPriorityDisinherit` 处理优先级继承降级，并清除 `xMutexHolder`

2. **若 `xPosition == queueSEND_TO_BACK`**：
   - `memcpy(pcWriteTo, pvItemToQueue, uxItemSize)`
   - `pcWriteTo += uxItemSize`，超出 `pcTail` 则回绕到 `pcHead`

3. **否则（`queueSEND_TO_FRONT` 或 `queueOVERWRITE`）**：
   - `pcReadFrom -= uxItemSize`，低于 `pcHead` 则回绕
   - `memcpy(pcReadFrom, pvItemToQueue, uxItemSize)`
   - 如果是 `queueOVERWRITE`，不增加 `uxMessagesWaiting`（覆盖已有条目）

#### 阶段 2：阻塞路径

当队列已满且 `xTicksToWait > 0`：

```c
taskEXIT_CRITICAL();  // 先退出临界区

vTaskSuspendAll();    // 挂起调度器
prvLockQueue(pxQueue); // 锁定队列

if (xTaskCheckForTimeOut(&xTimeOut, &xTicksToWait) == pdFALSE) {
    // 超时未到期
    if (prvIsQueueFull(pxQueue) != pdFALSE) {
        // 仍然满 → 把自己加入 xTasksWaitingToSend 事件列表
        vTaskPlaceOnEventList(&(pxQueue->xTasksWaitingToSend), xTicksToWait);
        prvUnlockQueue(pxQueue);
        // 恢复调度器（可能触发上下文切换）
        xTaskResumeAll();
        // 回到 for(;;) 循环头部重试
    } else {
        // 已经有空位了 → 解锁并重试
        prvUnlockQueue(pxQueue);
        xTaskResumeAll();
    }
} else {
    // 超时已过期 → 返回 errQUEUE_FULL
    prvUnlockQueue(pxQueue);
    xTaskResumeAll();
    return errQUEUE_FULL;
}
```

### xQueueGenericSendFromISR — ISR 版本差异

```c
BaseType_t xQueueGenericSendFromISR(
    QueueHandle_t xQueue,
    const void *const pvItemToQueue,
    BaseType_t *const pxHigherPriorityTaskWoken,
    const BaseType_t xCopyPosition);
```

**关键差异**：

1. **无阻塞**：ISR 不能阻塞，队列满则直接返回 `errQUEUE_FULL`
2. **中断安全临界区**：使用 `portSET_INTERRUPT_MASK_FROM_ISR()` 而非 `taskENTER_CRITICAL()`
3. **不直接修改事件列表**：
   - 如果队列**未锁定**（`cTxLock == queueUNLOCKED`）：正常操作，唤醒等待任务
   - 如果队列**已锁定**（`cTxLock != queueUNLOCKED`）：仅递增 `cTxLock` 计数，延迟处理

```c
if (cTxLock == queueUNLOCKED) {
    // 正常路径：直接唤醒等待接收的任务
    if (xTaskRemoveFromEventList(...) != pdFALSE) {
        *pxHigherPriorityTaskWoken = pdTRUE;
    }
} else {
    // 队列被锁定：记录"有数据在锁定时到达"
    pxQueue->cTxLock = (int8_t)(cTxLock + 1);
}
```

4. **返回方式**：通过 `pxHigherPriorityTaskWoken` 传出是否需上下文切换，ISR 退出时由调用方判断是否调用 `portYIELD_FROM_ISR`

### xQueueGiveFromISR — 信号量专用 ISR 版本

为信号量优化的 ISR 发送函数，与 `xQueueGenericSendFromISR` 的区别：

- 不调用 `prvCopyDataToQueue`（信号量无数据拷贝）
- 直接递增 `uxMessagesWaiting`
- 适用于信号量（`uxItemSize == 0`），有 assert 检查

```c
pxQueue->uxMessagesWaiting = uxMessagesWaiting + 1;
```

### xQueueReceive — 接收数据路径

```c
BaseType_t xQueueReceive(
    QueueHandle_t xQueue,
    void *const pvBuffer,
    TickType_t xTicksToWait);
```

结构与发送函数对称，同样在一个 `for(;;)` 循环中：

#### 阶段 1：快速路径

```c
taskENTER_CRITICAL();
if (uxMessagesWaiting > 0) {
    prvCopyDataFromQueue(pxQueue, pvBuffer);              // 拷贝数据
    pxQueue->uxMessagesWaiting = uxMessagesWaiting - 1;   // 减少计数
    
    // 队列有空间了 → 唤醒等待发送的任务
    if (listLIST_IS_EMPTY(&(pxQueue->xTasksWaitingToSend)) == pdFALSE) {
        xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToSend));
        queueYIELD_IF_USING_PREEMPTION();
    }
    
    taskEXIT_CRITICAL();
    return pdPASS;
}
```

#### 阶段 2：阻塞路径

队列为空且 `xTicksToWait > 0` 时，与发送函数对称：
- 挂起调度器 → 锁定队列 → 检查超时 → 加入 `xTasksWaitingToReceive` → 解锁 → 恢复调度器 → 重试

### xQueueReceiveFromISR — ISR 版本

与发送的 ISR 版本逻辑对称：
- 读数据 → 减少计数 → 若队列未锁定则唤醒等待发送的任务 → 若锁定则递增 `cRxLock`

```c
prvCopyDataFromQueue(pxQueue, pvBuffer);
pxQueue->uxMessagesWaiting = uxMessagesWaiting - 1;

if (cRxLock == queueUNLOCKED) {
    // 唤醒等待发送的任务
    if (xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToSend)) != pdFALSE) {
        *pxHigherPriorityTaskWoken = pdTRUE;
    }
} else {
    pxQueue->cRxLock = (int8_t)(cRxLock + 1);
}
```

### xQueuePeek — 读取不移除

```c
BaseType_t xQueuePeek(
    QueueHandle_t xQueue,
    void *const pvBuffer,
    TickType_t xTicksToWait);
```

与 `xQueueReceive` 几乎相同，唯一的区别是**读取后恢复读指针**：

```c
pcOriginalReadPosition = pxQueue->u.xQueue.pcReadFrom;  // 保存
prvCopyDataFromQueue(pxQueue, pvBuffer);                  // 读数据
pxQueue->u.xQueue.pcReadFrom = pcOriginalReadPosition;    // 恢复
```

这导致：
- `uxMessagesWaiting` 不变（数据未移除）
- 读指针回到原位
- 但为了公平，仍会唤醒其他等待接收的任务（它们读到的还是同一个数据）

## 信号量与互斥锁路径

### xSemaphoreCreateBinary — 映射到队列创建

```c
#define xSemaphoreCreateBinary() \
    xQueueGenericCreate(1, 0, queueQUEUE_TYPE_BINARY_SEMAPHORE)
```

- 长度 1，条目大小 0 → 本质上就是"是否有可用资源"的标志位
- `uxMessagesWaiting` 初始为 0（首次 take 会阻塞），需要先 give

旧的 `vSemaphoreCreateBinary` 宏创建后会立即 give 一次（初始计数值 = 1）。

### xSemaphoreCreateCounting — 映射到队列创建

```c
#define xSemaphoreCreateCounting(uxMaxCount, uxInitialCount) \
    xQueueCreateCountingSemaphore(uxMaxCount, uxInitialCount)
```

`xQueueCreateCountingSemaphore` 内部：
```c
xHandle = xQueueGenericCreate(uxMaxCount, 0, queueQUEUE_TYPE_COUNTING_SEMAPHORE);
((Queue_t *)xHandle)->uxMessagesWaiting = uxInitialCount;  // 直接设初值
```

利用 `uxMessagesWaiting` 作为信号量计数值，`uxLength` 作为最大计数值。

### xSemaphoreGive — 映射到队列发送

```c
#define xSemaphoreGive(xSemaphore) \
    xQueueGenericSend(xSemaphore, NULL, 0, queueSEND_TO_BACK)
```

- 数据指针为 NULL，数据大小 0 → 仅递增 `uxMessagesWaiting`
- `xTicksToWait = 0` → 永不阻塞（互斥锁 Give 必须立即成功）

### xSemaphoreTake — 映射到队列接收

```c
#define xSemaphoreTake(xSemaphore, xBlockTime) \
    xQueueSemaphoreTake(xSemaphore, xBlockTime)
```

`xQueueSemaphoreTake` 类似于 `xQueueReceive` 但去掉了数据拷贝操作，关键区别是互斥锁的**优先级继承**逻辑。

## 优先级继承流程

### 初始化

`xQueueCreateMutex` → `prvInitialiseMutex`：
```c
pxNewQueue->u.xSemaphore.xMutexHolder = NULL;
pxNewQueue->uxQueueType = queueQUEUE_IS_MUTEX;  // pcHead = NULL
pxNewQueue->u.xSemaphore.uxRecursiveCallCount = 0;
xQueueGenericSend(pxNewQueue, NULL, 0, queueSEND_TO_BACK);  // 使计数值 = 1
```

### Take 时的继承

当高优先级任务尝试 take 已被低优先级任务持有的互斥锁时：

```c
// xQueueSemaphoreTake 中，阻塞前：
if (pxQueue->uxQueueType == queueQUEUE_IS_MUTEX) {
    // 让持有者继承当前任务优先级
    xInheritanceOccurred = xTaskPriorityInherit(pxQueue->u.xSemaphore.xMutexHolder);
}
vTaskPlaceOnEventList(&(pxQueue->xTasksWaitingToReceive), xTicksToWait);
```

`xTaskPriorityInherit`（在 task.c 中）将持有者的优先级提升到与等待者相同（如果等待者优先级更高）。

### Give 时的降级

当持有者 give 互斥锁时，`prvCopyDataToQueue` 会处理：

```c
if (pxQueue->uxItemSize == 0) {
    if (pxQueue->uxQueueType == queueQUEUE_IS_MUTEX) {
        xReturn = xTaskPriorityDisinherit(pxQueue->u.xSemaphore.xMutexHolder);
        pxQueue->u.xSemaphore.xMutexHolder = NULL;
    }
}
```

`xTaskPriorityDisinherit` 将持有者的优先级降回其原始优先级。返回值指示是否需要上下文切换。

### 超时降级

当等待互斥锁的任务超时时，也需要降级：

```c
// xQueueSemaphoreTake 超时路径
if (xInheritanceOccurred != pdFALSE) {
    UBaseType_t uxHighestWaitingPriority = prvGetDisinheritPriorityAfterTimeout(pxQueue);
    vTaskPriorityDisinheritAfterTimeout(pxQueue->u.xSemaphore.xMutexHolder, uxHighestWaitingPriority);
}
```

`prvGetDisinheritPriorityAfterTimeout` 计算仍在等待的其它任务中的最高优先级：

```c
if (listCURRENT_LIST_LENGTH(&(pxQueue->xTasksWaitingToReceive)) > 0) {
    uxHighestWaitingPriority = configMAX_PRIORITIES -
        listGET_ITEM_VALUE_OF_HEAD_ENTRY(&(pxQueue->xTasksWaitingToReceive));
} else {
    uxHighestWaitingPriority = tskIDLE_PRIORITY;  // 没有其他等待者时降回空闲优先级
}
```

FreeRTOS 的列表以优先级反序存放（`configMAX_PRIORITIES - priority` 为列表项值），所以头部就是最高优先级的等待任务。

### 递归互斥锁

```c
BaseType_t xQueueTakeMutexRecursive(QueueHandle_t xMutex, TickType_t xTicksToWait) {
    if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) {
        // 已持有 → 只递增计数值，不阻塞
        pxMutex->u.xSemaphore.uxRecursiveCallCount++;
        return pdPASS;
    } else {
        // 未持有 → 走标准 semaphore take
        xReturn = xQueueSemaphoreTake(pxMutex, xTicksToWait);
        if (xReturn != pdFAIL) {
            pxMutex->u.xSemaphore.uxRecursiveCallCount++;
        }
        return xReturn;
    }
}

BaseType_t xQueueGiveMutexRecursive(QueueHandle_t xMutex) {
    if (pxMutex->u.xSemaphore.xMutexHolder == xTaskGetCurrentTaskHandle()) {
        pxMutex->u.xSemaphore.uxRecursiveCallCount--;
        if (uxRecursiveCallCount == 0) {
            // 计数值归零 → 真正释放互斥锁
            xQueueGenericSend(pxMutex, NULL, 0, queueSEND_TO_BACK);
        }
        return pdPASS;
    } else {
        return pdFAIL;  // 非持有者不能 give
    }
}
```

## 队列集 (Queue Set) 的内部实现

### 数据结构

队列集**本身也是一个 Queue_t**，类型为 `queueQUEUE_TYPE_SET`。它的存储区条目大小是 `sizeof(Queue_t *)`，即每个条目存的是成员队列的句柄。

```c
QueueSetHandle_t xQueueCreateSet(const UBaseType_t uxEventQueueLength) {
    return xQueueGenericCreate(uxEventQueueLength, sizeof(Queue_t *), queueQUEUE_TYPE_SET);
}
```

每个成员队列通过 `pxQueueSetContainer` 指针指向所属的队列集。

### 加入和移除

```c
xQueueAddToSet(xQueueOrSemaphore, xQueueSet):
    // 检查该队列是否已属于别的集合
    if (pxQueueOrSemaphore->pxQueueSetContainer != NULL) return pdFAIL;
    // 检查队列是否非空（非空队列不能加入，已有事件会丢失）
    if (pxQueueOrSemaphore->uxMessagesWaiting != 0) return pdFAIL;
    // 建立双向关联
    pxQueueOrSemaphore->pxQueueSetContainer = xQueueSet;
    return pdPASS;
```

移除时需要队列为空，且属于目标队列集。

### 通知机制 (prvNotifyQueueSetContainer)

当成员队列收到数据时，`xQueueGenericSend` 中检查 `pxQueueSetContainer` 是否为 NULL：

```c
if (pxQueue->pxQueueSetContainer != NULL) {
    // 如果数据是覆盖写入（队列已满时覆盖），且原计数不为 0 → 不通知
    if ((xCopyPosition == queueOVERWRITE) && (uxPreviousMessagesWaiting != 0)) {
        // 跳过：计数值未变
    } else {
        // 通知队列集 → 将本队列的句柄拷贝到队列集中
        prvNotifyQueueSetContainer(pxQueue);
    }
}
```

`prvNotifyQueueSetContainer` 实际上就是**向队列集队列中发一条"消息"**，消息内容是触发者的句柄指针：

```c
prvCopyDataToQueue(pxQueueSetContainer, &pxQueue, queueSEND_TO_BACK);
// 其中 &pxQueue 是指向成员队列指针的指针，拷贝 sizeof(Queue_t *) 字节
```

### 选择 (xQueueSelectFromSet)

```c
xQueueSelectFromSet(QueueSetHandle_t xQueueSet, TickType_t xTicksToWait) {
    QueueSetMemberHandle_t xReturn = NULL;
    xQueueReceive(xQueueSet, &xReturn, xTicksToWait);  // 阻塞式接收
    return xReturn;  // 返回值就是有数据的成员队列的句柄
}
```

巧妙地复用了标准队列接收：读取队列集存储区，取出的是一个队列句柄。

## 线程安全：双锁机制

### 问题

FreeRTOS 的队列需要在多任务 + 多中断嵌套环境中安全运作。任务可以阻塞（睡眠等待），而 ISR 不能。两者的临界区保护策略不同：

| 上下文 | 临界区保护 | 阻塞能力 |
|--------|-----------|---------|
| 任务 (xQueueGenericSend/Receive) | `taskENTER_CRITICAL()` | 可阻塞（加入事件列表后挂起调度器） |
| ISR (xQueueGenericSendFromISR/ReceiveFromISR) | `portSET_INTERRUPT_MASK_FROM_ISR()` | 不可阻塞，必须立即返回 |

### prvLockQueue / prvUnlockQueue

```c
#define prvLockQueue(pxQueue)          \
    taskENTER_CRITICAL();              \
    if (pxQueue->cRxLock == queueUNLOCKED) \
        pxQueue->cRxLock = queueLOCKED_UNMODIFIED; \
    if (pxQueue->cTxLock == queueUNLOCKED) \
        pxQueue->cTxLock = queueLOCKED_UNMODIFIED; \
    taskEXIT_CRITICAL()
```

锁定的实质是将 `cRxLock` 和 `cTxLock` 从 `-1`（`queueUNLOCKED`）设为 `0`（`queueLOCKED_UNMODIFIED`）。这个操作在临界区中完成，确保排他性。

### 为什么需要双重锁定

当任务决定阻塞时（队列满/空）：

1. 退出外层临界区（允许 ISR 访问队列）
2. **挂起调度器**（`vTaskSuspendAll`）— 防止其他任务抢占
3. **锁定队列**（`prvLockQueue`）— 防止 ISR 修改事件列表
4. 检查条件是否仍然满足（队列还是满/空的吗？）
5. 如果是，将自己加入事件列表
6. **解锁队列**（`prvUnlockQueue`）— 处理 ISR 期间积压的操作
7. **恢复调度器**（`xTaskResumeAll`）— 触发实际的上下文切换

这种设计允许 ISR 在任务被挂起调度器时仍然能向队列发送/接收数据——只不过 ISR 不直接操作事件列表，而是递增 `cTxLock`/`cRxLock` 计数器。

### cTxLock / cRxLock 计数跟踪

| 值 | 含义 |
|----|------|
| `-1` (`queueUNLOCKED`) | 队列未锁定，ISR 可以直接操作事件列表 |
| `0` (`queueLOCKED_UNMODIFIED`) | 队列已锁定，尚无 ISR 操作发生 |
| `>0` | 队列已锁定，ISR 操作发生了 N 次（N 个数据到达或被取走） |

### prvUnlockQueue 流程

解锁时分两阶段处理 Tx 和 Rx：

```c
static void prvUnlockQueue(Queue_t *const pxQueue) {
    // 阶段 1：处理 TxLock（ISR 发送了数据到已锁队列）
    taskENTER_CRITICAL();
    int8_t cTxLock = pxQueue->cTxLock;
    while (cTxLock > queueLOCKED_UNMODIFIED) {
        // 处理队列集通知
        if (pxQueue->pxQueueSetContainer != NULL) {
            prvNotifyQueueSetContainer(pxQueue);
        }
        // 或者直接唤醒等待接收的任务
        if (listLIST_IS_EMPTY(&(pxQueue->xTasksWaitingToReceive)) == pdFALSE) {
            xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToReceive));
            vTaskMissedYield();
        } else {
            break;  // 没有更多等待者，停止循环
        }
        --cTxLock;
    }
    pxQueue->cTxLock = queueUNLOCKED;
    taskEXIT_CRITICAL();

    // 阶段 2：处理 RxLock（ISR 取走了数据）
    taskENTER_CRITICAL();
    int8_t cRxLock = pxQueue->cRxLock;
    while (cRxLock > queueLOCKED_UNMODIFIED) {
        if (listLIST_IS_EMPTY(&(pxQueue->xTasksWaitingToSend)) == pdFALSE) {
            xTaskRemoveFromEventList(&(pxQueue->xTasksWaitingToSend));
            vTaskMissedYield();
        } else {
            break;
        }
        --cRxLock;
    }
    pxQueue->cRxLock = queueUNLOCKED;
    taskEXIT_CRITICAL();
}
```

此设计确保了：**ISR 不会在非预期时间唤醒任务**，被延迟的唤醒操作在队列解锁时集中处理。

## 其他辅助函数

### xQueueGenericReset

- 重置所有指针和计数器到初始状态
- `xNewQueue == pdTRUE`：初始化等待列表
- `xNewQueue == pdFALSE`：唤醒一个等待发送的任务（因重置后队列为空变为可写）

### prvIsQueueEmpty / prvIsQueueFull

简单的 `uxMessagesWaiting` 比较，在临界区内执行。

### uxQueueMessagesWaiting / uxQueueSpacesAvailable

在临界区内读取 `uxMessagesWaiting` 或 `uxLength - uxMessagesWaiting`。

### xQueueIsQueueEmptyFromISR / xQueueIsQueueFullFromISR

ISR 版本，不使用临界区（中断掩码已由调用方保证）。

### vQueueDelete

从队列注册表移除 → 根据分配类型决定是否调用 `vPortFree`。

### xQueueGetMutexHolder

在临界区内检查 `uxQueueType == queueQUEUE_IS_MUTEX` 后返回 `xMutexHolder`。
