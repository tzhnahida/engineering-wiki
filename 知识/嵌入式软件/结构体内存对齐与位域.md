# 结构体内存对齐与位域

## 一句话

**内存对齐不是编译器的怪癖，而是 CPU 访存机制的硬性要求——理解它，才能写出既省 RAM 又不牺牲性能的嵌入式 C 代码。**

## 为什么会有内存对齐

现代 CPU 按**字（word）**为单位批量读取内存，不是逐个字节取。ARM Cortex-M 默认 4 字节对齐：

```
int 在 0x1000（4 的倍数）→ CPU 一次读完 ✅
int 在 0x1001（非对齐）     → CPU 读两次再拼接 ❌ 又慢又可能 HardFault
```

**自然对齐规则**：一个 N 字节的变量必须存放在 N 的倍数地址上。

| 类型 | 大小 | 自然对齐要求 |
|------|------|-------------|
| `uint8_t` | 1 | 1 字节对齐（任意地址） |
| `uint16_t` | 2 | 2 字节对齐（偶数地址） |
| `uint32_t` | 4 | 4 字节对齐 |
| `uint64_t` | 8 | 8 字节对齐 |

## padding 怎么来的

编译器在结构体成员之间插入填充字节（padding），确保每个成员满足自然对齐。

### 经典案例

```c
// ❌ 浪费一半空间 — sizeof = 12
struct sensor_data {
    uint8_t  id;      // offset 0 (1 byte)
    // padding: 3 bytes   // offset 1~3
    uint32_t value;    // offset 4 (4 bytes)
    uint8_t  status;   // offset 8 (1 byte)
    // padding: 3 bytes   // offset 9~11
};  // sizeof = 12，6 字节被浪费

// ✅ 调换顺序 — sizeof = 8，省 4 字节
struct sensor_data_compact {
    uint32_t value;    // offset 0 (4 bytes)
    uint8_t  id;       // offset 4 (1 byte)
    uint8_t  status;   // offset 5 (1 byte)
    // padding: 2 bytes   // offset 6~7
};  // sizeof = 8
```

> [!tip] 黄金法则
> **把大成员放前面，小的放后面**——最简单有效的省 RAM 方法，零性能代价。

### 结构体整体对齐

结构体大小必须是**最大成员对齐值的整数倍**。`sensor_data_compact` 中 `uint32_t` 要求 4 字节对齐，6 不是 4 的倍数 → 补到 8。

```
结构体对齐值 = max(所有成员的对齐值)
结构体大小   = 对齐值的整数倍（末尾补 padding）
```

## `packed`：破除对齐的利刃与代价

`__attribute__((packed))` 强制取消所有填充：

```c
struct __attribute__((packed)) sensor_data_packed {
    uint8_t  id;      // offset 0
    uint32_t value;    // offset 1（不对齐！）
    uint8_t  status;   // offset 5
};  // sizeof = 6 — 完全无浪费
```

### 代价：非对齐访问

| CPU | 非对齐访问行为 |
|-----|---------------|
| Cortex-M0/M0+ | ❌ **直接触发 HardFault** |
| Cortex-M3/M4/M7 | ⚠️ 硬件能处理，但 2~5 倍性能下降 |

```c
// Cortex-M4：非对齐写入产生 3 次总线操作 vs 正常 1 次
volatile struct packed_s s;
s.b = 0x12345678;  // 慢！
```

### 正确使用场景

| ✅ 应该用 | ❌ 不应该用 |
|-----------|------------|
| 协议帧解析（TCP/IP 头、CAN 帧） | 高频访问的热路径 |
| 文件系统元数据读取 | 普通业务数据结构 |
| 与硬件共用数据结构 | 需要频繁读写的变量 |

更安全的折中：用 `aligned` 控制整体对齐而非完全取消：

```c
struct __attribute__((aligned(4))) partial_packed {
    uint8_t  a;
    uint32_t b;
    uint16_t c;
};  // 内部无填充，但整体按 4 字节对齐
```

## 位域（bit-field）：把比特用到极致

### 基本语法

```c
struct status_reg {
    unsigned int ready    : 1;   // bit 0
    unsigned int error    : 1;   // bit 1
    unsigned int mode     : 2;   // bit 2~3
    unsigned int reserved : 4;   // bit 4~7
};
// sizeof = 4（一个 unsigned int 的宽度）
```

### 实战：硬件寄存器映射

```c
typedef struct {
    volatile uint32_t PE   : 1;   // bit 0: 奇偶校验错误
    volatile uint32_t FE   : 1;   // bit 1: 帧错误
    volatile uint32_t RXNE : 1;   // bit 5: 读数据寄存器非空
    volatile uint32_t TC   : 1;   // bit 6: 发送完成
    volatile uint32_t TXE  : 1;   // bit 7: 发送数据寄存器空
    volatile uint32_t      : 24;  // bit 8~31: 保留
} USART_SR_Bits;

#define USART1_SR (*(volatile USART_SR_Bits *)0x40011000)

// 用法：比位运算直观
while (!USART1_SR.TC);   // 等发送完成
```

> [!warning] 位域跨平台不可移植
> C 标准对位域的布局只做最宽松约定。位序（LSB/MSB first）、能否跨字节边界、底层基本类型——不同编译器处理方式不同。**位域适合同一平台上的寄存器映射，不适合跨平台通信。**

### 位域的原子性问题

对位域成员的操作**不是原子的**——即使只改一个位，编译器也可能产生「读-改-写」序列：

```c
// ❌ 可能触发 RMW，非原子
status_reg->ready = 1;

// ✅ 直接写寄存器值，保证原子性
USART1->SR |= (1 << 5);
```

Cortex-M 上用 `__IO` 宏或内联函数完成位操作更可靠。

## `offsetof` 与 `container_of`

### offsetof — 编译期偏移计算

```c
#include <stddef.h>

struct example {
    uint8_t  a;
    uint32_t b;
    uint16_t c;
};

offsetof(struct example, b);  // 返回 4（a 1字节 + padding 3字节）
offsetof(struct example, c);  // 返回 8
```

**经典实现**：

```c
#define offsetof(TYPE, MEMBER) \
    ((size_t)&((TYPE *)0)->MEMBER)
```

这个宏假设地址 0 处有结构体，让编译器计算偏移量——**不产生实际内存访问，零运行时开销**。

### container_of — 从成员反查宿主

Linux 内核中广为人知的模式：已知结构体成员的指针，反推出包含它的结构体指针：

```c
#define container_of(ptr, type, member) ({ \
    const typeof(((type *)0)->member) *__mptr = (ptr); \
    (type *)((char *)__mptr - offsetof(type, member)); \
})

// 实战：从链表节点找到宿主结构体
struct sensor_data *sd = container_of(node, struct sensor_data, list);
```

## 五种方案选型矩阵

以存储 1000 条传感器数据（温度 `int16_t`、湿度 `uint8_t`、2 位标志）为例：

| 方案 | 单条大小 | 1000条占用 | 访问速度 | 适用场景 |
|------|----------|-----------|----------|----------|
| 对齐结构体 | 8 B | 8 KB | ⚡ 最快 | **常规存储首选** |
| packed 结构体 | 4 B | 4 KB | 🐢 慢 2~5x | 传输/存储格式 |
| 位域结构体 | 4 B | 4 KB | 🐢 稍慢 | 硬件寄存器映射 |
| 手动位移宏 | 4 B | 4 KB | ⚡ 最快 | 极致优化 |

**选择建议**：

```
常规存储     → 对齐结构体（大成员放前面）
协议/文件格式 → packed（确认 CPU 支持非对齐访问）
硬件寄存器    → 位域 + volatile
极致省 RAM   → 手动位移宏 + memcpy
```

## 四个常见坑

### 坑 1：结构体值传递

```c
// ❌ 100 字节的结构体每调用一次就拷贝 100 字节到栈
void process(struct sensor_data data);

// ✅ 只传 4 字节指针
void process(struct sensor_data *data);
```

### 坑 2：packed + volatile 叠加

对 packed 结构体成员加 `volatile`，非对齐访问时 volatile 语义可能触发额外总线操作。安全做法：

```c
uint32_t val;
memcpy(&val, &p->reg, sizeof(val));  // 用 memcpy 安全读取
```

### 坑 3：位域操作非原子

前文已述——即使改一个位也可能触发 RMW 序列。

### 坑 4：`sizeof` 是编译期运算符

`sizeof` 和 `offsetof` 在编译时就被常数替换，**没有运行时开销**——别怕用它们。

## 属性速查

| 属性 | 效果 | 代价 |
|------|------|------|
| 自然对齐（默认） | CPU 能一次读完 | padding 浪费内存 |
| `__attribute__((packed))` | 取消填充，极致省 RAM | M0 上 HardFault，M3+ 上 2~5x 降速 |
| `__attribute__((aligned(n)))` | 提升整体对齐 | 不省内存但保证对齐边界 |
| 位域 `:n` | 按位打包 | 不可移植、非原子 |
| 调换成员顺序 | 减少 padding | 零代价——永远应该做 |
